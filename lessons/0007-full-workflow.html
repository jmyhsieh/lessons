綜合演練 — 從任務描述到 PR 的完整一輪

任務目標：挑一個工作 repo 裡的真實中型任務，用官方推薦的四階段流程（Explore → Plan → Implement → Commit）獨立跑完一輪，並學會兩個新武器：可驗證的成功條件與context 管理。這是第 2–5 課的總驗收。

官方四階段流程（Best Practices）

階段模式你做的事
1. Exploreplan mode讓它讀相關程式碼、回答你的問題，不動手
2. Planplan mode要求具體計劃：動哪些檔、什麼順序，來回修到滿意
3. Implementdefault批准計劃後實作，逐項審 diff，要求跑測試
4. Commitdefault看完整 diff → commit → 開 PR 走團隊 review
什麼時候跳過 plan？官方判準：「如果一句話就能描述 diff，就不用 plan」。修 typo、加 log 直接做；跨多檔、不熟的區域、方向不確定 → 一律先 plan。

新武器一：給它一個能自己跑的驗證

官方最重要的一條心法：給 Claude 一個能自己執行的檢查（測試、build、lint），它就能自己迭代到通過；沒有的話，你就是它的驗證迴圈。比較：

❌ 「實作 email 驗證函式」
✅ 「實作 validateEmail：user@example.com → true、
    invalid → false、user@.com → false。
    寫成測試，實作後執行測試並修到全過。」

並要求它出示證據（測試輸出、執行的指令與結果），而不是只說「完成了」。

新武器二：context 管理

對話越長，它的表現越差 — context 塞滿無關內容是最常見的效能殺手。三個習慣：

  • 不相關的任務 → 開新對話（CLI 是 /clear）。別把一個 session 當萬用聊天室。
  • 糾正超過兩次還不對 → 砍掉重練：開新對話，把學到的教訓寫進更精準的第一句 prompt。乾淨的 session ＋好 prompt，幾乎總是贏過塞滿失敗嘗試的長對話。
  • 做錯了可以倒帶：/rewind（CLI 按兩下 Esc）能還原對話與程式碼到先前的檢查點。但它只追蹤 Claude 自己的修改，不取代 git。

實作：完整跑一輪（做完打勾）

挑一個半天內做得完的真實任務。動手前先寫下：「怎樣算成功？」— 最好是一個它能自己跑的檢查（哪個測試要過、哪個指令要成功）。

描述任務時給足脈絡：相關檔案路徑、症狀、預期行為、要它遵循的現有 pattern。審計劃，修到滿意。

批准計劃，prompt 裡明確要求：「實作後執行 [你的驗證]，失敗就修到通過，最後給我看測試輸出。」逐項審 diff。

看完整 diff → commit → 開 PR。PR 描述讓它代筆，你審核。

回顧這一輪：哪裡它表現超出預期？哪裡你糾正了它？被糾正的點若是「它本該知道的專案慣例」→ 立刻補進 CLAUDE.md（第 4 課的活文件迴圈）。

🎉 恭喜 — 任務目標二達成：你能在正式 repo 獨立使用 Claude Code 了。回對話視窗交復盤報告，我會記入學習紀錄並規劃進階主題。

觀念檢查（憑記憶作答）

1. 已經糾正它兩次同一個問題還是不對，下一步最該？

官方明確建議：兩次糾正失敗後 context 已被失敗嘗試污染，砍掉重練幾乎總是更快。

2. 「修 README 裡的一個錯字」該走什麼流程？

一句話能描述 diff 的任務直接做 — plan 是工具不是儀式。流程的價值與任務的不確定性成正比。

3.（複習第 5 課）四階段中 Explore/Plan 用 plan mode 而不是口頭約定，是因為？

（間隔複習）和第 5 課同一個原則：口頭是指引，模式是強制。
