用 /implement 完成一個有限切片

本課成果：一個已通過測試與程式碼審查的有限切片（bounded slice）。

本課只做：完成一個小而可驗收的功能切片。
先不要做：實作尚未對齊的需求，或一次處理多張工作項目。

先準備可驗收的輸入

/implement 需要明確的範圍。你可以使用目前對話中已確認的小型實作計畫，或提供規格與一張工作項目。兩種方式都要寫清楚驗收條件、預計修改的範圍，以及要跑的測試。

已確認的計畫或「規格 + 單張工作項目」
  → /implement
  → 測試
  → /code-review
  → commit
工程師要守的邊界：Claude Code 若想順手擴大修改範圍，先停下來看 git diff，再把工作收回這張工作項目的驗收條件。

實作步驟（做完打勾）

確認它只有一個主要結果，並列出驗收條件、相關檔案與測試命令。若資訊還不完整，先回前兩課補規格與工作項目。

/implement 根據 [規格路徑] 與 [工作項目路徑] 實作。
只處理這張工作項目；先回報預計修改的檔案與驗證命令。

核對它提出的檔案清單與你的預期是否一致。涉及額外權限、套件安裝或範圍外檔案時，先看原因再決定是否允許。

用 /tdd 保留紅燈到綠燈（RED → GREEN）的證據。測試必須能在需求被破壞時失敗，才算保護到這次修改。

先看 git diff，確認沒有範圍外修改；再執行程式庫規定的測試、型別檢查或程式碼檢查。未執行的檢查要留下原因。

/code-review [審查起點]

提供提交、分支、標籤或合併基準作為審查起點。處理審查發現後，再建立可指回工作項目與驗收結果的提交。

完成條件：有限切片符合工作項目、適用測試已通過、審查問題已處理，並保留 git diff --stat。

觀念檢查（憑記憶作答）

1. 哪種內容適合交給 /implement？

/implement 適合範圍已對齊、能獨立驗收的工作。

2. Claude Code 修改了工作項目以外的檔案，第一步該做什麼？

git diff 能讓你看見實際變更，並及早阻止範圍膨脹。

3. 為什麼要看過測試先失敗？

沒有紅燈證據，就無法確認測試是否真的保護了這次修改。
