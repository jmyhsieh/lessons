用 /implement 完成一個 bounded slice

目標：用 /implement 完成一個已對齊、可驗收的 bounded slice。單-session 小需求可沿用目前 context 裡的明確 plan；跨 session 工作則依 spec 與第 07 課切出的單張 ticket 冷啟動。兩條路都把 /tdd、測試、/code-review 與 commit 收進同一條實作流程。

本課只做：完成一個小而可驗收的 slice。
先不要做：實作尚未對齊的需求、一次丟整批 tickets，或把大功能假裝成單-session 工作。

Pipeline 全景：你在這裡

同一 context 的已對齊 plan ─┐
spec → 單張 ticket ─────────┴→ /implement → tests → /code-review → commit → /handoff

/implement 是 orchestrator

/implement 的原文職責是「依 spec 或 tickets 實作工作」。它不是單純寫 code，而是把施工流程串起來：

階段你要看什麼
確認一種 bounded input同一 context 的已對齊 plan，或 spec 加單張 ticket；只做這個 slice，不順手擴 scope。
使用 /tdd在預先同意的接縫上做 RED → GREEN；先不重構。
規律跑檢查常跑單檔測試與 typecheck，最後跑完整測試。
使用 /code-review以明確 fixed point 檢查 Standards 與 Spec，再處理發現。
commit 當前分支commit message 要能指回 originating plan／ticket 與驗收結果。
重點：/tdd 與 /code-review 是 /implement 裡的品質紀律，不是與 /implement 平行的主流程。
Reviewed TDD 邊界：目前 snapshot 把 TDD 明確定義為 RED → GREEN；refactoring 不在這個 loop 內，而是在 review 階段處理。不要把熟悉的「red-green-refactor」口號誤讀成這份 skill 的實際執行順序。

/code-review 先釘住 fixed point

/code-review 不只可放在 /implement 收尾，也能獨立 review 一個 PR、branch 或 WIP。無論哪種用法，都要先由你提供 commit、branch、tag 或 merge-base 當 fixed point，再固定使用 git diff <fixed-point>...HEAD 的 three-dot diff。

準備Review 規則
確認邊界先確認 fixed point 可解析，而且 diff 不是空的；錯誤 ref 或空 diff 要在派 reviewer 前就停下來。
找依據先找 originating requirement／plan／spec，以及 AGENTS.md、CONTRIBUTING.md 等 repo standards；不要讓 reviewer 自己猜需求或規範。
平行雙軸Standards reviewer 檢查 repo 規則，並把 Fowler code smell baseline 當 heuristic；repo 明文規則優先。Spec reviewer 則檢查漏做、scope creep 與做錯的需求。
保留分界兩份報告 side by side 呈現，不合併 findings，也不跨軸重排嚴重度。

實作步驟（做完打勾）

單-session fast path：需求已在目前 context 對齊，而且有明確驗收條件、測試接縫與窄 scope，就直接使用這份 plan。跨 session 路徑：選第 07 課產出的單張 frontier ticket，確認它有 spec 連結、驗收條件、測試接縫與 Blocked by。

# 單-session fast path：留在已對齊的目前 context
/implement 依剛確認的 plan 完成這個 bounded slice

# 跨 session 路徑：用 durable artifacts 冷啟動
/implement 根據這份 spec 與這張 ticket 實作：[spec 路徑] [ticket 路徑]

fast path 必須留在已有對齊脈絡的同一個 context；若工作需要換 session，就先產生 durable spec／ticket。每張 ticket 使用新的 context，只從 spec、單張 ticket、CONTEXT.md 與 ADR 冷啟動。如果它試圖擴大 slice 或一次處理多張 ticket，立刻收斂。

確認每個關鍵行為至少有一次 RED → GREEN。沒看見失敗的測試，不要相信它真的保護了需求；這一步不順手重構，結構調整留到 review 階段。

要求它回報 typecheck、單檔測試、完整測試或本 repo 對應的驗證命令。命令、結果與未跑原因都要講清楚。

/code-review [fixed point]

fixed point 必填。先確認它可解析、three-dot diff 非空，再找出 originating requirement／plan／spec 與 repo standards，讓 Standards 與 Spec reviewers 平行檢查。讀完 side-by-side findings、處理完發現後，才 commit 到目前分支。

觀念檢查（憑記憶作答）

1. /implement 最適合吃什麼輸入？

/implement 可承接同一 context 中已對齊的小 plan，也可依 spec 與單張 ticket 冷啟動；關鍵是 input 已對齊而且 scope bounded。

2. 開始 /code-review 前，哪組準備才完整？

先釘住 fixed point 與非空 diff，再把 spec 與 standards 分別交給平行雙軸 reviewer。結果要 side by side 保留，不合併或跨軸重排。

3. 沒看過測試先失敗就綠了，該怎麼辦？

TDD 的信任來自 RED → GREEN。沒看過 RED，就不知道測試是否真的抓得到問題。
