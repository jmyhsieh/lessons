Phase 2 · 第 06 課 · 約 60 分鐘 · 實作課（pipeline 收官）

用測試帶著實作前進（/tdd）

目標：認領 Phase 2 第 05 課切出的第一張 issue，用 /tdd 紅綠燈循環實作到驗收條件全過。完成即達成 Phase 2 成功條件第二條：對齊 → PRD → issues → TDD 實作的完整 pipeline。

本課只做：用紅綠燈循環完成一張可驗收 issue。
先不要做：先寫一大批測試或一次改完整個功能。

核心哲學（skill 原文）

「測試應該透過公開介面驗證行為，不是實作細節。程式碼可以整個換掉；測試不應該動。」

好測試壞測試
走真實路徑、讀起來像規格（「使用者能用有效購物車結帳」）mock 內部協作者、測私有方法、繞過介面直接查 DB
重構後依然存活警訊：重構沒改行為，測試卻壞了 — 它在測實作不是行為
對大型或高風險 repo，這條哲學就是重要保護機制：耦合實作的測試會把脆弱架構固定住（動不了）；驗證行為的測試才給你日後重構的自由。本課的判斷準則是：測試要編碼「為什麼重要」，不是鎖死「現在怎麼做」。

最大反模式：水平切（又來了）

skill 用最重的語氣警告：不要先寫完所有測試、再寫完所有實作。一批寫好的測試測的是「想像中的行為」，會變成測資料形狀而非使用者行為。正確節奏與 Phase 2 第 05 課的 issue 切法同一個道理 — 垂直：

錯（水平）： RED: test1..test5 → GREEN: impl1..impl5
對（垂直）： test1→impl1，test2→impl2，每輪都帶著上一輪學到的

/tdd 的四段流程

  1. Planning — 它會先和你確認：公開介面長怎樣？哪些行為最重要？不可能測所有東西 — 火力集中在關鍵路徑與複雜邏輯。測試命名用 CONTEXT.md 詞彙、尊重 ADR。計劃要你核准才動工。
  2. Tracer bullet — 第一發：一個測試證明路徑端到端通。
  3. Incremental loop — 一次一個測試 → 最小程式碼讓它過 → 重複。不寫超前的程式碼。
  4. Refactor — 全綠之後才重構（never refactor while RED），每步重構後重跑測試。
你的監工清單（每輪循環問自己）：這個測試描述的是行為還是實作？只用了公開介面嗎？內部重構後它還活著嗎？程式碼是不是「剛好夠過這個測試」、沒有偷加投機功能？— 這四題就是 skill 內建的 per-cycle checklist。

實作步驟（做完打勾）

挑 Phase 2 第 05 課標 AFK、無 blocked-by 的第一張。開分支（Phase 1 第 04 課的護欄不因 Phase 2 而免除）。

/tdd 實作這張 issue：[issue 檔案路徑或內容]

重點審它列的「要測的行為清單」：對照 issue 的驗收條件，有漏嗎？優先序對嗎？介面合理嗎？

確認你親眼看到 RED（測試先失敗）再看到 GREEN。沒看到 RED 的測試不可信 — 它可能根本沒在測東西。

每輪用監工清單抽查。特別盯：它有沒有偷跑（一次寫好幾個測試）？有沒有在 RED 狀態下順手重構？

全綠後讓它提重構候選，逐項批准。最後對照 issue 驗收條件逐條打勾 → 完整 diff review → commit → 把 issue 標記完成。

🎉 Phase 2 完整 pipeline 跑通：grill → PRD → issues → TDD！回對話視窗交報告：紅綠循環跑了幾輪？它有沒有試圖偷跑被你抓到？

觀念檢查（憑記憶作答）

1. 重構之後（行為沒變）有三個測試紅了。正確解讀是？

行為沒變而測試壞 = 測試在測實作（skill 明指的警訊）。當然先確認行為真的沒變 — 確認後，該修的是測試。

2. 它一口氣寫了五個測試然後開始實作。你該？

這正是 skill 最重警告的水平切：批量測試測的是想像的行為。一測一實作，每輪帶著上一輪學到的。

3.（複習 Phase 1 第 12 課）為什麼 TDD 特別適合 AI 寫程式？

（間隔複習）Phase 1 第 12 課 心法：給它能自己跑的檢查，它就能自己迭代到通過。TDD 就是把這個驗證迴圈制度化 — 每一步都有紅綠燈訊號。
