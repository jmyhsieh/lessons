本課成果：一份架構健檢結果，並選出一個值得繼續追問的候選問題。

本課只做：找出一個值得整理的架構摩擦。
先不要做：把架構健檢變成大型重構清單。

核心概念：深模組（deep module）

這個工作技能找的是「深化機會」：用較小的介面隱藏更多實作複雜度。相關詞彙集中在 codebase-design：

現行對應：深模組與介面設計詞彙現在集中在共用的 codebase-design；/improve-codebase-architecture 仍是用這套語言掃描架構深化機會的主力。
術語意思
模組任何有介面＋實作的東西（函式、類別、套件）
介面呼叫者必須知道的一切：型別、不變量、錯誤模式、順序與設定，而不限於型別簽名
深度（Depth）介面的槓桿：小介面後面藏大量行為 = 深；介面跟實作一樣複雜 = 淺
接縫（Seam）介面所在之處；不改內部就能換行為的地方
轉接器在接縫上滿足介面的具體角色；名稱描述它填入哪個位置，不描述內部材料或實作大小
槓桿與集中性（Leverage / Locality）深度給呼叫者的好處，以及把改動、錯誤與知識集中一處的維護效益
三句口訣：(1) 刪除測試：想像刪掉這個模組；複雜度消失，代表它是過水層；複雜度散落到 N 個呼叫端重新出現，代表它有在賺自己的飯。(2) 介面就是測試面（接 Phase 2 第 08 課：測行為不測實作）。(3) 一個轉接器 = 假想接縫，兩個轉接器 = 真接縫。

先圈範圍：還用不到就先別做（YAGNI）也是架構原則

先用使用者已點名的模組、子系統（subsystem）或痛點作為範圍，不自行擴張。若沒有指定，才讀 git log --oneline，從近期反覆被修改的區域選一個窄範圍。目標是找一個值得深化的接縫，不要替整個程式庫建立重構待辦清單。

三段流程

  1. 探索 — 先套用範圍關卡，再讀 CONTEXT.md 與 ADR，請探索代理在範圍內找出理解成本與變更摩擦。
  2. HTML 報告 — 寫到暫存目錄，不污染程式庫。每個候選列出檔案、問題、解法、前後差異與建議強度：優先處理、值得探索或暫不建議。
  3. 追問 — 你挑一個候選，要求 Claude Code 說明深化後的模組、接縫與測試。新領域概念放進 CONTEXT.md；重要而難以回頭的取捨才記成 ADR。

兩個對高風險程式庫重要的設計：建議若與既有 ADR 衝突，只在摩擦真的大到值得重開決策時才提出（不重新爭論已決定的事）；領域講 CONTEXT.md 的語言、架構講 codebase-design 的語言。

實作步驟（做完打勾）

/improve-codebase-architecture [模組、子系統或具體痛點]

有明確目標就直接用；沒有才先讀 git log --oneline，選近期反覆變動的一個高變動區。第一次別掃全程式庫，等它產出並打開 HTML 報告。

逐卡閱讀，對每個「淺模組」指控跑一次刪除測試：刪掉它，複雜度是消失還是散落？你同意它的建議強度嗎？

建議挑「優先處理且範圍小」的。追問：深化後的模組長什麼樣？接縫後面藏什麼？哪些測試可以保留？

挑一個你認為不值得做的，給出理由，再跑 ADR 關卡：是否難以回頭、缺少背景會令人意外，而且存在真實取捨？三項全中才寫 ADR；「現在沒時間」等暫時理由直接跳過。

把追問後的計畫依規模分流：能一次完成的小改，直接用 /implement 做有限切片；需要跨工作階段的工作才走 /to-spec → /to-tickets → /implement。CONTEXT.md 或 ADR 的更新也要納入版控。

完成條件：健檢報告列出有程式證據的候選問題，並選定一個範圍明確、值得繼續追問的項目。

觀念檢查（憑記憶作答）

1. 刪掉某個包裝層（wrapper）模組後，它做的事在六個呼叫端各自重新出現。結論是？

刪除測試的判讀：複雜度重新散落到多個呼叫端，表示它原本把複雜度集中在一處；這正是深模組的價值。複雜度一起消失，才代表它可能只是過水層。

2. 你因為「這季沒有時間」拒絕一個候選，該怎麼記錄？

暫時排程不符合 ADR 關卡，也不能幫未來接手的人理解關鍵決策。只有三項條件全中才寫 ADR；CONTEXT.md 則只放領域詞彙。

3.（複習 Phase 2 第 08 課）「介面就是測試面」和 TDD 哲學的關係是？

（間隔複習）深模組的小介面 = 穩定的測試面；TDD 測行為不測實作。架構線和測試線在這裡會合：介面越深，測試越能在重構中存活。
