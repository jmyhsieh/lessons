Phase 3 · 第 11 課 · 約 45 分鐘 · 維護入口

用 /improve-codebase-architecture 找維護切入點

目標：學會「深模組」的語言，在真實 repo 跑一次架構健檢，得到一份視覺化報告，並對其中一個候選跑 grilling loop。這是四大失敗模式的最後一塊：architectural decay。

本課只做：找出一個值得整理的架構摩擦。
先不要做：把架構健檢變成大型重構清單。

核心概念：深模組（deep modules）

這個 skill 找的是「深化機會」— 把淺模組變深的重構。詞彙表現在集中在 shared codebase-design，每個建議都應使用同一套語言：

現行對應：深模組與介面設計 vocabulary 現在集中在 shared codebase-design；/improve-codebase-architecture 仍是用這套語言掃描架構深化機會的主力。
術語意思
Module任何有介面＋實作的東西（函式、類別、套件）
Interface呼叫者必須知道的一切：型別、不變量、錯誤模式、順序、設定 — 不只是型別簽名
Depth 深度介面的槓桿：小介面後面藏大量行為 = 深；介面跟實作一樣複雜 = 淺
Seam 接縫介面所在之處；不改內部就能換行為的地方（Phase 3 第 06 課 to-spec 問你的就是這個）
Adapter在 seam 上滿足 interface 的具體角色；名稱描述它填入哪個位置，不描述內部材料或實作大小
Leverage / Locality深度給呼叫者的好處 / 給維護者的好處（改動、bug、知識集中一處）
三句口訣：(1) 刪除測試 — 想像刪掉這個模組：複雜度消失 = 它是過水層；複雜度散落到 N 個呼叫端重新出現 = 它有在賺自己的飯。(2) 介面就是測試面（接 Phase 3 第 08 課：測行為不測實作）。(3) 一個 adapter = 假想接縫，兩個 adapter = 真接縫。

先圈範圍：YAGNI 也是架構原則

先用使用者已點名的 module、subsystem 或痛點作為 scope，不自行擴張。若使用者沒有指定，才讀 git log --oneline，從近期反覆被修改的 hot spot 選一個窄範圍；只有摩擦明顯散落在多處時才擴大。目標是找一個值得深化的 seam，不是替整個 repo 建重構 backlog。

三段流程

  1. Explore — 先套用上面的 scope gate，再讀 CONTEXT.md 與 ADR，派 Explore subagent（Phase 2 第 05 課的 context 隔離）在範圍內有機地走 codebase 找摩擦：理解一個概念要在很多小模組間跳？淺模組？為了好測而抽出純函式但 bug 都藏在呼叫端？
  2. HTML 報告 — 寫到 temp 目錄（不污染 repo）自動打開：每個候選一張卡（檔案、問題、解法、locality/leverage 效益、before/after 圖、建議強度 Strong / Worth exploring / Speculative），結尾給首選建議。此階段不提介面設計 — 報告完它會問你想深入哪個。
  3. Grilling loop — 你挑一個候選，進入追問對話（Phase 3 第 04 課的肌肉直接重用）。過程中：已釐清的新領域概念進 CONTEXT.md；拒絕候選的 load-bearing reason 只是 ADR 候選，還要同時通過「難以回頭＋缺少背景會令人意外＋真實 tradeoff」三項 gate 才寫。

兩個對高風險 repo 重要的設計：建議若與既有 ADR 衝突，只在摩擦真的大到值得重開決策時才提出（不重新爭論已決定的事）；領域講 CONTEXT.md 的語言、架構講 codebase-design 的語言。

實作步驟（做完打勾）

/improve-codebase-architecture [module、subsystem 或具體痛點]

有明確目標就直接用；沒有才先讀 git log --oneline，選近期反覆變動的一個 hot spot。第一次別掃全 repo，等它產出並打開 HTML 報告。

逐卡閱讀，對每個「淺模組」指控自己跑一次刪除測試：刪掉它，複雜度是消失還是散落？你同意它的 Strong/Speculative 分級嗎？

建議挑「Strong 且範圍小」的。走完追問：深化後的模組長什麼樣？接縫後面藏什麼？哪些測試存活？

挑一個你認為不值得做的，給出理由，再跑 ADR gate：是否難以回頭、缺少背景會令人意外，而且存在真實 tradeoff？三項全中才寫 ADR；「現在沒時間」等暫時理由直接跳過。

grill 出來的深化計劃依規模分流：同一 context 內已對齊、能一次完成的小改，直接用 /implement 做 bounded slice；需要跨 session 的工作才走 /to-spec → /to-tickets → fresh /implement。CONTEXT.md/ADR 的更新 commit 進版控。

觀念檢查（憑記憶作答）

1. 刪掉某個 wrapper 模組後，它做的事在六個呼叫端各自重新出現。結論是？

刪除測試的判讀：複雜度「重新散落到 N 個呼叫端」= 它本來把複雜度集中在一處（locality）— 這正是深模組的價值。消失才代表過水層。

2. 你因為「這季沒有時間」拒絕一個候選，該怎麼記錄？

暫時排程不符合 ADR gate，也不能幫未來探索者理解 load-bearing decision。只有三項條件全中才寫 ADR；CONTEXT.md 則只放領域詞彙。

3.（複習 Phase 3 第 08 課）「介面就是測試面」和 TDD 哲學的關係是？

（間隔複習）深模組的小介面 = 穩定的測試面；TDD 測行為不測實作。架構線和測試線在這裡會合：介面越深，測試越能在重構中存活。
