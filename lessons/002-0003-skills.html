把重複流程打包成指令（Skills）

本課成果：一個能在目前程式庫重跑的工作技能（Skill）。

本課只做：判斷重複工作流程是否值得做成工作技能（Skill）。
先不要做：把一次性任務或尚未穩定的流程做成工作技能。

什麼時候該做成工作技能（官方文件）

訊號跟 CLAUDE.md 類似但對象不同：

  • 你發現自己重複貼同一段指示、檢查清單或多步驟流程到對話裡
  • CLAUDE.md 裡某一段已經長成「流程」而不是「事實」

載入方式不同：CLAUDE.md 的指示會在每個工作階段載入；工作技能（Skill）的完整內容只在使用時載入。

工作技能仍會占用對話脈絡：Claude Code 會先讀取所有工作技能的名稱與用途說明（description），大約可使用模型對話脈絡上限的 1%。數量太多或說明太長時，較少使用的用途說明會被縮短。可用 /context 查看實際占用量，再用 /doctor 找出主要來源。

選擇原則：長篇參考資料或偶爾才用的流程放進工作技能；每次都必須遵守的短規則放進 CLAUDE.md。

結構：一個資料夾 + SKILL.md

.claude/skills/summarize-changes/SKILL.md   ← 專案（隨 git 共享）
~/.claude/skills/<name>/SKILL.md            ← 個人（所有專案可用）

資料夾名稱就是指令名稱（deploy-staging/ → /deploy-staging）。SKILL.md 長這樣：

---
description: 摘要未提交的變更並標記風險。當使用者問
  「改了什麼」、要提交訊息、或要審查程式差異時使用。
---

1. 執行 git diff 取得所有未提交變更
2. 依模組分組摘要
3. 標記：碰到設定檔／migrations／權限相關的變更
4. 用團隊格式產生提交訊息草稿

兩種觸發方式，一個開關

方式怎麼觸發適合
你手動輸入 /skill-name有副作用的流程（部署、發布）
Claude 自動你的話符合 description 描述的情境知識型、無副作用的輔助
有副作用的工作技能一定加 disable-model-invocation: true，讓它只能由你手動觸發 — 你不會想要 Claude「覺得相關」就自己跑部署。另外 $ARGUMENTS 可接收參數：/fix-issue 1234 會把 1234 帶進內容。

寫好 description 是自動觸發的關鍵：說清楚「做什麼」與「什麼情境用」，把主要使用情境寫在最前面。工作技能目錄有變更會即時生效，不用重啟。

實作步驟（做完打勾）

回想最近兩週：你重複向 Claude 解釋過什麼流程？（例：「我們的 PR 前檢查」「依模板建新 API 端點」「產生發行說明」）。挑一個。

在工作程式庫建立 .claude/skills/<名稱>/SKILL.md。可以請 Claude 代寫初稿，但用途說明與步驟要自己打磨 — 步驟要具體到「另一個不認識你的工程師也能照做」。有副作用就加 disable-model-invocation: true。

在同一個工作階段直接輸入 /你的skill名（變更即時生效）。觀察它是否照步驟走、結果是否符合預期，來回修 SKILL.md 到穩定。

開新對話，用自然語言描述該情境（不要提工作技能名稱），看 Claude 會不會自己載入這個工作技能。不會的話 → 修改用途說明，把觸發情境寫得更像你實際會說的話。

.claude/skills/ 進版控，照常走 PR。隊友拉取變更後就多了這個斜線指令。

完成條件：工作技能已進入版控、可以重跑，並留下手動或自動觸發的實測結果。

觀念檢查（憑記憶作答）

1. 「我們的 API 命名慣例」（兩行規則，每次寫 code 都要遵守）該放？

每次都要、又短 → CLAUDE.md。工作技能的優勢在「用到才載入」，對每次都需要的兩行規則沒有意義；掛鉤是終端機指令，沒辦法「強制命名風格」這種需要判斷的事。

2. 「/deploy-staging 部署流程」最該加哪個檔頭設定（frontmatter）？

部署有副作用 — 必須只能手動觸發，防止 Claude 自行判斷「相關」就執行。when_to_use 反而是給自動觸發用的，方向相反。

3.（複習三層模型）「提交前必跑測試，不過就不准結束」這種保證，用什麼實現？

（間隔複習 Phase 2 第 01 課）關鍵字是「必」= 保證 = 自動化掛鉤。工作技能和 CLAUDE.md 都靠模型配合，只有掛鉤是系統強制。
