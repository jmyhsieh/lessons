Phase 1 · 第 11 課 · 約 20 分鐘 · 完整流程

從探索到提交的安全四步驟

本課成果：一筆依「探索、規劃、實作、提交」順序完成的小改動。

本課只做：練一次探索、規劃、實作、提交的安全節奏。
先不要做：跳過規劃或審查，直接要求它大量修改。

四階段流程

階段模式你要把關的事
探索（Explore）規劃模式它讀哪些檔？有沒有問清楚需求？
規劃（Plan）規劃模式計畫是否列出檔案、步驟、風險？
實作（Implement）Manual/default審核權限提示與程式差異；完成後跑驗收條件。
提交（Commit）Manual/default先確認驗證通過與完整程式差異，再寫清楚提交訊息。
一句話能描述程式差異的小改可以省略規劃；跨檔、不熟、方向不確定，就完整跑四階段。

實作步驟（做完打勾）

半天內做得完、出錯後能復原、範圍清楚。不要拿部署、資料庫移轉（migration）或大型重構當第一次練習。

使用規劃模式。探索相關檔案並提出計畫。
List files you expect to modify. Do not edit yet.

計畫過關後離開規劃模式。每次修改都看過再同意；看到偏離範圍就拒絕。

先執行任務的驗收條件，保留完整命令、結束狀態與關鍵輸出；失敗就修正並重跑。驗證通過後，桌面 App：點程式差異統計或打開差異檢視窗格查看完整變更。若 / 清單有 /diff，也可當快捷。最後才請它產生提交訊息草稿，你審過才提交。

完成條件：小改動依序完成探索、規劃、實作與提交，並保留驗證輸出及完整差異。

觀念檢查

1. 「修 README 一個錯字」該完整跑四階段嗎？

流程是為了降低不確定性，不是儀式。

2. 探索／規劃階段使用規劃模式的核心原因是？

這是 Phase 1 第 04 課的同一條原則：模式限制比口頭提醒可靠。
