Phase 2 · Lesson 0019 · 約 45 分鐘 · 實作課（維運線）

/diagnose — 維運除錯的紀律迴圈

目標：學會六階段診斷紀律，下次內部系統出 bug 時用 /diagnose 跑完整迴圈。對封閉遺產系統，這是日常價值最高的一支 skill — 維運的本質就是診斷。

整個 skill 就一句話

Phase 1 的原文：「This is the skill. Everything else is mechanical.」— 有了快速、確定性、agent 能自己跑的 pass/fail 訊號，bug 就等於修好了 90%；沒有它，盯 code 盯再久都沒用。這是第 7 課「給它能自己跑的驗證」的除錯版，也是整套課程的母題。

六階段地圖

階段做什麼鐵律
1. 建回饋迴圈用十種武器之一造出 pass/fail 訊號沒有迴圈不准進下一階段
2. Reproduce親眼看 bug 出現必須是使用者描述的那個 bug，不是隔壁的
3. Hypothesise先列 3–5 個排序假說再測任何一個每個假說要可否證（能說出預測）
4. Instrument每個探針對應一個預測，一次改一個變數debug log 全部加唯一前綴（如 [DEBUG-a4f2]）
5. Fix + 回歸測試先寫回歸測試（看它失敗）再修只在「正確的接縫」寫；沒有正確接縫＝那本身就是發現
6. Cleanup + 復盤grep 前綴清光 debug log、記錄學到的沒清乾淨不算完成

Phase 1 的武器庫（節選）

十種造迴圈的方法，大致依序嘗試：失敗測試 → curl/HTTP script → CLI＋fixture 比對快照 → headless browser → 重放捕獲的 trace（存下真實 payload 重放）→ 拋棄式 harness（mock 依賴只跑出 bug 的路徑）→ fuzz 迴圈 → bisection harness（自動化「回到狀態 X 檢查」讓 git bisect 跑）→ 差分迴圈（新舊版同輸入比輸出）→ 最後手段 HITL script。

三個對遺產系統特別重要的細則： (1) 迴圈本身要迭代 — 「30 秒且會閃爍的迴圈只比沒有好一點；2 秒且確定性的迴圈是除錯超能力」。 (2) 非確定性 bug：目標不是乾淨重現而是「拉高重現率」— 觸發 100 次、平行化、加壓、注入 sleep，50% 重現率就能除錯。 (3) 真的造不出迴圈時它會停下來明說，向你要環境存取、捕獲物（HAR/log dump/錄影）或臨時埋點的許可 — 它被禁止在沒有迴圈時瞎猜假說。

你的角色：Phase 3 的關鍵一秒

它列出排序假說後會先給你看 — 這是你部落知識的高光時刻：「#3 那個模組我們上週才改過」一句話就能瞬間重排序。skill 也明定你不在場時它會照自己的排序繼續，不會卡住。

實作步驟（做完打勾）

從維運待辦挑一個「known issue 但一直沒人查」的 bug — 最好是有點難重現的，才能看出這套紀律的價值。

/diagnose [描述症狀：錯誤訊息、何時發生、影響誰]

觀察它選哪種武器造迴圈。迴圈造出來後問自己：夠快嗎？訊號夠尖嗎（assert 的是具體症狀還是「沒 crash」）？

看到假說清單時認真讀，用你對系統的了解重排序或排除（「這個我們查過了」）。

確認：回歸測試先紅後綠了嗎？它寫測試的接縫真的能重現 bug 的觸發模式嗎？若它回報「沒有正確接縫」— 把這個發現餵給第 18 課的架構健檢。

grep debug 前綴確認清光、原始（未最小化）情境重跑通過、修 bug 過程的學習若值得就進 CONTEXT.md/ADR。

觀念檢查（憑記憶作答）

1. bug 很難重現（約 1% 機率），/diagnose 的正確策略是？

skill 原文：目標不是乾淨重現而是「更高的重現率」— 50% 就能除錯，1% 不行。沒有迴圈就猜著修，正是這套紀律要根除的行為。

2. 為什麼要求「先列 3–5 個假說再測任何一個」？

單一假說生成會錨定（anchoring）— 第一個合理解釋會吸走所有注意力。先發散再排序，而且每個假說都要能說出可否證的預測。

3.（複習第 17 課）Phase 5 「先寫回歸測試、看它失敗、再修」對應 TDD 的什麼？

（間隔複習）同一條鐵律：測試必須先紅 — 證明它真的在測這個 bug — 修完轉綠才有意義。診斷迴圈就是 TDD 哲學的除錯變體。
