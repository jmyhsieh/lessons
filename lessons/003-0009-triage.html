Phase 2 · 第 09 課 · 約 40 分鐘 · 外部回報入口

用 /triage 處理外部回報

本課成果：一張已完成分類、可以交給 Claude Code 處理的議題（issue）。

本課只做：把缺陷回報整理成可處理工作。
先不要做：把每個回報都直接交給代理實作。

缺陷流水線全景

議題回報 → /triage（分流到狀態）→ ready-for-agent
                                                  ↓
                            /diagnosing-bugs 或 /implement 接手
入口邊界：/triage 只處理你沒有建立、以原始回報形式進來的議題或外部 PR。/to-tickets 產出的工作項目已經是 ready-for-agent，不要再送進 triage。

先有耐久議題

你可以從 GitHub／GitLab／本機 Markdown／其他議題追蹤系統手動建立議題；若你的本機工作技能清單還有 /qa，也可以用它做對話式建檔。無論從哪個入口建立，議題（issue）都要能長期使用：

  • 輕度澄清 — 最多問 2–3 個短問題（預期與實際、重現步驟、穩定或間歇），「不要過度訪談」。
  • 背景探索 — 邊聊邊派 Explore 分身查程式庫，但目的不是找修法，是學該區域的領域語言、搞懂功能本該做什麼。
  • 議題必須耐久（durable） — 用使用者視角與領域術語寫，不寫檔名、行號、內部實作 — 大重構之後它仍然成立。一次抱怨若含多個獨立問題，它會拆成多張。
現行狀態：/qa 已不是上游主線工作技能。本課保留它作為本機舊版可選入口；穩定主線是把任何來源的回報整理成議題，再交給 /triage 分流。

/triage：七個角色的狀態機

每張議題帶一個類別＋一個狀態：

類別（2）bug ／ enhancement
狀態（5）needs-triage → needs-info（等回報者補件，回覆後回到 needs-triage）／ ready-for-agent ／ ready-for-human ／ wontfix

分流一張議題／PR 的流程：讀全文與先前分流筆記 → 依領域概念查「是否其實已實作」與「是否曾被 .out-of-scope/ 拒絕」→ 給你建議＋理由（等你裁決）→ 驗證主張（錯誤重現症狀；檢出 PR 的程式差異並跑相關檢查）→ 不夠清楚就用 /grilling＋/domain-modeling → 套用結果。四個制度細節：

  • 它發的每則內容都標 「This was generated by AI during triage」 — 透明度。
  • ready-for-agent 會附 代理任務摘要（agent brief）（讓 AFK 代理能冷啟動的完整說明）；ready-for-human 同格式但註明為何不能委派（判斷、外部存取、設計決策）。
  • 若追蹤系統設定允許處理外部 PR，/triage 也會把它當成「附程式碼的議題」進同一套流程。這項功能預設關閉，需要時再修改 docs/agents/issue-tracker.md。
  • wontfix 的 enhancement 寫進 .out-of-scope/ 知識庫 — 未來類似提案進來，它會比對並引用先前的拒絕理由。和 Phase 2 第 11 課「拒絕也是知識」同一個哲學。

實作步驟（做完打勾）

把你腦中積壓的 2–3 個真實問題寫成議題：使用者視角、預期與實際、重現線索、影響範圍。若用 /qa 輔助建檔，也要檢查它是否偷寫檔名或行號。

/triage 看看有什麼需要我處理的

它會列三個桶（未標記／needs-triage／needs-info 有新回覆）。剛建的議題應該在裡面。

逐張走：聽它的建議與理由 → 你裁決。錯誤類盯它的重現嘗試：重現結果有沒有如實回報？至少把一張推到 ready-for-agent 並讀它寫的任務摘要，再用「冷啟動的陌生人看得懂嗎」來檢驗。

挑一個你明知不會做的 enhancement 走 wontfix，確認拒絕理由進了 .out-of-scope/。

把那張標為 ready-for-agent 的議題交給 /implement。只有難解、間歇或回歸錯誤才改走 /diagnosing-bugs 建立緊密回饋迴圈。

完成條件：議題已有重現證據、正確分類與負責範圍，符合條件時才加上 ready-for-agent。

觀念檢查（憑記憶作答）

1. 缺陷議題為什麼不該綁死檔名與行號？

耐久性是核心設計：行為描述（用領域語言）在大重構後依然正確，檔名行號則很快過期。背景探索學的是語言，不是定位。

2. 一張錯誤重現失敗、回報者描述也含糊，最可能的正確狀態是？

工作技能原文：重現失敗或細節不足 = 強烈的 needs-info 訊號。回報者補件後回到 needs-triage 再評。直接 wontfix 或丟給人都是浪費。

3. 為什麼要把 wontfix enhancement 寫進 .out-of-scope/？

.out-of-scope/ 保存耐久的拒絕理由，讓未來分流能比對相似提案；它不是 ADR 的替代品，也不會隱藏原議題。

4. /to-tickets 剛產出的 ready-for-agent 工作項目，下一步應該是？

/to-tickets 產出的工作項目已經經過切片、阻塞關係與驗收確認，不是外部原始回報；重跑 triage 只會重複工作。
