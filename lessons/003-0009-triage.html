Phase 3 · 第 09 課 · 約 40 分鐘 · 外部回報入口

用 /triage 處理外部回報

目標：學會用 /triage 狀態機把 bug、產品摩擦或改進請求從回報分流到 ready-for-agent。若你的本機 skills 還有 /qa，可以把它當作建 issue 的可選入口；本課主線以現行 /triage 為準。

本課只做：把缺陷回報整理成可處理工作。
先不要做：把每個回報都直接交給 agent 實作。

缺陷流水線全景

issue 回報 → /triage（分流到狀態）→ ready-for-agent
                                                  ↓
                            /diagnosing-bugs 或 /implement 接手

先有耐久 issue

你可以從 GitHub / Linear / local files 手動建立 issue；若你的本機 skills 清單還有 /qa，也可以用它做對話式建檔。重點不是入口，而是 issue 要耐久：

  • 輕度澄清 — 最多問 2–3 個短問題（預期 vs 實際、重現步驟、穩定或間歇），「不要過度訪談」。
  • 背景探索 — 邊聊邊派 Explore 分身查 codebase，但目的不是找修法，是學該區域的領域語言、搞懂功能本該做什麼。
  • Issue 必須耐久（durable） — 用使用者視角與領域術語寫，不寫檔名、行號、內部實作 — 大重構之後它仍然成立。一次抱怨若含多個獨立問題，它會拆成多張。
現行狀態：/qa 已不是 upstream 主線 skill。本課保留它作為本機舊版可選入口；穩定主線是把任何來源的回報整理成 issue，再交給 /triage 分流。

/triage：七個角色的狀態機

每張 issue 帶一個類別＋一個狀態：

類別（2）bug ／ enhancement
狀態（5）needs-triage → needs-info（等回報者補件，回覆後回到 needs-triage）／ ready-for-agent ／ ready-for-human ／ wontfix

分流一張 issue 的流程：讀全文與先前 triage 筆記 → 給你建議＋理由（等你裁決）→ bug 先嘗試重現（重現成功的 agent brief 強得多；重現失敗 = 強烈的 needs-info 訊號）→ 不夠清楚就接 /grill-with-docs → 套用結果。三個制度細節：

  • 它發的每則內容都標 「This was generated by AI during triage」 — 透明度。
  • ready-for-agent 會附 agent brief（讓 AFK agent 能冷啟動的完整說明）；ready-for-human 同格式但註明為何不能委派（判斷、外部存取、設計決策）。
  • wontfix 的 enhancement 寫進 .out-of-scope/ 知識庫 — 未來類似提案進來，它會比對並引用先前的拒絕理由。和 Phase 3 第 11 課「拒絕也是知識」同一個哲學。

實作步驟（做完打勾）

把你腦中積壓的 2–3 個真實問題寫成 issue：使用者視角、預期 vs 實際、重現線索、影響範圍。若用 /qa 輔助建檔，也要檢查它是否偷寫檔名或行號。

/triage 看看有什麼需要我處理的

它會列三個桶（未標記／needs-triage／needs-info 有新回覆）。剛建的 issues 應該在裡面。

逐張走：聽它的建議與理由 → 你裁決。bug 類盯它的重現嘗試：重現結果有沒有如實回報？至少把一張推到 ready-for-agent 並讀它寫的 agent brief — 用「冷啟動的陌生人看得懂嗎」檢驗。

挑一個你明知不會做的 enhancement 走 wontfix，確認拒絕理由進了 .out-of-scope/。

把那張 ready-for-agent 的 issue 接到後續流程（bug → /diagnosing-bugs；功能 → /implement）。從抱怨到修復，全程都在制度裡。

🎉 外部回報已能進入制度。回對話視窗回報：哪張 issue 進了 ready-for-agent？它該接 diagnosing 還是 implement？

觀念檢查（憑記憶作答）

1. 缺陷 issue 為什麼不該綁死檔名與行號？

durable 是核心設計：行為描述（用領域語言）在大重構後依然正確，檔名行號則很快過期。背景探索學的是語言，不是定位。

2. 一張 bug 重現失敗、回報者描述也含糊，最可能的正確狀態是？

skill 原文：重現失敗或細節不足 = 強烈的 needs-info 訊號。回報者補件後回到 needs-triage 再評。直接 wontfix 或丟給人都是浪費。

3.（複習 Phase 3 第 11 課）.out-of-scope/ 知識庫與哪個既有制度是同一個哲學？

（間隔複習）兩者都是「拒絕也是知識」：把 No 的理由存檔，未來的 agent（或人）就不會重新提案、重新爭論同一件事。
