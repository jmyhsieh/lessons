設計 rerun policy

目標：替第 33 課的 run history 補上重跑規則。這一課只定義什麼狀態可以 rerun、如何保留舊 evidence、何時必須人工介入；不做自動排程、不做 repair loop。

Rerun 不是覆蓋舊結果

Claude Code checkpointing 可以回復 Claude 直接編輯的檔案與對話，但官方也明說 Bash command 造成的檔案變更、外部變更不在 checkpoint 追蹤範圍內，而且 checkpoint 不是 Git 的替代品。Harness rerun 不能假設「重跑一次就等於回到乾淨狀態」。

Cost tracking 也提醒失敗 conversation 仍可能消耗 token 與成本。因此 rerun policy 要能回答：誰允許重跑、為什麼重跑、上一輪 evidence 怎麼保留、這一輪是不是新 run。

先定義狀態能不能重跑

上一輪狀態預設動作原因
passed不自動重跑。除非 input 或 gate 版本改變，否則重跑只會製造噪音。
needs-review先人工判斷。需要 review 的不是 runner 壞掉，而是缺人類決策。
failed修正後可重跑。必須先改 input、prompt、code 或 gate，並記錄 reason。
blocked解除阻塞後可重跑。credential、權限、環境未解決前，重跑只會重複失敗。
stale先 verify artifacts。證據缺失時，不能把缺證據當作任務失敗。
判斷規則：每次 rerun 都是新 runId，用 parentRunId 指回上一輪；舊 evidence 永遠不覆蓋。

Rerun record 範例

{
  "runId": "run-0043",
  "parentRunId": "run-0042",
  "inputId": "issue-0042-login-timeout",
  "rerunReason": "gate failed after auth test timeout",
  "changedSinceParent": ["gate timeout 120s -> 240s"],
  "preRunState": {
    "gitRef": "abc1234",
    "dirty": false,
    "inputHash": "sha256:..."
  },
  "artifactPolicy": "preserve-parent-evidence",
  "status": "running"
}

實作步驟（做完打勾）

先在 Rerun policy 速查表 填上 passed、needs-review、failed、blocked、stale。

重跑時新增 runId，保留 parentRunId、上一輪 status、rerun reason、觸發者。不要覆寫 runs.jsonl 的舊行。

至少記錄 gitRef、dirty 狀態、input hash。若有 Bash 或外部 side effect，標成需要人工確認。

同一個 parent 最多自動重跑一次。第二次失敗後改成 needs-review，避免 agent loop 消耗成本又沒有新資訊。

Report 補一段 rerun note：上一輪為何不能收工、本輪改了什麼、保留哪些舊 evidence、還有哪些 side effect 未確認。

你已完成 rerun policy 切片。回對話視窗貼上 status table 與一筆 rerun record，請 AI 老師檢查哪些情況還不該自動重跑。

觀念檢查（憑記憶作答）

1. Rerun 時最不能做什麼？

舊 evidence 是審查材料，不能覆蓋。每次 rerun 都要是新 run，並用 parentRunId 串回上一輪。

2. 哪種狀態不該直接自動重跑？

needs-review 缺的是人類判斷，不是 runner 重跑。自動重跑會把決策問題偽裝成執行問題。

3. Checkpoint 不能取代什麼？

官方文件明確把 checkpoint 定位為 session-level recovery，長期歷史與協作仍要靠 Git 等版本控制。
