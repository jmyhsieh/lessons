Phase 3 · 第 07 課 · 約 35 分鐘 · 工作切片

用 /to-issues 切成可認領工作

目標：把第 06 課的 PRD 拆成一組可以獨立認領、獨立驗收的 issues。這一課練的是「切片品質」，不是把大計畫切成一堆技術層待辦。

本課只做：把 PRD 切成可認領 issues。
先不要做：用資料層、API 層、UI 層做水平切片。

Pipeline 全景：你在這裡

/to-prd → /to-issues → /implement

垂直切片，不是水平分工

/to-issues 的核心是 tracer bullet：每張 issue 都是一條窄但完整的端到端路徑。它可以很小，但必須自己能 demo、能測、能判斷完成。

好的 issue不好的 issue
新增「查詢一筆訂單」：schema、API、畫面、測試最小通路。先建完所有資料表，之後再補 API 與畫面。
一張 issue 有明確驗收條件與 blocked-by。一張 issue 只寫「完成後端」或「整理前端」。
標明 AFK 或 HITL，知道能不能交給 agent。沒有判斷邊界，agent 接手後才發現缺決策。
你要把關的問題：這片能不能獨立驗收？如果不能，就要求它再切。這比 issue 數量漂亮更重要。

AFK / HITL 怎麼判斷

標記意思例子
AFKagent 可以照 brief 完成，過程不需要人類決策。明確修一個驗收條件、補一條端到端路徑。
HITL需要人類判斷、外部權限、設計取捨或手動驗證。確認 UX 文案、開權限、選架構方向。

實作步驟（做完打勾）

確認 PRD 有 user stories、scope、驗收條件與測試接縫。沒有這些，先回第 06 課補 PRD。

/to-issues [PRD 路徑或 issue 連結]

讓它先列出 issue 草案，不要直接發布。

每片都問一次：能不能獨立 demo？能不能獨立測？是否只依賴少數明確前置？

AFK 太多可能低估人類決策；HITL 太多可能 brief 不夠清楚。要求它修正標記與原因。

核准後發佈 issues。挑第一張 AFK 且 blocked-by 最少的 issue，下一課用 /implement 完成。

🎉 PRD 已變成可認領工作。回對話視窗回報：你挑哪一張 issue 當第一張 implement？

觀念檢查（憑記憶作答）

1. 哪個比較像垂直切片？

垂直切片要窄但完整，能自己 demo、自己驗收。只做一層是水平切片。

2. issue 標 HITL 最常代表什麼？

HITL 代表需要人類判斷、外部權限或手動驗證；不是 agent 能力不足的同義詞。
