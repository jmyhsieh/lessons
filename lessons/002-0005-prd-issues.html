把計畫整理成 PRD 與 issues（/to-prd、/to-issues）

目標：把第 16 課 grill 出來的對齊計劃，先凝結成 PRD、再切成垂直切片（tracer bullet）的本地 issues。完成後，Phase 2 的 pipeline 只剩最後一步（/tdd 實作）。

Pipeline 全景：你在這裡

grill（對齊）→ /to-prd（凝結）→ /to-issues（切片） → /tdd（實作）
   第15課            本課                          下一課

/to-prd：凝結，不是再訪談

關鍵設計（skill 原文）：「不要再訪談使用者 — 直接綜合你已經知道的」。grill 已經把該問的問完了，to-prd 是收割。它會：

  • 用 CONTEXT.md 的詞彙寫整份 PRD、尊重相關 ADR
  • 產出：問題陳述、解法、大量編號的 user stories、實作決策
  • 發佈到第 14 課選定的 issue tracker（GitHub / Linear / local files）並標 ready-for-agent
它唯一會停下來問你的：測試的「接縫」（seams） — 要在哪些介面層驗證這個功能。原則：優先用既有接縫、用越高層的越好。高風險或 legacy repo 特別需要這一步，因為高層接縫（API 邊界、模組介面）通常比深挖內部更安全。看不懂它提的接縫就追問，別放行。

/to-issues：垂直切片，不是水平分層

核心觀念 — tracer bullet（曳光彈）：每張 issue 是一條「窄但完整」的端到端路徑，貫穿所有層（schema、API、UI、測試），不是「先做完整個資料層」這種水平切法。規則（skill 原文）：

  • 每片自己就能 demo 或驗證
  • 寧可多片薄的，不要少片厚的
  • 每片標 AFK（agent 可獨立完成）或 HITL（需要人參與決策/審查），能 AFK 就 AFK

它切完會先列清單問你：粒度對嗎？依賴關係對嗎？該合併或再切嗎？AFK/HITL 標對了嗎？— 你核准後才發佈 issues（含驗收條件與 blocked-by 鏈）。

實作步驟（做完打勾）

最理想：在第 16 課那個 session 繼續（context 都在）。若已關閉，開新 session 請它先讀 grill 產出的計劃與 CONTEXT.md。

重點審兩處：(a) 它提的測試接縫合理嗎？(b) user stories 有沒有漏掉你在 grill 中講過的場景？確認 PRD 寫進第 14 課選定的 tracker。

對著剛產出的 PRD 執行。在它的「quiz」階段認真把關：用垂直切片的標準逐片檢查 — 「這片自己能驗證嗎？」不能就要求重切。

打開 issues 逐張讀：標題用了 CONTEXT.md 的詞彙嗎？驗收條件具體可驗嗎？blocked-by 鏈正確嗎？挑出最該先做的一張 — 下一課就實作它。

PRD、issues、CONTEXT.md/ADR 的更新一起進版控或對應 tracker — 這些文件就是 repo 的交付制度。

🎉 pipeline 三分之二完成：對齊 → PRD → issues。回對話視窗回報：切了幾片？AFK 佔比多少？哪片你要求重切了？

觀念檢查（憑記憶作答）

1. 哪個是正確的「垂直切片」？

tracer bullet = 窄但貫穿所有層、自己能 demo。「先做完一層」是水平切片 — 每片都無法獨立驗證，正是 to-issues 要避免的。

2. /to-prd 開始重新問你一堆需求問題，這代表？

to-prd 的設計是「不訪談、只綜合」。若它沒料可綜合而開始發問，訊號是 grill 沒做透 — 回去補 grill，而不是在 to-prd 裡將就。

3.（複習第 16 課）PRD 全文該使用什麼語言？

（間隔複習）共享語言是整套制度的地基：grill 銳化術語 → CONTEXT.md 收錄 → PRD/issues 沿用 → 人和 AI 讀到的是同一個意思。
