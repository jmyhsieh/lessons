Phase 1 · 第 05 課 · 約 25 分鐘 · 實作課（桌面 App 優先）

第一次讓它改程式碼 — 分支、小改動、review

任務目標：在工作 repo 裡，讓 Claude Code 完成一個低風險的真實修改，全程走「先開分支 → 逐項批准 → 親自 review diff → commit」的安全流程。做完這課，你就具備在正式專案日常使用的基本功。

本課只做：在分支上做一個小改動，並看懂 diff。
先不要做：把第一個任務選成跨模組重構或高風險修復。
開始前檢查：本課需要 Git 可用，因為會建立分支與 commit。若還沒確認，先在終端機跑 git --version；看不到版本號就回第 02 課完成 Git 先備檢查。
正式專案三道護欄（這課的核心）：
  1. 分支隔離 — 永遠先開分支，main 不直接動。
  2. 審核有風險的動作 — 保持 Desktop Manual 或 CLI default；讀檔與內建唯讀指令通常直接執行，編輯與其他指令出現提示時逐項看懂再同意。
  3. 人工 review — AI 寫的 code 和同事寫的一樣：必看 diff 才合併。你批准它「執行」，不代表你已經「審核」過內容。

挑一個合適的第一個任務

好的第一個任務：小、可驗證、出錯也無傷。例如：

  • 修一個你已知的小 bug（有明確重現方式）
  • 幫某個沒測試的小函式補單元測試
  • 更新一段過時的 README / 註解

避免：跨多模組的重構、碰部署設定、資料庫 migration — 那是熟練之後的事。

實作步驟（做完打勾）

在 Code 分頁的 session 裡直接用自然語言（官方 Quickstart 示範的 git 對話式操作）：

create a new branch called claude/第一個任務名稱

批准它執行 git 指令前，看一眼指令內容 — 養成習慣。

具體描述（含檔案位置、預期行為），並要求它先說做法：

「[描述你的任務]。先告訴我你的修改計劃和會動到哪些檔案，
我確認後再動手。」

計劃合理再放行。不合理就追問或修正 — 你是 reviewer，不是旁觀者。

它每次要改檔案都會跳出請求。每個 diff 都讀過再按同意（桌面 App 的視覺化 diff 就是為這個設計的）。看到不對的，拒絕並說明原因。

Run the relevant verification. Show me the exact command,
exit status, and output. If it fails, fix it and rerun.

沒有測試的話，先寫清楚手動驗收步驟並親自驗一次。只說「完成了」或「測試通過」不算 evidence。

show me the full diff of all changes

桌面 App：點 diff stats / diff pane 看互動 diff。若 / 清單有 /diff，也可當快捷。從頭到尾讀一遍 — 這是第三道護欄。滿意後：

commit my changes with a descriptive message

之後要不要推上去開 PR，照你們團隊的正常流程走（PR review 仍然必要）。

🎉 完成！你已經走過一輪正式專案的安全工作流。回到對話視窗回報：它的計劃和 diff 品質如何？有沒有你拒絕過的修改？

觀念檢查（憑記憶作答）

1. 你按下「同意修改」，代表什麼？

批准 ≠ 審核。批准只是放行動作；diff 內容的正確性永遠由你把關（護欄三）。

2. 正式 repo 的基準：該停在哪個權限模式？

（間隔複習）Manual/default 是正式專案的基準。工作目錄內讀檔與內建唯讀指令通常不詢問；編輯與其他 shell 指令會停下確認。
