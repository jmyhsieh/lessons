Phase 3 · 第 03 課 · 約 15 分鐘 · 輕量實作

不熟 repo 時，先建立地圖

目標：學會在陌生 repo 的需求、實作或 review 前，用自然語言 prompt 取得模組、入口點、呼叫關係與風險區域的高層地圖。Bug 是例外：先進 /diagnosing-bugs，只在第 1 階段用窄地圖協助建立回饋迴圈，不先猜原因。

本課只做：在不熟 repo 時先取得人能讀懂的地圖。
先不要做：用地圖整理代替真正的 debugging 或 implementation。

核心 prompt

I don't know this area of code well. Go up a layer of abstraction.
Give me a map of all the relevant modules and callers,
using the project's existing domain vocabulary.
If CONTEXT.md does not exist, reuse terms from product docs and code;
do not invent new domain terms.
現行狀態：/zoom-out 曾是本機 skill 捷徑；若你的 skills 清單還有它，可以直接用。若沒有，就用上面的自然語言 prompt 達成同一件事。本課教的是穩定工作法，不是要求背一個 upstream 已移除的指令。

拆解這三句話，每一句都有設計：

原文為什麼這樣寫
「我不熟這區的 code」誠實宣告狀態 — 讓它別假設你懂，回答從基礎講起
「上升一個抽象層」對抗 AI 的預設行為：直接鑽進檔案細節。你要的是俯瞰不是放大鏡
「模組與呼叫者的地圖，用領域詞彙」已有 CONTEXT.md 就錨定其中的語言；尚未建立時沿用產品文件與 code 的既有詞彙，不自行發明。地圖才讀得懂、才耐久
為什麼要手動觸發：「我不熟悉這個區域」只有你自己知道；Claude 無法替你判斷熟悉程度。這也是為什麼本課把重點放在你何時要求地圖。

它在你工具鏈裡的位置

repo 地圖是其他 skill 的前置動作 — 在你要進入陌生區域之前先做：

情境組合
要 grill 一個碰到陌生模組的需求先建立地圖 → 看懂地形 → /grill-with-docs
bug 在你沒碰過的子系統進 /diagnosing-bugs 建回饋迴圈；需要時用窄地圖找 call path／測試 seam，但不先猜原因
review AI 寫的陌生區域改動先建立地圖 → 再讀 diff（你才有判斷基準）
新人 onboarding（包括未來的你）對每個主要模組各跑一次，產出可以存檔的地圖

和 Phase 2 第 05 課的 Explore subagent 分工：Explore 是 Claude 自己派 subagent 去查細節（結果給它用）；repo 地圖是你要一張給人看的高層地圖。

何時升高 effort

多數地圖整理先用目前模型的預設 effort。結果不完整時，先分辨它是沒讀夠，還是讀完仍判斷錯：漏讀 entry point、call path 或 tests 才提高 effort；已充分探索仍誤判 domain boundary，才換能力更高的模型。

情境建議理由
只想知道某資料夾在做什麼。目前模型 + 預設 effort先用官方建議的基準，不必每題手動升級。
地圖漏掉 caller、tests 或驗證路徑。同模型 + 較高 effort方向正確，但探索與查核不夠徹底。
已讀完整，仍把檔案依賴誤認成 domain boundary。opus + 預設 effort這是能力與抽象判斷問題，不只是工作量。
準備用地圖決定不可逆重構方向。opusplan 或 Opus plan mode先用較強模型規劃，再回到有效率的執行節奏。
不要用 max 跑一般地圖整理。若預設 effort 一直漏讀，先縮小 scope 或補明確驗收條件；若它已完整嘗試仍判斷錯，再升模型。

實作步驟（做完打勾）

真實 repo 裡那個你最不熟悉的模組或子系統 — 越不熟悉的越適合。

在該區域的脈絡下執行（先 cd 到相關目錄或在對話中指明區域）：

I don't know this area of code well. Go up a layer of abstraction.
Give me a map of all the relevant modules, entry points, callers, data flow,
tests, and risky areas. Use the project's existing domain vocabulary.
If CONTEXT.md does not exist, reuse terms from product docs and code;
do not invent new domain terms.

如果你的本機 skills 清單還有 /zoom-out，可以把它當快捷；沒有也不影響本課。

三個檢查：(a) 它講的是模組與呼叫關係，還是鑽進了檔案細節？(b) 有 CONTEXT.md 時是否遵守其中詞彙；沒有時是否沿用 repo 既有產品語言而未自行發明？(c) 看完你能向同事複述這區的結構嗎？不合格就追問「再上升一層」。

發現 CONTEXT.md 尚未建立或可能缺術語 → 先和能代表 domain 的人確認定義；確認後才按需建立或補進 CONTEXT.md。地圖本身若值得保存，存成 docs 下的一頁（標注日期 — 地圖會過期）。

拿著地圖立刻做一件原本不敢做的事：grill 一個碰這區的需求；若用在 bug，讓地圖協助 /diagnosing-bugs 找到 red-capable command 的 call path 或測試 seam，不要在回饋迴圈建立前先形成原因假說。

🎉 你最不熟悉的區域，現在有地圖了。回對話視窗回報：地圖第一版合格嗎？你追問了幾次「再上升一層」？

觀念檢查（憑記憶作答）

1. 為什麼 repo 地圖要用領域詞彙輸出？

共享的領域語言是人和 AI 的共同地圖座標；已有 CONTEXT.md 就遵守它，沒有時先沿用 repo 既有產品語言。只用檔名描述的地圖會在重構後作廢。

2. 這種地圖工作為什麼應由你手動要求？

這個觸發條件是你的主觀狀態 — Claude 無從判斷你對這個區域的熟悉程度。你知道自己不熟時，就先要求地圖。
