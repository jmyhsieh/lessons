把已對齊的 request 凝結成 delivery spec

任務：把 repo evidence、confirmed decisions 與 prototype answer（若有）寫成可引用的 spec；這一步不重新訪談，也不開始 implementation。

Spec location / revision:
  1. 執行 /to-spec，綜合現有 session；若大量新問題出現，回 alignment，不在 spec 偷補假設。
  2. 逐條把 user story 連到 observable behavior 與 test seam。
  3. 核對 CONTEXT、ADR、instructions 與 repo map；衝突要顯示，不發明 hybrid convention。
  4. 請使用者核准 scope 與 acceptance evidence，再固定 spec revision。
Tangible win：一份有 revision identity、可切片的 delivery spec。
Observable feedback：Reviewer 能由每條 story 找到 acceptance evidence、非目標與 repo constraint，且沒有未核准 scope。

/to-spec 開始大量追問新需求，怎麼辦？

Spec 是凝結已確認內容，不是用來掩蓋 alignment 缺口。

Legal stop／continuation：scope 未核准、stories 無 evidence、test seam 不可信或 spec revision 不固定時停止。Spec 可引用且已核准後，續到 006-0006；本 slice 到 ticket plan 為止，不提前進 implementation。
