/review — Standards × Spec 兩軸審查

目標：在 tdd 實作完成之後、合併之前，用 /review 對 diff 跑「規範符合度 × 規格符合度」兩軸的平行審查。這是 pipeline 的最後一道品質關卡，也把第 11 課 subagent、第 12 課 Writer/Reviewer 收進實戰。

它解決什麼：兩個不同的「對不對」

一份 diff 有兩種獨立的「對」，混在一起審就會互相干擾。review 把它們拆成兩個平行 subagent（SKILL.md）：

軸問的問題依據
Standards
規範符合度		這段 code 有沒有違反本 repo 記載的寫作規範？CLAUDE.md、CONTEXT.md、ADR、CONTRIBUTING、STYLE.md…
Spec
規格符合度		這段 code 有沒有忠實實作原始 issue/PRD？commit 裡的 issue 引用、PRD、spec 檔
為什麼要平行、不合併？兩軸跑在各自的 subagent（fresh context，第 11 課），彼此不污染；最後並列呈現、不重排也不合併。「這段不符規範」和「這段沒做到需求」是兩種問題，混在一起你會分不清該怎麼修。

它怎麼運作（五步，skill 原文）

  1. 釘住比較基準 — 你給的固定點（commit/branch/tag/main）。沒給它會問「review against what？」用三點 diff git diff <point>...HEAD（對 merge-base 比較）。
  2. 找 spec 來源 — 依序：commit 訊息裡的 issue 引用 → 你傳的路徑 → docs/specs 下符合分支名的 PRD → 都沒有就問你；你說沒有，Spec 軸就跳過並回報「no spec available」。
  3. 找 standards 來源 — 蒐集 repo 裡所有「規定 code 該怎麼寫」的文件（含 ADR — 架構決策也是規範）。機器已強制的（eslint/prettier/tsconfig）記下但不重複檢查工具已檢查的。
  4. 平行派兩個 subagent — 一則訊息兩個 Agent 呼叫。各自讀文件＋讀 diff，回報違規/缺口，引用依據，各 400 字內。
  5. 彙整 — 並列在 ## Standards 與 ## Spec 兩標題下，末尾一行總結：每軸幾個發現、最嚴重的一個。
對任何有 repo 規範的專案都適用：standards 來源正好就是你前面課程建立的制度 — CONTEXT.md（第 14 課）、ADR、CLAUDE.md。review 等於讓那些文件「活過來」自動把關每一次改動。文件不再只是擺著，而是審查的依據。

它和你已學的審查工具的關係

工具角色
第 11 課 subagent review通用的「fresh context 審 diff」— review 是它的結構化專版（固定兩軸）
第 12 課 Writer/Reviewer 雙 session同一個哲學的人工版；review 把它自動化成一個指令
內建 /code-review找 correctness bug；/review 找的是規範與規格的符合度 — 互補不重疊

實作步驟（做完打勾）

最理想：第 19 課 tdd 做完的那條分支（它有對應的 issue＝spec）。沒有的話挑任何一條近期分支。

/review main

（或你的目標分支/commit）。觀察它怎麼找 spec 與 standards 來源 — 它找到的 standards 文件，正是你前面建立的 CONTEXT.md/ADR 嗎？

Standards 的發現＝改 code 對齊規範；Spec 的發現＝補做漏掉的需求或砍掉 scope creep。不要把兩堆混著修，照軸別逐項處理。

特別看 Spec 軸有沒有抓到「做了沒被要求的東西」— 這在 AI 寫的 code 很常見，高風險 repo 尤其需要管住 scope creep。

處理完發現 → 重跑 review 確認清掉 → 合併。若某個「違規」其實是規範本身過時 → 回頭更新 ADR/CONTEXT.md（文件也要進化）。

🎉 你的文件制度現在會自動審查每一次改動了。回對話視窗回報：兩軸各抓到什麼？standards 軸引用到你哪幾份文件？

觀念檢查（憑記憶作答）

1. review 為什麼把 Standards 與 Spec 跑成兩個平行 subagent？

（接第 11 課）各自 fresh context 不互相干擾；「不符規範」與「沒做到需求」是兩種問題，刻意分開呈現、不合併不重排。

2. review 找 standards 來源時，遇到 eslint/prettier 設定檔該怎麼處理？

skill 原文：machine-enforced standards — note them but don't re-check what tooling already checks。讓 AI 重查 linter 能查的事是浪費；它的價值在文件裡的「人類規範」。

3.（複習第 14 課）你的 CONTEXT.md 與 ADR 在 review 裡扮演什麼？

（間隔複習）ADR=架構決策=standards；CONTEXT.md 的語言也是規範。前面課程建立的文件制度，在這裡變成自動審查的依據 —「文件活過來」。
