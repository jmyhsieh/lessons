先造出會紅的 feedback loop，再診斷難解 bug

進入條件／條件分支：適用於已確認的難解、間歇、回歸 bug 或效能退化；你已掌握 exact symptom、可用的安全 workspace、repo instructions 與可執行 checks。一般範圍清楚的 bug 不必強制走本 branch。

1. 先交出一個 red-capable command

優先順序可從 failing test、HTTP／CLI fixture、headless browser、captured trace、throwaway harness、fuzz／bisection／differential loop 到結構化 HITL。這個 command 必須走過真實 bug path、斷言使用者回報的 exact symptom，且已至少跑過一次；「沒有 crash」不是足夠訊號。

循環品質閘門：red-capable、deterministic（flaky bug 則固定高重現率）、快速且 agent-runnable，四項缺一就繼續縮緊 loop，不進入原因假說。

2. 重現、最小化，再比較假說

  1. 重跑 original scenario，確認紅的是同一個 symptom。
  2. 一次移除一個 input、caller、config 或 step；留下的每一項都必須 load-bearing。
  3. 列出 3–5 個 ranked、falsifiable hypotheses，每個都寫「若 X 是原因，改變 Y 應觀察到 Z」。
  4. 讓 learner／domain owner 看排序，再一次只改一個變因，以 debugger 或 targeted [DEBUG-…] probe 收集 evidence。

3. 先鎖 regression，再修正與清理

只有能重現真實觸發模式的 seam 才寫 regression test：先看它紅，再做最小 fix、看它綠，最後重跑 original feedback loop。若沒有正確 seam，誠實記錄；不要用過淺的 test 製造假信心。

Diagnosis 不是 architecture implementation：先把 bug 修好並保存 regression evidence，再問「什麼會預防它」。若答案是缺乏 test seam、callers 糾纏或 hidden coupling，只記成 006-0012 架構後續作業 input；不要在同一 diagnosis diff 偷跑廣泛重構。

具體成果：一份 hard-bug diagnosis packet，包含已執行的 red-capable command、最小 repro、假說 evidence、regression RED／GREEN、original-loop rerun 與 cleanup。
可觀察回饋：Reviewer 能用一個 command 先捕捉 exact symptom，再核對修正後同一 signal 轉綠；原因結論可追到 falsifiable probes，而不是敘事猜測。

目前只能寫一個單一 caller 的 shallow unit test，但原 bug 需要多個 callers 的 chain 才會發生；應怎麼做？

錯誤 seam 會製造假信心。先以 original loop 保護 diagnosis 與最小 fix，再把缺少 test seam 當作獨立架構 evidence。

合法停止／返回／續行：無法建立 red-capable command、缺少能重現的環境／artifact／權限、紅的是不同 symptom、loop 仍不穩定、fix 後 original loop 未綠、debug artifacts 未清，或 regression／architecture 邊界不清時，保存所有嘗試後停止並向 owner 要 access、HAR／logs／trace 或 instrumentation authority。Evidence 對齊後，把 diagnosis packet 回送 006-0003，對齊最小交付或 separate architecture request。完成本頁只代表這個 bug 已形成可重現 diagnosis evidence，不代表 Engineering Phase 或 Migration complete。
