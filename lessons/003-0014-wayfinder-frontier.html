Phase 3 選修 · 第 14 課 · 約 45 分鐘 · Wayfinder

沿 frontier 解一張 decision ticket

目標：從 shared map 找到一張未被阻擋、未被認領的普通 frontier ticket，在一個乾淨 session 內解完、留下答案、更新 map，然後停止。

本課的一般 loop：認領並解完一張 decision ticket；已啟動的 research subagents 是平行例外。
先不要做：一次載入全部 tickets，或把 ticket session 變成 destination 的施工 session。

Frontier 是現在可前進的邊緣

一張 ticket 同時滿足三個條件，才在 frontier：

  • 仍然 open。
  • 所有 blocking tickets 都已關閉。
  • 尚未被另一個 session 認領。
認領就是並行鎖：開始工作前，先把 ticket assign 給自己。其他 session 查 frontier 時就會跳過它；不要只在聊天裡說「我來做」。
Research 是明確例外：普通 frontier ticket 仍是一個乾淨 session 只解一張；charting 時建立並 wire 好的 research tickets，則已平行交給各自的 /research subagent。每個研究結果留在 throwaway research/<name> branch，ticket 保留 context pointer，不必排隊等前一個一般 ticket session 結束。

只載入需要的解析度

新 session 先讀 map 的低解析全貌，再打開選中的 ticket。不要一次展開所有 child tickets；需要某個舊決策時，才按連結 zoom in。

shared map（低解析）
  ↓ 找第一張 open + unblocked + unclaimed
claim ticket
  ↓
只讀本票與必要 linked decisions
  ↓
resolve → comment → close → 更新 map

人類看到的文字一律用 ticket title，連結包住名稱；不要讓 #42 #43 #44 這種裸 ids 取代可讀的決策名稱。

Type怎麼解完成證據

Resolution 要更新兩個層次

位置記什麼
Ticket resolution comment完整答案、證據與 linked assets；然後 close ticket。
Map 的 Decisions so farticket 名稱與連結，加一句足以判斷相關性的 gist；不要複製完整答案。

答案可能讓 fog 變得可精確提問：把那一塊從 Not yet specified 移除，建立新 tickets，再 wire blocking edges。若答案證明某件事超出 destination，移到 Out of scope，不要把它偽裝成下一步。

/wayfinder [map URL 或編號]

確認它 open、unblocked、unclaimed，再 assign 給自己。若已被別人 claim，回 frontier 選下一張。

普通 frontier ticket 在本 session 內完成；research 則由平行 subagent 在 research/<name> branch 留下 citations，並把 context pointer 留回 ticket。Prototype 要有人類反應；grilling 要真人回答；task 要留下可驗證 facts。

建立現在才看得清楚的新 tickets、wire edges、移除已升級的 fog。即使下一張普通 frontier ticket 已出現，也留給下一個 session；已啟動的 research subagents 可以平行繼續。

何時離開 wayfinder

當沒有 open tickets、沒有可升級的 fog，而且通往 destination 的路已清楚，map 就完成。預設不是直接施工，而是把 linked decisions 收斂回一般主線：

completed map → /to-spec → /to-tickets → fresh /implement sessions

只有當探索結果證明整件事其實縮成單一小任務，才在保留必要 decision links 的前提下直接 /implement。

觀念檢查（憑記憶作答）

1. 沒有指定 ticket 時，應優先選哪一張？

Frontier ticket 已解除 blockers 且尚未被認領；blocked 或 claimed ticket 都不該搶做。

2. 開始解 ticket 前，第一個寫入動作是？

Assignee 是多 session 的 claim mechanism。先 claim，其他 session 才知道要跳過這張票。

3. Ticket 解完後，哪個收尾順序正確？

完整答案屬於 ticket resolution；map 只加 linked gist。Ticket 要關閉，frontier 才會正確前進。

4. Map 已經清楚完整，預設接到哪裡？

Wayfinder 的 linked decisions 要先由 /to-spec 收斂成 buildable plan；直接 implement 容易丟掉分散在 tickets 裡的細節。

5. 哪種情況是「一個 session 只解一張 ticket」的例外？

普通 frontier ticket 仍一次只解一張；research tickets 在建立並 wire 後，就由各自的 /research subagent 平行處理，結果留在 throwaway branch，ticket 留 context pointer。
