Phase 3 · 第 02 課 · 約 25 分鐘 · Issue / brief

把任務寫到 agent 可以直接接手

目標：把 Phase 3 第 01 課判定「值得 harness 化」的任務，先寫成 agent 可接手的 issue 或 brief。核心產物是一份穩定 input contract：任務來源、範圍、驗收與停止條件都講清楚。

本課只做：產出一份 agent 可接手的 issue / brief。
先不要做：在 input 不穩時先做 gates 或 runner。

為什麼 issue / brief 要先 harness-ready

Claude Code best practices 強調兩件事：給 Claude 可執行的驗證方式，並在 prompt 裡提供具體脈絡。這正是 harness-ready issue / brief 的用途：讓每次啟動都拿到同樣清楚的任務，而不是靠你在對話裡臨場補洞。

模糊需求 → harness-ready issue / brief → runner prompt → gate → evidence

如果 input 不穩，後面即使加上 claude -p、Agent SDK 或 CI，也只是把模糊需求自動化。

一份 issue / brief 要有六格

欄位寫在 issue 或 brief 裡的內容例子
ID這次任務可追蹤的名稱。issue-0042-login-timeout
Source任務正本在哪裡，不要把全文複製到每個地方。issues/0042.md
Outcome完成後使用者或團隊能觀察到什麼。逾時後重新登入不會卡在空白頁。
Scope允許碰哪些路徑、系統或資料。src/auth/**、tests/auth/**
Gates哪些檢查失敗就不能收工。npm test -- auth、人工 review
Stop遇到哪些缺口必須停下來問人。需要 production secret、要改 migration、需求互相衝突。
判斷規則：一個陌生 agent 只看這份 issue / brief，就應該能開始探索、知道不能碰哪裡、知道怎麼驗收、知道何時必須停下來問你。

實作步驟（做完打勾）

只挑一個。最好是重複、可驗收、常讓你重講背景的任務，例如「每週整理 bug issue」或「修登入回歸」。

打開 Harness-ready issue / brief 速查表，把 ID、Source、Outcome、Scope、Gates、Stop 填完。

圈出「改善、整理、處理、看一下、幫我」這類詞。每個都要改成可觀察結果、允許範圍或明確停止條件。

如果 Source 與 Gates 都穩，可以進下一課設計 runner。若 Scope 或 Stop 還很模糊，先維持半手動 checklist。

請讀取 [Source]，只在 [Scope] 內工作。
目標是 [Outcome]。
完成前必須通過 [Gates]。
若遇到 [Stop]，停止並回報問題，不要自行假設。
你已完成第一份 harness-ready brief。回對話視窗貼上六格內容，請 AI 老師檢查哪一格還不夠穩。

觀念檢查（憑記憶作答）

1. 這一課的主要產物是什麼？

Phase 3 第 02 課只把 issue / brief 的任務來源、範圍、驗收與停止條件寫穩，還不是 runner 或測試報告。

2. contract 裡遇到 production secret 才能繼續，應該怎麼做？

Production secret 屬於 Stop 條件。Agent 應停止並回報缺口，不應自行假設或繞過權限。

3. 為什麼不要太早把流程接進 CI 或 SDK？

如果 issue / brief 的 input contract 不穩，自動化只會放大模糊需求；先穩住 Source、Scope、Gates、Stop。

下一步

先把一個真實任務寫成 harness-ready issue / brief。若六格都穩，接著進入 Phase 3 第 03 課：把驗收條件轉成 gates，並定義每個 gate 要留下哪些 evidence。
