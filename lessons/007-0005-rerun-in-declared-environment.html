Phase 7 · 驗證 · 007-0005 · Failure sensitivity and rerun

先讓 controlled fault 擊中 assertion，再修正後重跑

進入條件：007-0004 已固定一個 test file、test name、user action 與 decisive assertion；你也有合法可控制的 faulty fixture／recoverable app state。本課在同一 declared environment 執行兩次：故障行為必須讓 assertion RED，修正後同一 test identity 才能 GREEN。不能用改 expected、skip、重錄 snapshot 或 retries 把 RED 消掉。

操作方式校準：2026-07-17 以 @playwright/test@1.61.1、retries: 0、Node 24.16.0、macOS 26.5.2 arm64 與 system Google Chrome 校準：faulty fixture 顯示「仍在處理」時，exact heading「訂單完成」assertion 以 element(s) not found 失敗；只修正 fixture behavior 後，同名 test 與相同 assertion 通過。這是 recipe 證據，不是你專案的 run result。

同一對象檢查：RED 與 GREEN 除了已宣告的 faulty→corrected behavior／revision外，test name、action、assertion、browser project、viewport、role、seed 與 relevant configuration 必須相同。若 run 中偷換 fixture、login 或 expected outcome，兩次結果不可組成同一份 durability evidence。

2. 先跑 controlled RED

  1. 用 repo 的 exact command 限定同一個 test；暫時關閉 retries，避免故障敏感度被重試分類掩蓋。
  2. 以可恢復方式啟用已知 faulty fixture／behavior；不要改 test expected，也不要碰 production data。
  3. 執行 test，要求 non-zero exit 與 failure message 指向 claim 的 observable outcome，而不是 server 未啟動、syntax error、browser 缺失或 permission error。
  4. 記錄 command、exit status、test identity、actual observation 與 artifact identity；結束後恢復或修正同一 fixture。
# 使用 repo 自己的 test command；下列只是形狀
FAULTY_FIXTURE=1 npx playwright test tests/browser/checkout.spec.ts \
  --grep "guest can complete checkout" --retries=0

Expected RED:
- exact named test runs
- user-observable assertion fails
- failure is not setup / syntax / authority failure

3. 不改 assertion，修正後跑 GREEN

FAULTY_FIXTURE=0 npx playwright test tests/browser/checkout.spec.ts \
  --grep "guest can complete checkout" --retries=0

結果判讀返回點
RED 是 decisive assertion，GREEN 同 identity 通過Claim 已有一組可重跑的 failure-sensitivity evidence。若無未解 failure，跳過 trace，直接準備 007-0007 addendum。
RED 是 setup／syntax／browser failure尚未證明 assertion 對壞 behavior 敏感。修 environment／fixture，再從 RED 重跑。
GREEN 失敗且原因不明，或結果 flakyEvidence 尚不 durable；一次 retry 成功不等於修正。只有此時進 007-0006 conditional trace diagnosis。
修正改了 app／test repo diffCandidate identity 已變。Addendum 前回 Engineering Review contract 建新 checkpoint並完整 re-review。

成果物邊界：Test result 是對 assertion 的執行結果；report、screenshot、video、log 或 trace 是 captured artifacts；「可能是 race」是 inference。三者分欄保存。預設不要開 trace：已得到 decisive RED／GREEN 時，多一份 trace 不會提高 claim strength，只增加敏感資料、體積與清理成本。

可見成果：一份綁定同一 test identity與 declared environment 的 RED／GREEN evidence pair，清楚列出唯一受控差異、exact commands、exit results 與 unverified scope。
可觀察回饋：Reviewer 能由 failure output確認 assertion 因錯誤 browser behavior 失敗，並比對 corrected rerun 未改 test expected；若刪除 assertion 後 evidence 仍看似成立，紀錄不合格。

哪一組結果能證明 assertion 對故障行為敏感？

有效 evidence 必須讓 claim assertion 與壞 behavior 直接衝突，並以同一 test identity與可比較 environment 完成修正後重跑。

合法停止／返回／條件式續行：沒有 recoverable fault control、RED 不是 decisive assertion、RED／GREEN identities 不可比較、test 仍 flaky、relevant service／auth 不可重建、artifact 含未處理敏感資料，或 app／test diff 尚未進 Review 時，保存 facts與 cleanup 後停止。Test mapping 錯誤回 007-0004；environment 或 fixture 修正後從本頁 RED重跑。只有未解 failure 需要診斷時進 007-0006；若 RED／GREEN 已清楚且沒有未解 failure，合法 bypass trace，直接續到 007-0007。本頁不代表 Browser evidence addendum、Phase 或 Migration complete。
