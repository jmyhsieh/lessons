Phase 5 Lab · 第 08 課 · 約 40 分鐘 · Promote or retire

升級或退役 workflow contract

目標：根據 Phase 5 第 07 課的 effectiveness evidence，決定 contract 應留在文件、升級成 template/hook/gate，或合併與退役。

本課只做：一份 promotion 或 retirement decision。
先不要做：把容易誤判、缺 evidence 或仍需討論的規則強制化。

強制化要比提醒更嚴格

Claude Code hooks 可在工具使用前後執行自訂 command；runner gate 也可以在收工前判定 pass/fail。這些機制能提供保證，但也會放大誤判成本。

因此，只有當規則低誤判、可機械判定、失敗時有明確修正方式，且錯過會造成實際風險時，才值得升級成 hook 或 gate。仍需要語境判斷的規則，留在 template、checklist 或 review loop。

Promotion ladder

層級用途例子
Reminder提醒 agent 或人類注意。CLAUDE.md 中的工作慣例。
Template讓必要欄位提早出現。issue template 的 evidence 欄。
Review checklist由 reviewer 判斷是否合格。handoff 是否列出未驗證項目。
Runner gate收工前自動判斷 pass/fail。link check、unit tests、schema validation。
Hook在工具使用時點攔截或記錄。阻擋危險 git command、要求特定檔案不可直接改。
判斷規則：如果你無法用一句話說明「失敗 signal 是什麼、修正方式是什麼」，就不要升級成 hook/gate。

先判斷是否只需要 template

若問題是 input 重複缺同一欄，或 reviewer 一直追同一份 evidence，優先放進 issue、PR 或 handoff template。Template 讓正確輸入提早出現，但不強制 pass/fail，也不適合承載每次都不相關的欄位。

Effort 也可以被治理

Hook/gate 不只治理檔案和命令，也可以治理模型成本。不要禁止高 effort，而是把它變成有條件、可回看的例外：誰允許、為什麼、對應哪個 gate、下一次何時降回 high。

規則適合層級
max 只允許在已標記 high-risk review 的 session。review checklist 或 settings policy。
Unattended runner 不允許 max。runner gate。
切到支援 xhigh 的模型後，連續三次仍 blocked，就停止自動迭代。runner gate。
任務完成後 effort 自動回到 high。team practice 或 settings review。

Promotion spec 範例

hookGatePromotion:
  sourceContract: PR template requires link-check evidence
  candidateType: runner-gate
  deterministicSignal: command exits non-zero when links are broken
  falsePositiveRisk: low
  failureMessage: "Run pnpm link-check and attach artifact path."
  effortPolicy: max is not allowed for unattended runs; xhigh requires reason
  rolloutMode: warn-only for 2 weeks
  rollback: remove gate if more than 2 valid exceptions in 5 runs

規範也要能退役

Contract 若已被 template/gate 取代、與其他規則重複、長期沒有 usage evidence、或增加負擔卻沒降低返工，就應合併、移動或退役。清理時保留 decision note，不要讓過時規則繼續消耗 context。

contractCleanup:
  contract: require manual link-check reminder
  decision: retire
  reason: replaced by low-false-positive runner gate
  evidence: last 5 runs passed automatically
  reviewedAt: 2026-07-12
清理規則：每條 contract 都要能指出最近有效 evidence 與下次 review 時點；兩者都沒有，就應檢查是否合併、移動或退役。

實作步驟（做完打勾）

只選已觀察多次、結果明確的 contract。先判斷維持 reminder、放入 template、升級技術閘門，或退役。

例如 command exit code、schema validation、檔案存在、禁止指令。若只能靠人類讀懂，就先留在 review。

工具使用當下要攔截，就考慮 hook；收工前驗收，就考慮 runner gate。

先用警告或 report-only 觀察誤判。若是 effort policy，也先記錄哪些任務要求 xhigh/max，不要第一天就阻擋所有人。

Promotion 要有 warn-only rollout 與 rollback；retirement 要記錄原因、替代機制、evidence 與 review date。

你已完成 contract lifecycle decision。回對話視窗貼上 promotion 或 retirement note，請 AI 老師檢查 evidence 是否支持這個治理層級。

觀念檢查（憑記憶作答）

1. 最適合升級成 gate 的規則是？

gate 需要可機械判定的 pass/fail。仍需人類語境判斷的規則不適合強制化。

2. Hook/gate 初次推出時，建議先？

warn-only 或 report-only 能先觀察誤判與例外，再決定是否強制。

3. 需要在工具使用當下攔截，較適合？

hook 的價值是在工具使用前後執行檢查或攔截。收工驗收則偏向 runner gate。

4. 哪個 effort 規則適合 unattended runner？

Unattended runner 應保持成本與行為可控；max 只能作為人工審查下的例外，不宜作為預設。

5. 哪種 contract 最應該檢查是否退役？

長期未使用、與其他規則重複或已被技術機制取代的 contract 只會增加 context 與維護成本。

Phase 5 收束

到這裡，你已能判斷是否需要 harness、建立可重跑 runner、保存證據與 run lineage、用演練修正流程，並治理 contract 的升級與退役。若沒有重複性、可機械 gates 或營運 evidence，停在 Phase 3 仍是正確答案。

Phase 5 Lab 驗收 rubric

  • 同一 input 可以穩定 show 與 run --dry，且 dry run 不改檔。
  • 至少一筆真 run 能追到 agent evidence、gate results、report 與 closeout。
  • 失敗 fixture、rerun lineage 與 stop condition 都有實際證據。
  • 至少兩次同類 rehearsal 支持一個 keep、revise 或 revert 決策。
  • 最後能用 effectiveness evidence 說明 contract 為何保留、升級或退役。
