Headless 與 CI 自動化 — 沒有人在場的 Claude

任務目標：理解 claude -p 非互動模式的運作與安全模型，寫一個可重複使用的「diff 審查」script，並評估把它放進團隊 CI 的方式。注意：本課是 CLI 課 — headless 本質上是命令列工具，桌面 App 沒有對應功能。

從對話到指令（官方文件）

加上 -p，Claude Code 就從互動對話變成「一個普通的命令列工具」：吃 stdin、印 stdout、跑完退出 — 可以放進 script、pipeline、CI：

# 直接問
claude -p "What does the auth module do?"

# 像 Unix 工具一樣用管線
cat build-error.txt | claude -p "concisely explain the root cause" > output.txt

# 結構化輸出給程式解析
claude -p "Summarize this project" --output-format json | jq -r '.result'
旗標作用
--bare跳過 hooks/skills/MCP/CLAUDE.md 的自動載入 — CI 必加，保證每台機器結果一致
--output-format json結構化輸出（含 session ID、成本 total_cost_usd）
--allowedTools預先核准工具（沒人在場按同意，沒核准就中止）
--permission-mode dontAsk未預先允許的一律自動拒絕 — 鎖死的 CI 基準
--continue / --resume接續對話，多步驟 script 用

安全模型：沒有人在場 = 權限就是一切

互動模式的最後防線是「你逐項批准」。headless 沒有你 — 權限設計取代了你的眼睛：
  • --allowedTools 用第 5 課學過的規則語法，給最小集合："Bash(git diff *),Bash(git log *)" 而不是 "Bash"。
  • 能用管線餵的資料就用管線（餵 diff 進 stdin 就不用給它 git 權限）。
  • 唯讀任務（審查、摘要）安心跑；會寫入的任務無人看管時要三思 — 從唯讀的開始。
費用注意：2026/6/15 起訂閱方案的 claude -p 用量改計入獨立的 Agent SDK 額度。放進 CI 前先用 --output-format json 的 total_cost_usd 估每次成本。

範例：把 Claude 當專案專屬 linter

官方範例 — 餵 diff 進去、只回報錯字，可直接放 package.json：

"lint:claude": "git diff main | claude -p \"you are a typo linter.
  for each typo in this diff, report filename:line on one line
  and the issue on the next. return nothing else.\""

注意兩個設計：diff 用管線餵（不需給 git 權限）、輸出格式講死（給人或程式讀都穩定）。再進一步就是 CI：PR 自動審查用現成的 GitHub Actions / GitLab CI/CD 整合，不用自己從零搭。

實作步驟（做完打勾）

在工作 repo 的終端機（Windows 用 PowerShell 或 WSL）：

claude --bare -p "Summarize this file: README.md" --allowedTools "Read"

故意下一個需要未核准工具的任務（例如只給 Read 卻要它跑測試），觀察它如何中止 — 這就是 headless 的安全網。

仿照 typo linter 範例，做一個對你們團隊有用的版本（審 API 慣例？找 console.log？檢查 commit 規範？）。重點：用管線餵 diff、輸出格式講死、--bare。

乾淨的 diff、有問題的 diff、空 diff — 確認輸出都穩定可預期。這是第 7 課「可驗證」原則用在 script 本身。

讀 GitHub Actions 整合文件，評估：你們的 pipeline 哪一步最適合加 AI 審查？跟團隊討論後再上 — CI 變更影響所有人。

觀念檢查（憑記憶作答）

1. CI script 裡為什麼要加 --bare？

--bare 跳過的是「環境自動載入」：某個同事 ~/.claude 裡的 hook 不會悄悄影響 CI 結果。權限該怎麼給還是怎麼給。

2. headless script 要讀 git diff，較安全的設計是？

資料能用管線餵就不給工具權限 — 無人在場時，每少給一個權限就少一分風險（最小權限原則的 headless 版）。

3.（複習第 5 課）互動模式的「逐項批准」在 headless 中被什麼取代？

（間隔複習）沒人在場按同意 → 權限的事前設計就是你的眼睛。未核准的工具呼叫會讓執行中止，而不是等待。
