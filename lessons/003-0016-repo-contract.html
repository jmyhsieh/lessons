Phase 3 · Lesson 0040 · 約 25 分鐘 · Repo contract

把 verified workflow 固化成 repo contract

目標：把第 39 課驗證為 keep 的 workflow patch，放到最小、最合適的 repo contract 裡。這一課不把一次成功直接升級成平台、hook 或 runner。

Contract 不是全部放進 CLAUDE.md

Claude Code memory 說明 CLAUDE.md 是每次 session 載入的持久指引，適合放你本來會重複解釋的專案規範；但它是 context，不是強制執行層。如果規則必須在特定時點阻擋或驗證，應該考慮 Hooks reference 或 settings。

Claude Code settings 把 project scope 放在 repo 的 .claude/，適合分享 permissions、hooks、MCP servers 等團隊設定。這代表 repo contract 要先決定「這是行為指引、任務模板、還是技術閘門」。

把 patch 放到正確位置

Contract target適合放不要放
CLAUDE.md每個 session 都需要的短規則、build/test 指令、工作慣例。長流程、偶爾才用的任務。
.claude/rules/*.md可依路徑或主題拆分的規則，例如 API、前端、測試。整個 repo 都不需要知道的細節。
AGENTS.mdCodex 或多 agent 共用的 repo 指南；必要時用 CLAUDE.md 橋接。假設 Claude Code 一定會自動讀到。
Issue template每次任務 input 都要填的欄位。每個 session 都要遵守的工作規範。
Reference checklist半手動流程、reviewer 判斷規則、handoff 格式。需要硬性擋下的危險操作。
Hook / runner gate已重複驗證、低誤判、必須強制的檢查。仍需要大量人類判斷的提醒。
判斷規則：只有第 39 課結果是 keep，才進 repo contract。revise 回第 38 課；revert 記錄原因即可。

Repo contract note 範例

# Repo workflow contract
sourceVerification: run-0052
verifiedPatch: brief must state when link-check evidence is enough
contractTarget: reference/harness-input-contract.html
rule: Scope-out must name which validation classes are intentionally skipped.
enforcement: reviewer checklist only
verification: next same-class doc task includes scope-out without clarification
rollback: remove the checklist row if it adds questions without reducing rework

實作步驟（做完打勾）

只拿已被第二輪 evidence 支持的 patch。不要把 revise 或 revert 的內容寫進規範。

先選 reference、checklist 或 issue template。只有每個 session 都需要才放 CLAUDE.md；只有必須強制才放 hook。

規則要短、具體、可審查。例如「Scope-out 必須列出本輪不跑的 validation 類型」，不要寫「請更謹慎」。

說明下一次怎麼知道 contract 有效：少問問題、gate 更清楚、handoff 可接手，或 reviewer 能直接找到 artifact。

如果 contract 讓流程更重、造成誤判、或沒減少返工，就撤回。Repo contract 也要可修正。

你已完成 repo contract note。回對話視窗貼上 contract note，請 AI 老師檢查 target 是否選得太重。

觀念檢查（憑記憶作答）

1. 最適合放進 CLAUDE.md 的是？

CLAUDE.md 適合每個 session 都需要、你會重複解釋的短規則。一次性任務直接寫在 brief。

2. 必須強制擋下的檢查應該用？

需要保證的事要用 settings、hook 或 runner gate。記憶文件只能引導模型，不能保證執行。

3. Verified patch 第一次固化時，優先選？

先放到最小且可 review 的文件或 checklist。連續驗證後，才考慮技術化或平台化。
