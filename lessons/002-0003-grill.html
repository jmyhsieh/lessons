把模糊需求問清楚（Grill）

目標：用 /grill-with-docs 把真實 repo 的一個模糊需求追問成對齊的計劃，過程中讓 CONTEXT.md 與 ADR 自然長大。這直攻 misalignment — AI 開發最常見、也最昂貴的失敗模式。

兩支 grill，怎麼選

/grill-me/grill-with-docs
做什麼對你的計劃做結構化追問，一次一題，每題附建議答案同樣追問，外加對照 CONTEXT.md/ADR/程式碼，邊問邊更新文件
適合快速壓力測試一個想法正式開發前的對齊（本課程建議的預設選擇）

共同的底層機制（skill 原文）：「沿著設計樹的每一條分支走，逐一解決決策之間的依賴」「能從 codebase 找到答案的問題，直接去探索 codebase 而不是問你」。

/grill-with-docs 的五個追問手法

知道它會怎麼問，你才接得住（出自 skill 定義）：

  1. 對照詞彙表 —「你的 CONTEXT.md 定義『取消』是 X，但你現在的意思是 Y — 哪個對？」
  2. 銳化模糊語言 —「你說『帳號』— 是 Customer 還是 User？這是兩個東西。」
  3. 具體情境壓測 — 發明邊界案例情境，逼你把概念之間的界線講清楚。
  4. 與程式碼交叉比對 —「程式碼是整單取消，但你剛說可以部分取消 — 哪個才對？」高風險 repo 的關鍵檢查：你以為的和程式碼實際做的常常不一樣。
  5. 文件即時更新 — 術語一敲定就寫進 CONTEXT.md（純詞彙表，不放實作細節）；ADR 則節制地提議。
ADR 三條件（全滿足才寫）：難以回頭（hard to reverse）＋ 沒脈絡會看不懂為什麼（surprising without context）＋ 真實取捨的結果（real trade-off）。缺一就跳過 — ADR 多了就沒人讀。

你在 grill 中的角色

grill 的品質取決於你的回答。三個原則：

  • 別敷衍 — 「都可以」是 misalignment 的溫床。不確定就說不確定，讓它幫你列選項。
  • 善用它的建議答案 — 每題附的建議是好的起點，但它不懂你的業務脈絡，該推翻就推翻。
  • 讓它去查 code — 它問「現在系統怎麼處理 X」時，正確回應常是「你去看 code 確認」。

何時升高 effort

Grill 的成本應該花在「決策不確定」上，不是花在每個小需求上。若只是釐清文案或簡單流程，維持 high；若它正在跨程式碼、ADR 與產品語言找矛盾，升到 xhigh；若這次 grill 會決定不可逆架構方向，先用 opusplan 做 plan-first。

實作步驟（做完打勾）

從產品、維運或開發待辦裡挑一個「知道要做但說不清楚怎麼做」的需求 — 越模糊越好，那正是 grill 的用武之地。

在目標 repo 的 session 裡：

/grill-with-docs 我想做：[一兩句描述你的需求]

一次一題，認真答。預期 10–30 分鐘的來回。

(a) 哪一題讓你發現「我其實沒想清楚」？(b) 它有沒有抓到你的話和程式碼的矛盾？(c) CONTEXT.md 長出了哪些新詞條？

結束時你手上應該有：一份對齊的計劃、更新過的 CONTEXT.md、可能 0–2 篇新 ADR（用三條件檢查它提議的 ADR 該不該存在）。先不要實作 — 計劃留著，下一課接 /to-prd 與 /to-issues。

🎉 Phase 2 成功條件第一條達成：模糊需求 → 對齊計劃。回對話視窗回報：哪一題最有幫助？CONTEXT.md 多了幾條？

觀念檢查（憑記憶作答）

1. grill 過程中它問「現在系統的逾時是怎麼算的？」你不太確定，最好的回應是？

skill 設計原文：能從 codebase 回答的問題就去探索 codebase。憑印象答是在把 misalignment 重新引進來；跳過則留下未解決的決策依賴。

2. 它提議為「選用輪詢而非 webhook」寫 ADR。判斷該不該寫的標準是？

三條件缺一不可（skill 原文「offer ADRs sparingly」）。什麼都記 = 什麼都沒人讀。

3.（複習第 14 課）grill 中敲定了「『結算日』指每月 25 日鎖帳那天」。這寫進哪？

（間隔複習）術語定義 = CONTEXT.md（純詞彙表）。ADR 記「為什麼選這個設計」；CLAUDE.md 管工作規範 — 三份文件的職責別混。
