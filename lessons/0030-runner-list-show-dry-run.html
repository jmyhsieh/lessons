實作 runner 第一片 — list / show / dry-run

目標：把第 29 課的 runner contract 變成第一個可測 CLI 切片。這一課只做 list、show、dry-run，不呼叫真 agent、不改檔、不產 PR。

為什麼先不跑 agent

Claude Code best practices 建議用 claude -p 和結構化輸出來自動化，但在接上模型前，runner 本身要先能穩定回答三件事：有哪些 input、某個 input 解析成什麼、真正執行前會送出什麼 prompt 與 gates。

Claude Code CLI reference 提到 --output-format json、--tools、--allowedTools 等旗標；這些只有在 dry-run 能清楚列出時，才適合交給 unattended run。

第一片只做三個命令

命令要回答的問題不做什麼
runner list目前有哪些可跑 input？ID、來源、狀態。不解析完整 prompt。
runner show <id>這個 input 被正規化後長什麼樣？不呼叫 agent。
runner run --dry <id>真的執行前會用哪些 prompt、tools、gates、paths？不改檔、不跑模型。
判斷規則：如果 show 和 dry-run 的輸出無法讓 reviewer 判斷 runner 會做什麼，就還不能接 claude -p。

Dry-run 輸出要固定

{
  "id": "issue-0042-login-timeout",
  "source": "issues/0042.md",
  "promptPreview": "...",
  "allowedTools": ["Read", "Edit", "Bash(npm test -- auth)"],
  "gates": ["scope", "npm test -- auth"],
  "evidenceDir": ".harness/evidence/run-preview",
  "reportPath": ".harness/reports/run-preview.md",
  "willCallAgent": false,
  "willModifyFiles": false
}

實作步驟（做完打勾）

例如 issues/*.md 或 .harness/inputs/*.md。先固定一種，不要同時支援 GitHub、Linear、Notion。

打開 Runner 第一片速查表，先寫出 id、source、outcome、scope、gates、stop。

一個完整 input 應該通過；一個缺少 Outcome 或 Gates 應該失敗。測試先保護 parser，不保護 agent。

先讓三個命令輸出 deterministic JSON。文字版可以晚點加，JSON 先穩才方便測試與 report。

跑完 dry-run 後檢查 git diff --stat 或 temp fixture 目錄。若 dry-run 會寫 report 或 evidence，它就不是 dry-run。

你已完成 runner 的第一個可測切片。回對話視窗貼上三個命令的輸出摘要，請 AI 老師檢查是否已經能安全接下一片。

觀念檢查（憑記憶作答）

1. 第一片 runner 不應該做什麼？

第一片只保護 input、parser、prompt preview、gate plan。還沒驗證前，不應呼叫真 agent。

2. Dry-run 最應該輸出什麼？

Dry-run 要讓 reviewer 看見將要送出的 prompt、tools、gates、paths，證明 runner 不會跑錯任務。

3. 測試第一片時，最該先保護哪一層？

這一片還不碰模型與排程。最重要的是 input 解析與 dry-run 輸出穩定。
