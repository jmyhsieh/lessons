Phase 4 · 第 03 課 · 約 20 分鐘 · Design system grounding

設定、匯入並校正 design system

目標：分清楚組織 design system 的 setup／publish 與專案的 /design-sync import，完成其中一條符合權限的路徑，再以權威來源校正結果。

本課只做：選定 setup／publish 或 project import 其中一條路徑，並抽查 tokens 與 components。
先不要做：把 /design-sync 當成組織發布開關，或混入過時截圖與實驗分支。

核心知識：輸出品質受來源品質限制

Claude Design 可以從 codebase、prototype、文件與品牌資產抽取 colors、typography、components 與 layout patterns；官方也明確提醒，design system import 的品質取決於來源，混亂或不完整的來源會反映在結果裡。請先讀 Set up your design system 與 Get started with Claude Design。

以下是本課採用的保守優先序，是校正方法，不是平台自動保證：

優先來源先檢查
1正式 design-system repo／component library目前 release、token 檔、公開 API、deprecated 元件
2已發布的 component docs／產品流程狀態、variant、responsive 與 accessibility 行為
3品牌 guidelines 與核准資產logo、字體、色票與使用限制是否仍有效
4截圖、簡報與探索稿只當參考，不能覆蓋正式 token 與 component contract
Repo 與 assets/ 要扮演什麼角色？Repo 提供可實作的 component 與 token 事實；assets/ 提供經核准的 logo、圖像與字體。兩者若衝突，先找擁有者或版本紀錄，不要讓模型自行裁決。

兩條工作流，不是同一個動作

組織 design system 的建立與發布在 Claude Design onboarding 或 organization settings 完成：上傳來源、review 生成結果、以 test project 驗證，最後切換 Published。/design-sync 則從 Claude Code 把 GitHub repo、design files、uploads 或 local codebase 中的一個或多個既有 systems 帶入 Claude Design project；它不會替你建立、發布或設成組織預設。

大型 repo 可從 Claude Code 使用 /design-sync 匯入，避免直接在 browser 處理過多內容。無論來源是 settings upload 或 project import，抽取結果都仍需稽核；功能處於 beta，方案、角色與管理員設定也可能影響可用性。

實作 checklist

只能選「組織 setup／publish」、「project import」、「驗證已發布 system」或「僅附 project context」。若不確定，先向管理員或 design-system owner 確認。

記下 repo、branch 或 release、核心路徑與擁有者。一般成員記錄已發布系統；沒有系統時則記錄這次附上的 project context。

組織 owner 走 onboarding/settings 的 upload → review → test → publish；project import 才執行 /design-sync；一般成員驗證已發布 system；沒有授權者只附核准 context。

至少比對 3 個 tokens、3 個 components、desktop/mobile 各 1 個狀態，並記錄 source path 與差異；沒有正式系統時，改以 brief 與核准 context 為比較基準。

Setup 路徑記錄發布狀態；import 路徑記錄 project revision，不宣稱已發布；一般成員記錄是否可沿用；沒有 system 者明寫「project context，不是組織 design system」。

你已建立可追溯的 design-system 路徑。把權限分支與驗證紀錄貼回對話視窗，請 AI 老師找出「來源」與「抽取結果」被混為一談的地方。

觀念檢查（憑記憶作答）

1. 哪個入口負責把 system 發布給組織使用？

組織 system 要在 Claude Design onboarding／organization settings review、test 並開啟 Published；/design-sync 是 project import。

2. 哪個來源最適合當 component 行為的權威依據？

正式 component library 最接近可實作 contract；截圖與概念稿可補視覺 context，但不應覆蓋它。

3. 來源互相衝突時，應該怎麼處理？

衝突代表 source-of-truth 問題。先釐清版本與擁有者，才能避免模型合成第三套規則。
