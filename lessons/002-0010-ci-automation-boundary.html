在 CI 中安全使用 Claude Code

本課成果：一張 CI 自動化邊界卡，列出允許的任務、權限、輸出與成本限制。

本課只做：界定 CI 中能安全交給 Claude Code 的任務。
先不要做：讓 CI 自動產生未經人工審查的正式環境改動。
CI 執行時沒有人逐項確認，因此必須事先限制權限與可執行的動作。CI 裡先做唯讀摘要、程式差異審查與文件檢查；會寫檔、會推送、會修改環境的任務不要直接無人值守。

CI 任務的四個條件

  • 明確認證：--bare 不讀 OAuth/keychain；使用 ANTHROPIC_API_KEY、傳入的 apiKeyHelper 或服務供應商憑證，不依賴開發者電腦的登入狀態。
  • 最小工具面：--allowedTools 只會預先批准工具，不是允許清單；用 --tools 限制內建工具。能從 stdin 餵資料就用 --tools ""。
  • 穩定輸出：--output-format json 固定結果外層結構；回答內容需要固定欄位時用 --json-schema。
  • 可追蹤：記錄成本、執行時間、失敗率與誤報率。

安全的程式差異審查範例

git diff main |
claude --bare -p "Review this diff for risky production config changes.
Return only filename:line and reason. Return empty output if none." --tools ""

這個設計沒有給 Claude 內建工具；程式差異已經從管線餵進去。CI 還必須依上面的規則提供 bare 模式可用的明確認證。

實作步驟（做完打勾）

例如錯字檢查、危險設定審查、發行說明摘要。

能不用工具就用 --tools ""；真的需要才列最小內建工具集合。不要把 --allowedTools 誤當成限制工具可見性的允許清單。

正常程式差異、有問題的程式差異、空白程式差異，輸出都要穩定。

CI 紀錄、PR 留言、成品檔或 JSON 檔。要讓人能判斷是否採納。

Claude Code 擴充實作完成條件：自動化邊界卡列出允許任務、權限、輸出、成本限制與必須由人確認的步驟。

觀念檢查

1. CI 裡要讀程式差異，較安全的做法是？

能用資料輸入解決，就不要給工具權限。

2. headless 任務進 CI 前，最不該忽略的是？

CI 不是命令跑得動就算完成；還要能追蹤權限、輸出、成本與失敗情況。
