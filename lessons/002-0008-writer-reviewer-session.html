Phase 2 · 第 08 課 · 約 20 分鐘 · 品質工作流

用兩個工作階段分開撰寫與審查

本課成果：一輪由兩個乾淨工作階段完成的撰寫與審查交接。

本課只做：用兩個工作階段分開撰寫與審查。
先不要做：讓同一個工作階段自寫自審後直接合併。

雙工作階段流程

撰寫工作階段審查工作階段
在撰寫用工作樹實作、驗證，建立檢查點提交。
在另一個工作樹以明確起點與撰寫分支讀取同一份已提交的程式差異。
逐項處理審查意見。
為什麼要檢查點提交：不同工作樹共用 Git 物件與參照（refs），但不共用尚未提交的工作目錄變更。若撰寫者只留下未提交的程式差異，審查用工作樹看不到那份內容。

實作步驟（做完打勾）

完成探索、實作、驗證與程式差異審查，然後在撰寫分支建立檢查點提交。先記下審查起點與撰寫分支，例如 main 與 claude/task-name。

在另一個工作樹的乾淨工作階段，不必切換到撰寫分支；用明確參照取得已提交的程式差異，先確認檔案清單正是要審的範圍：

git diff --stat main...claude/task-name
git diff main...claude/task-name
Review the committed diff from main...claude/task-name
against this task brief. Only report correctness gaps,
missing tests, or scope creep.

先分類成必修、可選與不相關，再處理有效意見。

修完審查意見後，重新跑原本的成功條件，並用新提交或修訂提交（amend）更新撰寫分支。若程式差異的參照改變，審查者必須重新讀取新的已提交程式差異。

完成條件：撰寫者交付內容與審查者意見分開保存，修正後的差異已再次核對。

觀念檢查

1. 雙工作階段比同一對話直接審查的主要優點是？

乾淨的對話脈絡比「自己檢查自己」更接近獨立審查。

2. 審查者回報很多建議時，第一步是？

審查意見仍要人類判斷，不能直接當成新的命令來源。
