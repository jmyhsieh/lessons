用 /to-spec 把對話凝結成 spec

目標：把前面 grill 與 prototype 已經釐清的內容，整理成一份可引用、可審查、可切 ticket 的 spec。你也可以把它理解成 PRD；upstream 現在用 /to-spec 作為 canonical 名稱。這一課只做「凝結」，不重新訪談，也不開始實作。

本課只做：把已對齊的內容整理成 spec。
先不要做：需求還沒問清楚就硬產 spec。

Pipeline 全景：你在這裡

/grill-with-docs → 可選（/handoff → /prototype → /handoff）→ /to-spec → /to-tickets → /implement

凝結，不是再訪談

/to-spec 的關鍵設計是：不要再訪談使用者，直接綜合這個 session 已經知道的內容。若它開始問大量新問題，通常代表前面的 grill 沒做透，應該回去補對齊，而不是把 spec 當補救訪談。

Context hygiene：從 grill 到本課，再到下一課 /to-tickets，盡量維持同一個未中斷 context；不要中途 clear 或 compact，讓 spec 與 tickets 共用完整的決策脈絡。只有接近 smart zone 上限時才用 /handoff 換 session。
Spec 應該包含你要檢查什麼
問題陳述與範圍邊界是否清楚說明要解的問題，以及哪些事不做。
大量編號 user stories是否覆蓋 grill 中談過的場景與邊界案例。
實作決策與測試接縫是否尊重 CONTEXT.md、ADR 與既有 repo 介面；測試 seam 是否在夠高、夠穩的位置。
發佈位置是否寫到第 01 課設定的 GitHub / GitLab / local markdown / Other issue tracker。
你的主要工作：審 spec 的「漏」與「多」。漏掉 user story 會讓後續 ticket 不完整；多寫未同意 scope 會讓 agent 做出不該做的功能。

實作步驟（做完打勾）

在第 04 課 grill 的同一個 session 繼續；若 prototype 曾分支出去，先讀它帶回來的 handoff。只有原 context 已接近上限時，才用 handoff 開新 session，並引用 grill 結論、prototype 結論、CONTEXT.md 與相關 ADR。

/to-spec

若它說資訊不足，先回到 /grill-with-docs；不要在 spec 階段臨時補一堆沒有驗證的假設。

逐條對照前面對齊過的需求：有沒有漏掉角色、例外、錯誤狀態、權限或資料邊界？

確認它提的 seams 是 repo 裡真實可測的位置。看不懂就追問：為什麼在這個介面驗證？有沒有更高層的接縫？

確認 spec 被發佈到 issue tracker；local markdown 的 canonical 位置是 .scratch/<feature>/spec.md。下一課會從這份 spec 切成 tickets。

🎉 你已把對話凝結成 spec。回對話視窗回報：spec 裡最重要的 user story 是哪一條？

觀念檢查（憑記憶作答）

1. /to-spec 開始大量追問新需求，這代表？

/to-spec 是綜合已知內容，不是重新訪談。大量追問代表上游沒有足夠材料。

2. spec 裡的 user stories 最重要的作用是？

下一課 /to-tickets 會依 spec 切成可認領的工作；user stories 是切片的主要材料。
