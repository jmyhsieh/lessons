用 /to-spec 把對話凝結成規格

本課成果：一份可引用、可審查，也能往下切工作項目的規格（spec）。

本課只做：把已對齊的內容整理成規格。
先不要做：需求還沒問清楚就硬產規格。

工作流程全景：你在這裡

/grill-with-docs → 可選（/handoff → /prototype → /handoff）→ /to-spec → /to-tickets → /implement

凝結，不是再訪談

/to-spec 的關鍵設計是：不要再訪談使用者，直接綜合這個工作階段已經知道的內容。若它開始問大量新問題，通常代表前面的 grill 沒做透，應該回去補對齊，而不是把規格當補救訪談。

保持對話脈絡乾淨：從需求追問到本課，再到下一課 /to-tickets，盡量維持同一個未中斷工作階段；不要中途使用 /clear 或 /compact。只有脈絡快滿時才用 /handoff 換工作階段。
規格應該包含你要檢查什麼
問題陳述與範圍邊界是否清楚說明要解的問題，以及哪些事不做。
編號的使用情境（user stories）是否涵蓋需求追問時談過的情境與邊界案例。
實作決策與測試接縫是否尊重 CONTEXT.md、ADR 與既有程式庫介面；測試接縫是否在夠高、夠穩的位置。
發佈位置是否寫到第 01 課設定的 GitHub／GitLab／本機 Markdown／其他議題追蹤系統。
你的主要工作：審規格的「漏」與「多」。漏掉使用情境會讓後續工作項目不完整；多寫未同意範圍會讓 Claude Code 做出不該做的功能。

實作步驟（做完打勾）

在第 04 課 grill 的同一個工作階段繼續；若 prototype 曾分支出去，先讀它帶回來的交接。只有原對話脈絡已接近上限時，才用交接開新工作階段，並引用 grill 結論、prototype 結論、CONTEXT.md 與相關 ADR。

/to-spec

若它說資訊不足，先回到 /grill-with-docs；不要在規格階段臨時補一堆沒有驗證的假設。

逐條對照前面對齊過的需求：有沒有漏掉角色、例外、錯誤狀態、權限或資料邊界？

確認它提的接縫是程式庫裡真實可測的位置。看不懂就追問：為什麼在這個介面驗證？有沒有更高層的接縫？

確認規格被發佈到 議題追蹤系統；本機 Markdown 的標準位置是 .scratch/<feature>/spec.md。下一課會從這份規格切成工作項目。

完成條件：規格包含使用者故事、可判定的驗收條件、範圍與尚未決定的問題。

觀念檢查（憑記憶作答）

1. /to-spec 開始大量追問新需求，這代表？

/to-spec 是綜合已知內容，不是重新訪談。大量追問代表上游沒有足夠材料。

2. 規格裡的使用情境最重要的作用是？

下一課 /to-tickets 會依規格切成可認領的工作；使用情境是切片的主要材料。
