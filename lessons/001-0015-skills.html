Phase 1 · 第 15 課 · 約 30 分鐘 · 進階實作課

把重複流程打包成指令（Skills）

任務目標：把你工作中一個重複出現的多步驟流程做成 skill，之後一句 /指令 就能執行，並透過 git 分享給全隊。

本課只做：判斷重複工作流是否值得打包成 skill。
先不要做：把一次性任務或尚未穩定的流程做成 skill。

什麼時候該做成 skill（官方文件）

訊號跟 CLAUDE.md 類似但對象不同：

  • 你發現自己重複貼同一段指示、檢查清單或多步驟流程到對話裡
  • CLAUDE.md 裡某一段已經長成「流程」而不是「事實」

關鍵差異：CLAUDE.md 每個 session 都全文載入（吃 context）；skill 只在用到時才載入。所以長的參考資料、偶爾才用的流程 → skill；每次都要遵守的短規則 → CLAUDE.md。

結構：一個資料夾 + SKILL.md

.claude/skills/summarize-changes/SKILL.md   ← 專案（隨 git 共享）
~/.claude/skills/<name>/SKILL.md            ← 個人（所有專案可用）

資料夾名稱就是指令名稱（deploy-staging/ → /deploy-staging）。SKILL.md 長這樣：

---
description: 摘要未 commit 的變更並標記風險。當使用者問
  「改了什麼」、要 commit message、或要 review diff 時使用。
---

1. 執行 git diff 取得所有未提交變更
2. 依模組分組摘要
3. 標記：碰到設定檔／migrations／權限相關的變更
4. 用團隊格式產生 commit message 草稿

兩種觸發方式，一個開關

方式怎麼觸發適合
你手動輸入 /skill-name有副作用的流程（部署、發布）
Claude 自動你的話符合 description 描述的情境知識型、無副作用的輔助
有副作用的 skill 一定加 disable-model-invocation: true，讓它只能由你手動觸發 — 你不會想要 Claude「覺得相關」就自己跑部署。另外 $ARGUMENTS 可接收參數：/fix-issue 1234 會把 1234 帶進內容。

寫好 description 是自動觸發的關鍵：說清楚「做什麼」+「什麼情境用」，把主要使用情境寫在最前面。skill 目錄有變更會即時生效，不用重啟。

實作步驟（做完打勾）

回想最近兩週：你重複向 Claude 解釋過什麼流程？（例：「我們的 PR 前檢查」「依模板建新 API endpoint」「release notes 產生」）。挑一個。

在工作 repo 建 .claude/skills/<名稱>/SKILL.md。可以請 Claude 代寫初稿，但 description 與步驟自己打磨 — 步驟要具體到「另一個不認識你的工程師也能照做」。有副作用就加 disable-model-invocation: true。

同一個 session 直接輸入 /你的skill名（變更即時生效）。觀察它是否照步驟走、結果是否符合預期，來回修 SKILL.md 到穩定。

開新對話，用自然語言描述該情境（不要提 skill 名字），看 Claude 會不會自己載入這個 skill。不會的話 → 修 description，把觸發情境寫得更像你實際會說的話。

.claude/skills/ 進版控，照常走 PR。隊友 pull 下來就多了這個 / 指令。

🎉 你的第一個團隊 skill 上線了！回對話視窗回報：做了什麼 skill？自動觸發的 description 調了幾次才命中？

觀念檢查（憑記憶作答）

1. 「我們的 API 命名慣例」（兩行規則，每次寫 code 都要遵守）該放？

每次都要、又短 → CLAUDE.md。skill 的優勢在「用到才載入」，對每次都需要的兩行規則沒有意義；hook 是 shell 指令，沒辦法「強制命名風格」這種需要判斷的事。

2. 「/deploy-staging 部署流程」最該加哪個 frontmatter？

部署有副作用 — 必須只能手動觸發，防止 Claude 自行判斷「相關」就執行。when_to_use 反而是給自動觸發用的，方向相反。

3.（複習三層模型）「commit 前必跑測試，不過就不准結束」這種保證，用什麼實現？

（間隔複習 Phase 1 第 13 課）關鍵字是「必」= 保證 = hooks。skill 和 CLAUDE.md 都靠模型配合，只有 hook 是系統強制。
