Subagents — 用分身保護你的 context

任務目標：理解 subagent 的核心價值（context 隔離），學會委派調查與獨立 review 兩種用法，並建立一個團隊共用的自訂 subagent。

為什麼需要分身

第 7 課學過：context 塞滿是效能最大殺手。可是調查 codebase 必然要讀大量檔案 — 全部進主對話就完了。subagent 的解法（官方文件）：

主對話：「用 subagent 調查我們的認證系統怎麼處理 token refresh」
        ↓
分身在自己的獨立 context 裡讀幾十個檔案
        ↓
主對話只收到一份摘要 — 你的 context 乾乾淨淨

內建三個常用分身（Claude 會自動委派，你也可明講）：Explore（唯讀搜索）、Plan（規劃）、general-purpose（通用）。

第二個殺手用法：獨立 review

寫 code 的那個 Claude 會偏袒自己剛寫的 code。subagent 用全新的 context 看 diff — 它沒看過產生這段 code 的推理過程，只看結果與你給的標準：

用 subagent 對照 PLAN.md 審查這次的 diff：
每個需求都實作了嗎？列出的邊界案例有測試嗎？
有沒有改到任務範圍以外的東西？只回報影響正確性的缺口。
官方提醒：被要求「找缺口」的 reviewer 幾乎一定會回報一些 — 即使工作沒問題。指明「只回報影響正確性或明列需求的缺口」，其餘當選配，避免過度工程。

自訂 subagent

當你反覆派出「同一種工人」時，把它定義成檔案。位置：.claude/agents/（專案、進版控）或 ~/.claude/agents/(個人)；也可用 /agents 指令互動建立。格式與 skill 神似：

---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for:
- Injection vulnerabilities (SQL, XSS, command injection)
- Secrets or credentials in code
Provide specific line references and suggested fixes.

重點欄位：tools 限制它能用的工具（review 用的分身不給 Edit — 又一個「強制優於指引」）；model 可指定便宜快速的模型跑簡單任務控制成本；description 決定 Claude 何時自動委派。

實作步驟（做完打勾）

在工作 repo 挑一個你好奇的子系統：「用 subagent 調查 [子系統] 的運作方式，回報摘要」。對比第 2 課直接問的體感 — 注意主對話多乾淨。

下次完成任務後（或拿現有分支），用上面的範本叫 subagent 審 diff。觀察它找到的缺口：哪些真有價值、哪些是「為找而找」？

想想你們團隊 review 時最常抓什麼（安全？效能？API 慣例？），用 /agents 或手寫檔案建一個專門的 reviewer，tools 只給唯讀（Read, Grep, Glob）。

明講「用 [名稱] subagent 審查這段 code」測試行為，調整 prompt 到輸出有用，然後 .claude/agents/ 走 PR 進版控。

🎉 進階四件套（hooks、skills、MCP、subagents）集滿！回對話視窗回報：自訂 reviewer 第一次出手抓到什麼？

觀念檢查（憑記憶作答）

1. 為什麼用 subagent 做 code review 比同一個對話裡接著問「review 一下」更有效？

關鍵是 context 隔離：同一對話裡的 Claude 會偏袒自己剛寫的 code；分身只看 diff 和標準，立場獨立。

2. review 用的自訂 subagent，tools 欄位該怎麼設？

審查者不該有筆 — tools 限制是系統層強制（同一條主線：強制優於指引）。發現的問題回到主對話修，職責分離。

3.（複習第 7 課）「調查這個 bug 可能在哪」會讀大量檔案。不用 subagent 的話，最大的代價是？

（間隔複習）context 是最稀缺的資源，塞滿會讓它「忘記」指示、錯誤變多 — 這正是第 7 課 context 管理三習慣存在的原因。
