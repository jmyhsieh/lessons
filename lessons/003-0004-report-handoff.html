產出 report / handoff

目標：把第 26 課的 issue / brief 與第 27 課的 gates/evidence，收束成兩份交付物：report 給 reviewer 判斷結果，handoff 給下一個 session 或 agent 繼續工作。

Report 與 handoff 的分工

Claude Code best practices 建議讓 Claude 展示 evidence，而不是只宣告完成；也建議管理 context、在跨日任務中能 resume 或用乾淨 context 接續。Report 和 handoff 正好服務兩種讀者。

交付物讀者用途
Reportreviewer、PM、未來的你。判斷這次 run 是否可信、哪些 gate 通過、哪些 evidence 支撐結果。
Handoff下一個 agent、下一個 session、接手的人。冷啟動下一步，不重複貼 issue、report、diff，只引用正本。
判斷規則：report 是「這次發生了什麼」；handoff 是「接下來要怎麼繼續」。兩者可以互相連結，但不要互相取代。

Report 要回答五件事

區塊內容例子
Status本次 run 的狀態。done、blocked、needs-review
Input使用哪份 issue / brief。issues/0042.md
Changes改了什麼，不貼整段 diff。修正 token refresh，新增 timeout regression test。
Gates每個 gate 的結果與 evidence。npm test -- auth pass，log 在 .harness/evidence/run-42/test.txt。
Next還要誰看、還缺什麼。等待 security reviewer；production secret 缺口未解。

Handoff 要保留四種脈絡

區塊寫什麼不要寫什麼
Current state現在停在哪裡，下一步是什麼。不要重貼整份 report。
Canonical linksissue、report、evidence、PR、ADR 的路徑或 URL。不要複製正本內容。
Decisions這次 run 才產生的非顯而易見判斷。不要寫已在 issue 明列的需求。
Suggested skills下一個 agent 應該用哪些 skill 或模式。不要丟一串無關工具清單。

實作步驟（做完打勾）

至少要有 command、result、artifact、decision。沒有 evidence，就先回第 27 課補，不要寫漂亮 report。

打開 Report / handoff 速查表，填 Status、Input、Changes、Gates、Next。

Reviewer 不應只看到「完成」。他要能看到 gate 結果、artifact 路徑、未驗證項目與例外。

handoff 只寫下一個 session 需要的脈絡：停在哪裡、看哪些 canonical links、哪些決策不能忘、建議用哪些 skill。

請讀取 [handoff path]。
先不要改檔，請回報：
1. 你認為目前狀態是什麼？
2. 下一步要做什麼？
3. 還缺哪些 evidence 或權限？

觀念檢查（憑記憶作答）

1. Report 的主要讀者是誰？

Report 要讓 reviewer 判斷本次 run 是否可信，因此重點是 status、gate、evidence、例外與下一步。

2. Handoff 裡遇到既有 issue 或 report，應該怎麼處理？

handoff 不應複製正本內容，否則會產生兩份可能分岔的事實。它應引用 canonical links。

3. 哪個內容最適合放在 handoff？

handoff 服務下一個 session 冷啟動，最重要的是目前狀態、下一步、正本連結、決策與建議 skill。

下一步

先用一個真實任務練習：同一包 evidence 產出一份 report，再產出一份 handoff。若它能被 reviewer 判斷、也能讓新 session 接手，下一課就可以把整條流程串成最小 runner。
