PM 如何把任意 skill 組成可交付流程

目標：把圖片裡「從需求到可交付內容」的流程，轉成一套可重複使用的 skill 編排法。重點不是背哪個 skill，而是判斷每一步需要什麼 artifact，然後選能產生它的工具。

先看流程，不要先看 skill

圖片的主線其實是這句話：

需求 → 收斂 → 文件 → 發散 → 原型 → 校準 → 驗證 → 交付

這條線可以用 mattpocock/skills，也可以混用 Obsidian、Figma、Playwright、文件、簡報、試算表、圖片生成、browser QA，甚至一般 prompt。判斷標準只有一個：這一步有沒有把上一個輸入變成下一個可驗收 artifact？

把圖片拆成七個工作槽位

槽位圖片例子可替換選項輸出
1. 定義範圍接受需求、轉成開發範圍Obsidian、obsidian-vault、文件筆記需求摘要
2. 收斂假設/grill-me 收斂想像grill-with-docs、訪談、問題清單風險與開放問題
3. 固化文件產出 PROJECT.mdto-prd、設計 brief、issue spec可引用的專案文件
4. 發散方案/superpowers brainstormingdesign-an-interface、writing-fragments、imagegen可比較的候選方案
5. 製作原型Claude Code 實作 UIprototype、presentations、spreadsheets、hyperframes可打開的 artifact
6. 校準驗證/impeccable、Playwright 自測Browser 截圖、playwright、review、設計 token 檢查測試與回饋紀錄
7. 交付接力Figma/Claude Code 往返handoff、PR、簡報、文件、prototype 連結下一個人能接手
替換原則：如果你沒有圖上的 /superpowers、/impeccable 或 /normalize，不要硬找同名工具。問自己它在流程裡扮演什麼角色：發散、校準，還是統一設計 token？再選等價工具。

實作步驟（做完打勾）

用一句話寫出：誰要什麼、為什麼現在要、最後要交付什麼。例：PM 需要一個可點的設定頁 prototype，讓設計師明天 review。

如果需求還霧，先收斂；如果方向已定，做 prototype；如果 artifact 已有，跑驗證。不要因為某個 skill 很酷就先用它。

例：需求摘要、PROJECT.md、三個方案、可點 prototype、Playwright 截圖、handoff 文件。沒有輸出的步驟先砍掉。

不要一次開滿所有工具。先跑：需求摘要 → grill → prototype → browser/Playwright 檢查 → handoff。真的缺發散或設計 token，再插入對應槽位。

交付成果要包含三件事：artifact 本身、怎麼驗證過、下一個人該怎麼接。這讓 AI workflow 不只是產出，而是能接進團隊流程。

你已經把 skill 清單轉成工作流編排了。回對話視窗貼上你的需求、選到的槽位、以及第一輪交付成果。

觀念檢查（憑記憶作答）

1. 選 skill 前，第一個問題該問什麼？

本課的核心是 artifact-driven workflow。先知道下一個輸出，才知道要選收斂、發散、製作、驗證或交付類工具。

2. 圖上有你沒有的 skill 名稱時，該怎麼辦？

skill 名稱會變，槽位比較穩定。/superpowers 在圖上是發散；/impeccable 是 UI 校準；/normalize 是設計 token 統一。

3. Playwright 自測最適合放在哪裡？

Playwright 屬於驗證槽位。它需要一個可打開的 artifact，也應該早於交付，否則下一個人拿到的是未驗證成果。
