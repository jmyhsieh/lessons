完成 mattpocock/skills 的 repo setup

Phase 3 任務：用 mattpocock/skills 在真實 repo 中處理需求對齊、文件化、開發品質與缺陷分流。本課只有一個成果：選定安裝模式並跑完 /setup-matt-pocock-skills，讓後續 skills 知道 issue tracker、triage label vocabulary 與 domain docs 放在哪裡。

本課只做：完成安裝與 repo setup。
先不要做：建立 glossary、ADR，或啟動需求流程；它們會在真正釐清術語或決策時才按需產生。

這套 skills 在解什麼問題

Matt Pocock 把 AI 輔助開發的翻車原因歸納成四大失敗模式（GitHub README），每種配對應的 skill：

失敗模式症狀對策 skill
Misalignment
沒對齊需求		做出來的不是你要的/grill-me、/grill-with-docs — 動工前被追問到對齊
Verbosity
缺共享語言		詞彙不一致、溝通成本高domain-modeling、CONTEXT.md — 定義專案的領域語言
Broken code
回饋迴圈不足		看似完成、實則會壞/tdd、/diagnosing-bugs — 紅綠燈與系統化除錯
Architectural decay
架構腐化		越改越難改/improve-codebase-architecture、codebase-design、/to-spec、/to-tickets
為什麼這套對真實 repo 有價值：AI 最容易翻車的地方不是少打一行 code，而是需求沒對齊、詞彙不一致、驗證不足與架構慢慢腐化。CONTEXT.md 與真正需要的 ADR，讓 agent、工程師與 reviewer 共用同一套語言與決策脈絡。封閉或遺產系統只是風險最高的範例，不是唯一場景。

兩個地基概念

CONTEXT.md — 放在 repo 的純領域 glossary：只記系統術語與業務概念的精確定義，不放模組結構、class 名稱或其他實作細節。人和 AI 共用同一份。它和 Phase 1 第 06 課的 CLAUDE.md 分工：CLAUDE.md 講「怎麼工作」（規範、指令），CONTEXT.md 講「這個領域是什麼」（語言、概念）。

ADR（Architecture Decision Record） — 一份決策一個檔案，記「為什麼這樣設計」。只有當決策同時難以回頭、缺少背景會令人意外，而且是真實 tradeoff 的結果時才寫；少一項就跳過。/grill-with-docs 與 domain-modeling 會在術語或決策真正收斂時，才更新這些文件。

現行 shared skills — domain-modeling 管共享語言與決策脈絡，codebase-design 管深模組與介面設計語言；它們通常是其他 skill 背後共用的 vocabulary，不需要每次獨立成任務。

實作步驟（做完打勾）

Claude Code plugin（managed/current）：想直接訂閱 upstream、由 marketplace 管理唯讀 skill bundle，就在 Claude Code 裡執行：

/plugin marketplace add mattpocock/skills
/plugin install mattpocock-skills@mattpocock

Editable project copy（通用／Codex 路徑）：想把 skills 複製到 project 裡自行調整，或使用 Codex 與其他支援 Agent Skills 的 agent，就在目標 repo 目錄執行：

npx skills@latest add mattpocock/skills

兩條路選一條即可；選好後再進行下一步的 repo setup。

回到剛才選定的 agent session（plugin 路徑是 Claude Code；project copy 可在 Codex 或相容 agent 使用），執行：

/setup-matt-pocock-skills

它會先探索 repo，再依現況提出設定草案：issue tracker 一定會確認；只有安裝了 triage 才會問標籤；一般 repo 直接採 single-context，只有偵測到 monorepo 訊號才會問是否使用 multi-context。可用 GitHub 或 GitLab 就接正式 tracker；沒有 tracker、受限環境或練習 repo 再選 local markdown；Linear、Jira 或其他工具走 Other，把實際流程寫進 docs/agents/issue-tracker.md。GitHub／GitLab 的 external PR request surface 預設關閉，setup 不會追問；需要時再直接改 tracker 文件。寫入前先審完整草案，確認後才讓它修改檔案。

確認 agent 已回報並讓你審過 docs/agents/issue-tracker.md 與 docs/agents/domain.md；若已安裝 triage，再確認 docs/agents/triage-labels.md。這些檔案只描述後續 skills 的共同設定，不應預先製造 CONTEXT.md 或 ADR。

🎉 地基完成：安裝路徑與 repo setup 都已確認。回對話視窗回報：選了哪種安裝模式？setup 寫入了哪些設定檔？

觀念檢查（憑記憶作答）

1. 「系統裡有個內部術語叫『計費規則』，新功能會用到它」— 這個知識該放哪？

術語與概念 = CONTEXT.md。CLAUDE.md 管「怎麼工作」；ADR 記「為什麼這樣設計」— 三份文件三種職責。

2. 團隊曾在計費一致性與效能間取捨，最後決定繞過快取；這項選擇日後很難改，沒有背景也會令人意外。最該用哪個機制記錄？

這個情境同時符合難以回頭、缺少背景會令人意外、真實 tradeoff 三項條件，因此適合 ADR。TDD 保護的是行為不是原因；CONTEXT.md 只定義領域語言。

3. 本課的 repo setup 驗收後，哪組 artifacts 最符合邊界？

setup 只建立後續 skills 共用的 repo 設定：issue tracker 與 domain 設定一定會有，triage labels 只在安裝 triage 時出現。CONTEXT.md、ADR、spec 與 tickets 都要等真實需求出現後按需建立。
