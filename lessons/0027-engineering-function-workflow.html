工程職能 — 從 issue 到可 review diff

目標：把 Claude Code 放進工程紀律，而不是讓它無限制寫 code。你要練的是把 issue 切成可測、可 review、可交接的小 diff。

工程職能的穩定流程

Issue → Codebase 探索 → Plan / Spec → 小 diff → Test / Build / Lint → Review → PR / handoff

工程案例反覆出現三個 gate：session 能不能重跑、diff 是否小到能 review、工具層風險是否有被檢查。

槽位對照

槽位工程問題下一個 artifact
探索這段 codebase 怎麼運作？檔案地圖與修改點
計畫要改哪裡、不改哪裡？小 spec / plan
製作最小可驗證 diff 是什麼？小 diff 與測試
驗證什麼會證明它沒壞？test / build / lint / review 結果

實作步驟

請 Claude Code 先讀相關檔案、找 immediate callers、測試與現有 pattern，不要直接改。

plan 至少包含改動範圍、驗證指令、風險、rollback 或不做事項。

要求一次只交最小可驗證 diff。若需要多步，先切 issue 或 checkpoint。

用 review、subagent 或另一個 session 檢查 spec 與 standards，不讓寫 code 的同一條脈絡自己放行。

完成工程職能演練。把你的 issue 貼回對話，請 AI 老師檢查能不能切成更小 diff。

觀念檢查

1. Claude Code 開始改 repo 前，最該先做什麼？

工程職能要讀相關檔案、caller、測試與工具，再決定改法。

2. 好的工程 artifact 是？

可 review、可測、可回復的小 diff 比大量 code 更可靠。

3. 為什麼要分離 writer / reviewer？

寫作者容易合理化自己的改動；獨立 review 能補 spec 與 standards 缺口。
