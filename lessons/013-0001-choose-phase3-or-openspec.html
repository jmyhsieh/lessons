判斷這次工作要走 Phase 3 還是 OpenSpec

本課成果：一張工作路線卡，寫明選擇理由、規格正本與保留的交付檢查。

OpenSpec 管的是規格生命週期：跨工作階段的行為變更可以留在 repo 裡。需求追問、除錯、TDD、code review 與 handoff，仍沿用 Phase 3 的方法。

先看工作型態

目前情況建議路線
需求還模糊、正在 triage、查難解 bug，或找架構切入點先走 Phase 3，把問題縮成可交付的小變更。
工作可在一次 session 完成，完成後不需要維護 current behavior spec走 Phase 3 即可，不必為了用工具而增加規格流程。
工作會跨 session、交給多人審查，或完成後要留下目前行為規格用 OpenSpec 管 proposal、行為差異、tasks 與 archive。
需求先靠 Phase 3 釐清，之後仍需保存規格先完成釐清，再把單一變更交給 OpenSpec；實作時保留 Phase 3 的測試與審查。

做一張路線卡

句子要能指出誰在什麼情況下看到什麼結果。若目前只能寫成「改善系統」或「整理架構」，先回 Phase 3 做需求追問或診斷。

查看是否有人要接手、是否同時有別的 change、完成後是否需要 current spec，以及這項行為是否會繼續演進。

觀念檢查

一項已釐清、會跨多個 session，且完成後要保留 current spec 的行為變更，較適合哪條路？

OpenSpec 能把變更意圖、行為差異與封存後的目前規格留在 repo；同一項變更仍只留一份規格正本。

關鍵判斷

先把選路理由寫清楚。只有確定這項變更需要長期規格，才進下一課安裝 OpenSpec；否則留在 Phase 3。

主要閱讀：OpenSpec v1.6.0 Existing Projects；完整比較見 Phase 3／OpenSpec 路線卡。
