Phase 3 · Lesson 0038 · 約 25 分鐘 · Workflow patch

把 rehearsal finding 變成 workflow patch

目標：把第 37 課得到的一個 rehearsal finding，分類成 input、gate、evidence、handoff、closeout 或流程過重問題，然後只改最痛的一點。這一課不新增 runner 功能、不把一次發現擴成大改版。

演練後先修流程，不先加功能

Claude Code best practices 強調先用小範圍驗證工作流，再擴大。Repo rehearsal 的價值不是「我們跑過一次」，而是能從 evidence 看出哪個環節最弱。

Workflow patch 是很小的流程修補：可能只是一個 brief 欄位、一條 gate、一個 evidence path 檢查、一段 handoff 模板，或一個 closeout 規則。若 patch 需要新增平台、排程或多團隊治理，代表 rehearsal finding 還沒有被切小。

Finding 先分類

類型症狀最小 patch
input任務一直重講、scope 常變。補 brief 欄位或 scope-out 範例。
gate完成與否仍靠模型判斷。新增一條 deterministic check。
evidenceReviewer 找不到 stdout、截圖或結果。固定 artifact path。
handoff下一個 agent 還要問上下文。補 handoff section。
closeout不知道 ship、review、rerun 還是 blocked。補 decision rule。
overhead流程比任務本身還重。downgrade 或刪步驟。
判斷規則：一次 rehearsal 只產出一個 workflow patch。若你想同時改三件事，先選下一輪最可能重複造成成本的一件。

Workflow patch note 範例

{
  "findingId": "finding-0048-01",
  "sourceRunId": "run-0048",
  "category": "input",
  "symptom": "agent repeatedly asked whether documentation-only changes need tests",
  "patch": "add validation expectation field to brief template",
  "changedArtifact": "reference/harness-input-contract.html",
  "acceptance": "next rehearsal brief states when test evidence can be link-check only",
  "doNotDo": "do not add a new runner command"
}

實作步驟（做完打勾）

只拿第 37 課 rehearsal record 裡最痛的一個 finding。其他先放進 backlog，不要一起修。

把它歸到 input、gate、evidence、handoff、closeout 或 overhead。分類決定要改哪張表。

填 source run、category、symptom、patch、changed artifact、acceptance、do-not-do。這是下一輪改進 issue 的核心。

優先改 reference template 或 lesson note；只有連續多次 rehearsal 證明必要時，才改 runner。

下一輪 rehearsal 要能看出 patch 是否有效。若無法驗收，這個 patch 還太抽象。

你已完成 workflow patch。回對話視窗貼上 patch note，請 AI 老師檢查它是否真的只修一個可驗收問題。

觀念檢查（憑記憶作答）

1. 一次 rehearsal 最好修幾個問題？

一次只修一個，下一輪才知道改動是否有效；同時改太多會讓 evidence 失焦。

2. 找不到 artifact path 屬於哪類？

找不到 stdout、截圖、gate result 或 report path，是 evidence 問題，最小 patch 通常是固定 artifact path。

3. 流程比任務還重時該做？

如果流程成本高於任務價值，應該 downgrade 或刪步驟，不是繼續平台化。

下一步

把 patch note 當成下一輪 rehearsal 的起點。接著進入 第 39 課：用第二輪同類型 rehearsal 驗證 patch 是否有效。若同一類 finding 重複出現三次，再考慮把它固化進 runner、hook 或團隊模板；一次出現只改 reference 或 checklist。
