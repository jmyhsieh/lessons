/improve-codebase-architecture — 對抗架構腐化

目標：學會「深模組」的語言，在真實 repo 跑一次架構健檢，得到一份視覺化報告，並對其中一個候選跑 grilling loop。這是四大失敗模式的最後一塊：architectural decay。

核心概念：深模組（deep modules）

這個 skill 找的是「深化機會」— 把淺模組變深的重構。詞彙表（skill 規定每個建議都用這套語言，出自 LANGUAGE.md）：

術語意思
Module任何有介面＋實作的東西（函式、類別、套件）
Interface呼叫者必須知道的一切：型別、不變量、錯誤模式、順序、設定 — 不只是型別簽名
Depth 深度介面的槓桿：小介面後面藏大量行為 = 深；介面跟實作一樣複雜 = 淺
Seam 接縫介面所在之處；不改內部就能換行為的地方（第 18 課 to-prd 問你的就是這個）
Leverage / Locality深度給呼叫者的好處 / 給維護者的好處（改動、bug、知識集中一處）
三句口訣：(1) 刪除測試 — 想像刪掉這個模組：複雜度消失 = 它是過水層；複雜度散落到 N 個呼叫端重新出現 = 它有在賺自己的飯。(2) 介面就是測試面（接第 19 課：測行為不測實作）。(3) 一個 adapter = 假想接縫，兩個 adapter = 真接縫。

三段流程

  1. Explore — 先讀 CONTEXT.md 與 ADR，再派 Explore subagent（第 11 課的分身！）有機地走 codebase 找摩擦：理解一個概念要在很多小模組間跳？淺模組？為了好測而抽出純函式但 bug 都藏在呼叫端？
  2. HTML 報告 — 寫到 temp 目錄（不污染 repo）自動打開：每個候選一張卡（檔案、問題、解法、locality/leverage 效益、before/after 圖、建議強度 Strong / Worth exploring / Speculative），結尾給首選建議。此階段不提介面設計 — 報告完它會問你想深入哪個。
  3. Grilling loop — 你挑一個候選，進入拷問對話（第 16 課的肌肉直接重用）。過程中：新概念進 CONTEXT.md；你以站得住腳的理由拒絕某候選 → 它會提議寫成 ADR，讓未來的架構健檢不再重複建議同一件事。

兩個對高風險 repo 重要的設計：建議若與既有 ADR 衝突，只在摩擦真的大到值得重開決策時才提出（不重新爭論已決定的事）；領域講 CONTEXT.md 的語言、架構講 LANGUAGE.md 的語言。

實作步驟（做完打勾）

/improve-codebase-architecture

建議圈定範圍（例如你最近 TDD 動過的模組周邊），第一次別掃全 repo。等它產出並打開 HTML 報告。

逐卡閱讀，對每個「淺模組」指控自己跑一次刪除測試：刪掉它，複雜度是消失還是散落？你同意它的 Strong/Speculative 分級嗎？

建議挑「Strong 且範圍小」的。走完拷問：深化後的模組長什麼樣？接縫後面藏什麼？哪些測試存活？

挑一個你認為不值得做的，給出站得住腳的理由，觀察它是否提議寫 ADR — 體驗「拒絕也是知識」的制度。

grill 出來的深化計劃接你熟的 pipeline：/to-issues 切片 → 之後用 /tdd 實作。CONTEXT.md/ADR 的更新 commit 進版控。

觀念檢查（憑記憶作答）

1. 刪掉某個 wrapper 模組後，它做的事在六個呼叫端各自重新出現。結論是？

刪除測試的判讀：複雜度「重新散落到 N 個呼叫端」= 它本來把複雜度集中在一處（locality）— 這正是深模組的價值。消失才代表過水層。

2. 你拒絕了「合併兩個計費模組」的候選，因為監管要求它們分離。最該發生什麼？

站得住腳的拒絕理由 = 未來探索者需要的知識 → ADR（skill 原文的設計）。下次架構健檢讀到它，就不會再提同一個建議。

3.（複習第 19 課）「介面就是測試面」和 TDD 哲學的關係是？

（間隔複習）深模組的小介面 = 穩定的測試面；TDD 測行為不測實作。架構線和測試線在這裡會合：介面越深，測試越能在重構中存活。
