Phase 3 · 第 02 課 · 約 20 分鐘 · 路線判斷

用 /ask-matt 判斷該走哪條路

目標：在開始動手前，先用 /ask-matt 判斷現在是單一 session 的小需求、多 session build、外部回報、架構維護，還是需要跨 session 交接。這一課讓 Phase 3 從「背 skill 名稱」改成「選對流程」。

本課只做：判斷下一步該用哪條路。
先不要做：把 /ask-matt 當成會替你完成工作的萬用指令。

它是 router，不是施工隊

/ask-matt 的職責是把情境分到正確流程。它會告訴你該先用哪個 skill、何時切 session、何時改走 triage、wayfinder 或維護線。真正產出 spec、tickets、程式碼或 handoff 的，是後面的專門 skill。

情境建議路線
單一 session 能完成的新需求/grill-with-docs → 同一個 context 直接 /implement
需要多個 session 的 build/grill-with-docs → /to-spec → /to-tickets → 每張 ticket 開新 context 跑 /implement
必須用可跑成果回答的設計問題/handoff 出主線 → /prototype → /handoff 把答案帶回
外部 bug 或需求回報/triage → /diagnosing-bugs 或 /implement
巨大、模糊、超過一個 session 的 effort/wayfinder 先建立共享 map，逐張 decision ticket 推進到路徑清楚，再回到 /to-spec；只有 effort 最後縮成單一小任務才直接 /implement
架構維護/improve-codebase-architecture → 選一個改善點 → 回到 /grill-with-docs
context 太滿或要分支/handoff 開新 session；/compact 留在同一個 session。
記住主線：/implement 是實作 orchestrator；它內部會用 /tdd，做完再用 /code-review。不要把 /tdd 和 /code-review 畫成與 /implement 平行的主流程。
Context hygiene：從 grill 到 /to-tickets 盡量維持同一個未中斷 context，不要在中途 clear 或 compact；切完 tickets 後，每張 /implement 才各自用乾淨 context。若主線接近 smart zone 上限，先 /handoff，不要硬撐。
Wayfinder 是選修分支：只有當「通往 destination 的路仍看不清楚」，而且一個 session 放不下時才使用。若你已能列出完整 spec 與 tickets，就不需要先畫 map。選到這條路時，前往 第 13 課。

先分清楚：入口與流程內能力

不是每個 skill 名稱都代表同一種入口。初學時先把它們分成兩層，會比較不亂：

類型例子你怎麼用
主要手動入口/ask-matt、/grill-with-docs、/to-spec、/to-tickets、/implement、/triage、/wayfinder、/improve-codebase-architecture、/handoff你通常會主動選它們開始一段工作。
流程內能力/tdd、/code-review、diagnosing-bugs、domain-modeling、codebase-design常由主流程帶出來，或在特定情境下才單獨使用。

實作步驟（做完打勾）

各寫一句：一個新功能想法、一張外部 bug 回報、一個你覺得難維護的模組。

/ask-matt 我現在的情境是：[貼上情境]。我應該從哪個 skill 開始？

只看它選的路線與理由，先不要立刻執行後續指令。

如果它把 /tdd 或 /code-review 當成主流程起點，請它重新對照 /implement 的職責。

挑一個情境，記下下一課要帶進 repo 地圖或 grill 的輸入。

🎉 你現在知道 Phase 3 的路線入口了。回對話視窗回報：三個情境各被分到哪條路？

觀念檢查（憑記憶作答）

1. 一個新功能還不清楚，最合理的主線入口是？

新需求先對齊，不是先做。/grill-with-docs 會把想法、詞彙、程式碼現況與 ADR 放在同一個脈絡裡問清楚。

2. /implement 和 /tdd 的關係比較接近哪一種？

/implement 負責依 spec/ticket 施工；/tdd 是它內部用來保護實作品質的紀律。

3. Grill 後確認需求能在單一 session 完成，也不需要 prototype，下一步是？

只有 multi-session build 才需要先固化成 spec 與 tickets。小而已對齊的需求可以留在同一個 context，直接交給 /implement。

下一步

完成後回對話視窗回報。一般路線下一課是 Phase 3 第 03 課 — 不熟 repo 時，先建立地圖；若選到巨大模糊 effort，改走 Phase 3 選修第 13 課 — 畫出 shared map。
