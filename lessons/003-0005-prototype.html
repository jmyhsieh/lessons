當「這個狀態機對不對」或「這頁該長怎樣」只靠討論講不清楚時，可以用能跑的原型取得答案。確認過的狀態機或資料結構，再整理進後續規格與工作項目。

先補一個即時前置：若你還不熟 /handoff，先讀 Phase 3 第 12 課。用第一次交接把問題交給新的原型工作階段，完成後再用第二次交接把答案帶回主線，避免拋棄式探索污染主要對話。

核心定義

原型是用來回答問題、完成後可以丟棄的程式碼；問題會決定原型的形狀。所以第一步是選分支：

你的問題分支產出
「這個邏輯／狀態模型對嗎？」LOGIC小型互動終端機小程式，把狀態機推過紙上難想的案例
「這東西該長什麼樣？」UI同一個路由上數種差異極大的 UI 變體，用 URL 參數＋浮動列切換
選錯分支等於整個原型白做（工作技能原文）。問題若真的模糊且你不在線上，它會依周邊程式碼預設（後端模組→logic，頁面/元件→UI）並在原型開頭註明假設 — 但最好你自己先想清楚要回答哪個問題。

兩個分支都遵守的鐵律

  1. 第一天就是拋棄式，且標明 — 放在它將被使用的程式碼旁（脈絡清楚），但命名要讓人一眼看出是原型不是正式碼。
  2. 一個指令就能跑 — 用程式庫既有的工作執行工具，使用者不用猜怎麼啟動。
  3. 預設不持久化 — 狀態存記憶體。持久化是原型要檢驗的東西，不是它該依賴的。
  4. 跳過所有打磨 — 無測試、無錯誤處理（除了能跑起來所需）、無抽象。重點是快速學到東西。
  5. 把狀態攤開 — 每個動作後（logic）或每次切換變體後（UI），印出/渲染完整相關狀態，讓你看見變化。
  6. 吸收決策、保存證據 — 把驗證過的決策放進正式程式碼；完整原型則提交到不會合併的拋棄式分支，並在實作議題留下連結。
完成後留下兩樣東西：把「問題＋結論」寫進議題、提交或 ADR；原型則是產生答案的第一手證據，留在不會合併的拋棄式分支供未來重跑。main 只保留正式實作。

實作步驟（做完打勾）

從 grill 出來的計劃裡，挑一個「講不清、用想的會吵架」的點：一個棘手的狀態轉移、一個你拿不定的畫面。明確寫下「我要回答的問題是 X」。

/prototype 我想搞清楚 [你的問題]

先 /handoff 到新工作階段，再啟動 prototype。看它選 LOGIC 還是 UI — 對照你的問題，選對了嗎？選錯立刻糾正。

用它給的單一指令啟動。LOGIC：把狀態機推過邊界案例；UI：切換變體比較。重點是親手玩，不是看它描述。

玩出結論後，把「問題＋結論」寫進耐久處。只有決策同時難以回頭、缺少背景會令人意外，而且是實際取捨的結果時才寫 ADR；缺一就寫進實作議題或提交紀錄。

把驗證過的設計放進正式程式碼；接著把完整原型提交到不會合併的拋棄式分支，從 main 移除原型，並在實作議題留下分支連結。然後用 /handoff 把答案帶回主線。

完成條件：原型只回答一個設計問題，操作結果與得到的答案都已留下紀錄。

觀念檢查（憑記憶作答）

1. 原型預設不做持久化（狀態只放在記憶體）的理由是？

持久化是原型要檢驗的對象，不該先變成原型的依賴，否則會失去快速試錯的意義。

2. 原型回答完問題後，正確的保存方式是？

正式決策進 main，完整原型留在不會合併的拋棄式分支，議題再指向它。

3.「這個取消流程的狀態機對不對」該選哪個原型分支？

狀態／邏輯問題 → LOGIC 分支。原型用可執行的狀態機驗證它在邊界案例下行不行得通；這是本課剛建立的分支判斷，不是硬把前課包裝成提取練習。
