用 /prototype 驗證講不清的問題

目標：在 grill 後仍有問題必須用可跑成果回答時，用 /handoff 分支到 /prototype，做一個回答單一問題的拋棄式原型，再把答案帶回主線。pipeline 多了一道「先玩過再承諾」的保險。

本課只做：用可丟棄原型驗證一個設計問題。
先不要做：把 prototype 當 production foundation。

它在 pipeline 的位置

/grill-with-docs → /handoff → /prototype → /handoff → 回到主線
   Phase 3 第 04 課              本課                    Phase 3 第 06–08 課

不是每個需求都需要 prototype — 但當「這個 state machine 對不對」「這頁該長怎樣」用想的講不清時，原型用能跑的東西取代爭論。to-spec / to-tickets 可以把原型敲定的關鍵片段（state machine、schema）收進後續 spec 或 ticket。

跨 session 規則：主線裡需要 prototype 時，用 /handoff 把「要回答的問題」交給新 session；新 session 跑完 /prototype 後，再用 /handoff 把答案帶回原 thread。這能保留 grill → spec → tickets 的完整思路，也避免拋棄式探索污染主線 context。

核心定義（SKILL.md 原文）

「A prototype is throwaway code that answers a question. The question decides the shape.」— 問題決定形狀，所以第一步是選分支：

你的問題分支產出
「這個邏輯／狀態模型對嗎？」LOGIC小型互動終端機 app，把狀態機推過紙上難想的案例
「這東西該長什麼樣？」UI同一個路由上數種差異極大的 UI 變體，用 URL 參數＋浮動列切換
選錯分支等於整個原型白做（skill 原文）。問題若真的模糊且你不在線上，它會依周邊程式碼預設（後端模組→logic，頁面/元件→UI）並在原型開頭註明假設 — 但最好你自己先想清楚要回答哪個問題。

兩個分支都遵守的鐵律

  1. 第一天就是拋棄式，且標明 — 放在它將被使用的程式碼旁（脈絡清楚），但命名要讓人一眼看出是原型不是正式碼。
  2. 一個指令就能跑 — 用專案既有的 task runner，使用者不用思考怎麼啟動。
  3. 預設不持久化 — 狀態存記憶體。持久化是原型要檢驗的東西，不是它該依賴的。
  4. 跳過所有打磨 — 無測試、無錯誤處理（除了能跑起來所需）、無抽象。重點是快速學到東西。
  5. 把狀態攤開 — 每個動作後（logic）或每次切換變體後（UI），印出/渲染完整相關狀態，讓你看見變化。
  6. 吸收決策、保存證據 — 把驗證過的決策折進正式碼；完整原型則 commit 到不會 merge 的 throwaway branch，並在 implementation issue 留下 pointer。
完成後留下兩樣東西：答案是「問題＋結論」，寫進 issue、commit 或 ADR；原型是產生答案的 primary source，留在 throwaway branch 供未來重跑。main branch 只保留正式實作，不保留無測試、無錯誤處理的原型殘骸。

實作步驟（做完打勾）

從 grill 出來的計劃裡，挑一個「講不清、用想的會吵架」的點：一個棘手的狀態轉移、一個你拿不定的畫面。明確寫下「我要回答的問題是 X」。

/prototype 我想搞清楚 [你的問題]

先 /handoff 到新 session，再啟動 prototype。看它選 LOGIC 還是 UI — 對照你的問題，選對了嗎？選錯立刻糾正。

用它給的單一指令啟動。LOGIC：把狀態機推過邊界案例；UI：切換變體比較。重點是親手玩，不是看它描述。

玩出結論後，把「問題＋結論」寫進耐久處（若這決策難回頭→ADR；否則 implementation issue 或 commit）。

把驗證過的設計折進真正的程式碼；接著把完整原型 commit 到不會 merge 的 throwaway branch，從 main 移除原型，並在 implementation issue 留下 branch pointer。然後用 /handoff 把答案帶回主線，依規模接 /implement 或 /to-spec。

🎉 你用能跑的東西取代了一場設計爭論。回對話視窗回報：你回答了什麼問題？原型推翻了你原本的假設嗎？

觀念檢查（憑記憶作答）

1. prototype 預設不做持久化（state 存記憶體）的理由是？

skill 原文：persistence is the thing the prototype is checking。讓原型依賴它要驗證的東西，就失去了快速試錯的意義。

2. 原型回答完問題後，正確的保存方式是？

答案是耐久結論；原型是產生答案的 primary source。正式決策進 main，完整原型留在不會 merge 的 throwaway branch，issue 再指向它。

3.（複習 Phase 3 第 04 課）「這個取消流程的狀態機對不對」該選哪個分支？

狀態/邏輯問題 → LOGIC 分支。grill 銳化了「取消」的定義（Phase 3 第 04 課），prototype 用可跑的狀態機驗證它在邊界案例下行不行得通。
