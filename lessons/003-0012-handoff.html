Phase 2 · 第 12 課 · 約 20 分鐘 · 可攜式工作交接

用 /handoff 做可攜式工作交接

本課成果：一份能把工作帶到另一個 harness、目錄、程式庫或同事手上的可攜式交接文件。

本課只做：工作真的需要移動時，用 /handoff 打包下一個環境需要的脈絡。
先不要做：因為 context 快滿、準備收工或任意換 session，就把交接當成預設動作。

它解決的問題

/handoff 解決的是可攜性（portability）：工作必須離開目前的 harness、目錄、程式庫或執行者時，把不能由既有產出還原的脈絡壓成一份可帶走的文件。它不是一般性的 context 整理工具。

目前工作階段 → /handoff [目的地要做什麼]
                       ↓
             可攜式交接文件（作業系統暫存目錄）
                       ↓
另一個 harness／目錄／程式庫／同事 → 讀文件後接手

先走 phase-boundary decision tree

只有在一個 phase 結束、下一個 phase 要開始的邊界，才依序問下面五題；第一個「是」就是答案。不要在工作做到一半時為了整理 context 而切換。

順序問題選擇
1下一階段需要目前對話作為 primary source，或剩餘 smart zone 足以完成嗎？Continue：留在目前工作階段，資訊零損失
2目前 context 對下一階段完全無關嗎？/clear：清空 context；舊工作階段仍可恢復
3工作需要移到新 harness、新目錄／程式庫、同事手上，或把 mid-phase 副線帶到別處嗎？/handoff：產生可攜式文件
4工作範圍已明確，可以讓你離席後獨立完成嗎？Subagent：另開 context 執行，主線不動
5以上都不是，但相關 context 要帶進同一環境的下一階段嗎？/compact：預設落點，帶著有方向的摘要繼續
判斷核心：Continue 保留 primary source；/clear 丟掉無關 context；/handoff 買的是 portability；Subagent 適合 AFK；其餘 phase boundary 才落到 /compact。/compact 是預設落點，但因為摘要會有損，所以放在 decision tree 最後。

四個設計細節（SKILL.md 原文）

設計為什麼
存到作業系統暫存目錄，不放程式庫交接文件是消耗品，不該污染程式庫（同 Phase 2 第 11 課報告的做法）
不重複既有產出 — 規格、ADR、工作項目、提交紀錄用路徑引用單一事實來源：脈絡的正本在文件制度裡，交接只記「正本沒有的東西」（當下的決策過程、卡住的點、下一步）
內建 建議工作技能 區塊告訴下一個代理該用哪些工作技能繼續（例：「接下來跑 /implement 實作工作項目 3」）
產出時遮蔽敏感資訊（API key、密碼、個資）這是工作技能的必要指令，不是零漏網保證；交接前仍要自己掃一眼
參數很重要：使用 /handoff 下一個工作階段要做 X，它會針對 X 裁剪內容。「為了繼續除錯」和「為了寫文件」需要的脈絡完全不同。

什麼時候真的需要 /handoff

  • 換 harness：例如從 Claude Code 移到 Codex，需要一份不綁定原對話的文件。
  • 換目錄或程式庫：下一階段要在另一個 workspace 工作，原環境的 context 不會跟著走。
  • 跨人交接：需求追問到一半要請假，改由同事接手。先透過經授權的安全管道，把交接文件送到對方能讀取的路徑，再由他的 Claude Code 冷啟動。
  • mid-phase 副線：主線中發現一個不該打斷當前工作的副任務，把它交給另一個環境處理，再將結論帶回。
  • Prototype detour：prototype 會進入獨立目錄，因此 handoff → prototype → handoff 仍是正確案例；第一份把設計問題帶入原型，第二份把實測結論帶回主線。

「今天做到這裡」、「context 快滿」或「想換個乾淨 session」本身都不是 handoff 理由。若相關 context 還要留在同一個 harness 與目錄，而且無法直接 Continue，decision tree 通常會落到 /compact。只有某樣東西真的要移動時，才需要 handoff。跨人或跨機器時，本機暫存路徑不會自動同步，必須先經授權管道安全傳送。

跨機器邊界：不要把 /tmp/... 或 $TMPDIR/... 路徑直接貼給另一台機器。先重新檢查敏感資訊是否已遮蔽（redaction），再用組織核准的安全管道傳送；確認接手方可讀後，依資料保留政策清理兩端暫存副本。

實作步驟（做完打勾）

例如換 harness、移到另一個目錄／程式庫、交給同事，或把 mid-phase 副線帶到另一個環境。若只是收工或 context 快滿，改用 decision tree 選其他路線。

先排除 Continue 與 /clear，確認「某樣東西需要移動」是第一個成立的條件，再選 /handoff。把目的地、要接續的 phase 與選擇理由記下來。

/handoff 下一個工作階段要 [具體說明接下來做什麼]

打開暫存目錄的文件檢查：(a) 有沒有重複貼規格或工作項目內容（應引用路徑）？(b) 建議的下一個工作技能是否正確？(c) 有沒有漏網的敏感資訊？

在目標 harness、目錄、程式庫或同事可用的工作階段輸入：「讀 [文件路徑]，繼續這個工作」。觀察它是否還要追問本該寫在文件裡的事；如果需要，表示交接文件有漏洞，回頭補上。跨機器實測時，必須改用安全傳送後的目的端路徑。

完成條件：已記錄 decision tree 為何選到 /handoff，而且真正的目標環境已用交接文件成功接手；缺少的資訊也已補回文件。

Phase 2 驗收標準

不要用「12 課都看過」當結業證據，也不要強迫每條成果鏈都以 handoff 結尾。選一條真實路線，交出可驗證成果，再在 phase boundary 走一次 decision tree：

  • 新需求：對齊結論 → 規格／工作項目（若需要）→ 實作證據 → 程式碼審查 → phase-boundary route。
  • 外部回報：議題 → 分類狀態 → 診斷證據 → 回歸驗證 → phase-boundary route。
  • 維護改善：架構發現 → 被選定的接縫 → 規格／實作證據 → phase-boundary route。
  • 巨大模糊工作：決策地圖 → 關聯決策 → 規格 → 工作項目 → 實作證據 → phase-boundary route。

驗收時要能說出為何選 Continue、/clear、/handoff、Subagent 或 /compact。只有 decision tree 選到 handoff 時，才額外要求新的目標環境只靠成果與交接文件，說出「做了什麼、怎麼驗證、還剩什麼」。

觀念檢查（憑記憶作答）

1. 交接文件裡發現它把整份規格內容貼了進來，該怎麼處理？

工作技能原文：不重複既有產出，用路徑引用。複製會製造兩份會分岔的事實；交接文件的價值在「正本沒有的脈絡」（決策過程、卡點、下一步）。

2. Phase boundary 到了：相關 context 要留給下一階段、仍在同一個 harness 與目錄、需要你持續 steering，而且剩餘 smart zone 不足。decision tree 會落到哪裡？

context 相關，所以不能 clear；沒有任何東西要移動，所以不需 handoff；又不適合 AFK Subagent。排除前四個選項後，預設落點就是 /compact。

3. 哪個情境最符合 /handoff 的窄用途？

/handoff 買的是 portability。換 harness 且換程式庫需要一份能旅行的文件；收工或 context 快滿本身不是 handoff 理由。

4. 為什麼 handoff → prototype → handoff 仍是正確路線？

這條路線符合 portability：第一份交接把問題帶進獨立 prototype 目錄，第二份把實測結論帶回主線。若 prototype 沒有跨環境，就仍應重新走 decision tree。
