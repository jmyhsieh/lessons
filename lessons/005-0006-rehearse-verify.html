Phase 5 Lab · 第 06 課 · 約 40 分鐘 · Rehearse + verify

演練、修正並驗證 harness

目標：選一個低風險真實 repo 任務跑完整 lifecycle，找出一個 workflow finding，做最小 patch，再用同類型任務驗證是否有效。

本課只做：一次基準演練、一個 workflow patch、一次對照驗證。
先不要做：因為一次成功就平台化或強制化。

先練一輪，不先自動化

Claude Code best practices 強調先探索、計畫、實作、測試，再提交或開 PR；也建議先在少量檔案測試，再擴大範圍。Repo rehearsal 就是把這個原則放進 harness：先拿一個小任務跑完整輪，確認每個 artifact 真的有用。

CLI reference 與 Hooks reference 讓你把非互動執行、工具限制與 Stop 檢查接進流程。但第一輪 rehearsal 的目標不是寫更多自動化，而是找出流程在哪裡太重、太模糊、或缺證據。

任務挑選規則

可選不要選
小 bug、文件修正、單一元件測試、低風險 cleanup。跨服務 migration、付費流程、資料刪除、權限變更。
有明確驗收條件。只有「改善一下」的模糊目標。
可以在本機驗證。只能靠 production 行為判斷。
可在一個 branch 完成。需要多人同步與多 repo 協調。
判斷規則：如果 rehearsal 需要先建立平台、排程、dashboard 或跨團隊權限，它太大了。降級成更小的任務。

Rehearsal record 範例

{
  "inputId": "issue-0048-doc-link-fix",
  "repo": "product-web",
  "branch": "codex/rehearsal-doc-link-fix",
  "briefPath": ".harness/inputs/issue-0048.md",
  "runId": "run-0048",
  "gateResultsPath": ".harness/evidence/run-0048/gate-results.json",
  "handoffPath": ".harness/reports/run-0048-handoff.md",
  "closeoutDecision": "ship",
  "rehearsalFinding": "gate command was useful; input template needs clearer scope-out field"
}

一次只修一個 finding

把 finding 分成 input、gate、evidence、handoff、closeout 或流程過重。只選下一輪最可能再次造成返工的一項，寫成可回復的 workflow patch；不要同時改三個欄位、兩個 gate 和 runner 架構。

{
  "finding": "scope-out field is too vague",
  "category": "input",
  "patch": "require skipped validation classes",
  "expectedSignal": "fewer clarification turns",
  "rollback": "remove field if it adds questions without reducing rework"
}

用第二輪同類任務驗證

Patch 前後必須比較同類型、小範圍、相近 gates 的任務。觀察 clarification turns、gate failures、review rework 或 handoff gaps；結果只分 keep、revise、revert。

驗證規則：一次 rehearsal 只修一點，第二輪只驗證那一點。不同風險、不同 repo、不同 gates 的任務不能證明 patch 有效。

實作步驟（做完打勾）

用 Repo rehearsal 速查表 的挑選規則，排除高風險、跨系統、缺驗收條件的任務。

填 inputId、outcome、scope、scope-out、gates、stop condition。若寫不清楚，先回 Phase 5 第 02 課。

照順序產出 evidence、gate results、run history、final handoff。不要在第一輪補 dashboard。

只能選 ship、review、rerun、blocked、downgrade。每個非 ship 都要有 owner 與 next action。

把 finding 寫成有 expected signal 與 rollback 的 patch，再選同類任務比較 patch 前後，最後決定 keep、revise 或 revert。

你已完成 rehearsal 與 patch verification。回對話視窗貼上前後兩輪紀錄與決策，請 AI 老師檢查 evidence 是否真的支持 patch。

觀念檢查（憑記憶作答）

1. 第一輪 rehearsal 最適合選？

第一輪是驗證流程，不是挑戰組織邊界。低風險、可本機驗證、範圍小的任務最適合。

2. 驗證 workflow patch 時應比較什麼？

只有條件相近的同類型任務，才能把差異合理歸因於 workflow patch。

3. Rehearsal 第一輪最不該先做？

第一輪要驗證流程本身，先平台化會把尚未證明有價值的流程固定下來。

4. 演練後最有價值的產物？

Repo rehearsal 的重點是找到流程哪裡有用、哪裡太重，下一輪才能只改善最痛的一點。

下一步

只有第二輪 evidence 支持的 patch 才能進 repo contract。下一課會把它放到最小 contract target，並建立 review 與 effectiveness loop。

主要閱讀資源：Claude Code best practices 的小範圍實驗與 verification-first 原則；實作模板用 Repo rehearsal、Workflow patch、Patch verification。
