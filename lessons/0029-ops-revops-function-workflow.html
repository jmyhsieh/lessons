營運 / IT / RevOps — 從事件到可控系統更新

目標：把 Claude Code 放進營運流程時，先保護資料與系統。你要練的是先產生 diff / runbook / incident note，再由人核准寫入。

營運職能的穩定流程

營運事件 / 活動資料 → 擷取或診斷 → diff / runbook update → 人工核准 → 系統寫入

RevOps 與 IT 案例的共同風險是：AI 可能碰到客戶、CRM、設備或 production 資料。流程要先設可讀範圍、可改範圍與 rollback。

槽位對照

槽位營運問題下一個 artifact
擷取哪些資料要轉成結構化候選？import diff / entity match 表
診斷系統或流程哪裡卡住？incident note / diagnosis
核准誰能批准寫入？approval record
回復出錯怎麼退回？rollback checklist

實作步驟

列出 Claude Code 可以讀什麼、不能讀什麼、可以建議什麼、不能直接寫入什麼。

CRM、ticket、runbook 或設定變更，都先輸出候選差異與信心分數。

任何會碰到客戶、營收、設備或 production 的寫入，都要由 owner 核准。

每個系統更新都要留下復原方式、受影響範圍與檢查方法。

完成營運 / IT / RevOps 演練。把你的流程貼回對話，請 AI 老師指出第一個該加人工核准的地方。

觀念檢查

1. CRM 匯入前最該先交付什麼？

營運流程要先讓人看見變更，再決定是否寫入。

2. Claude Code 做 IT 診斷時，最重要的邊界是？

系統權限要先被界定，診斷結果也要由人核准。

3. runbook update 應該放在哪裡？

runbook 是讓下一次事件可重複處理的交付成果，應在寫入前就更新。
