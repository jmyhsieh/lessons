產品職能 — 從需求到可驗收原型

目標：把第 25 課的通用流程套到產品職能。你要練的是把需求霧氣變成可驗收 prototype，而不是讓 Claude Code 產生越多畫面越好。

產品職能的穩定流程

需求痛點 → 範圍切片 → 原型行為 → 使用者回饋 → 驗收證據 → handoff

產品職能最容易誤用 AI 的地方，是把「能做出來」當成「值得做」。Postcard Press 案例的重點不是四小時，而是更早拿到 ProductCon 回饋、付款整合與資安修正。

槽位對照

槽位產品問題下一個 artifact
收斂誰的哪個痛點要先解？一頁範圍與非目標
製作哪個行為必須被看見？可點 prototype 或 demo
驗證誰確認這真的有用？回饋紀錄、截圖、驗收條件
交付下一個人怎麼接？handoff 註記、風險、待辦

實作步驟

用三行寫出使用者、目標、非目標。沒有非目標，Claude Code 很容易擴張範圍。

不要說「做一個設定頁」。改成「使用者能打開通知設定、切換三個頻道、儲存後看到成功狀態」。

請 Claude Code 交付 prototype 時，同時附測試方式、已知限制、下一輪要問使用者的問題。

把 prototype、回饋、風險與未解問題交給設計、工程或下一個 agent，而不是只貼一個連結。

完成產品職能演練。把你的產品需求貼回對話，請 AI 老師檢查範圍是否過大。

觀念檢查

1. 產品職能最該先定義什麼？

產品課的核心是行為與驗收，不是工具或畫面數量。

2. Postcard Press 案例最值得學的是？

速度的價值在縮短 feedback loop，不是跳過付款、資安與上線檢查。

3. prototype 交付前要補什麼？

下一個人要能接手，所以交付要包含限制、測試方式與待辦。
