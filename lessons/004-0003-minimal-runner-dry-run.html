建立 minimal runner 與 dry-run

目標：把 Phase 4 第 02 課的 harness contract 變成第一個可執行切片：能列出任務、顯示解析結果、產生 dry-run plan。這一課不呼叫模型、不改工作區。

本課只做：list、show、run --dry 三個命令。
先不要做：真 agent call、排程、多任務或佇列。

Runner 不是平台

Claude Code best practices 建議用 claude -p 做非互動模式，並用 --output-format json 或 stream-json 讓腳本能解析輸出。Agent SDK 則適合你需要用程式控制 agent loop、工具與權限時再升級。

最小 runner 的價值不是「更聰明」，而是把可預期的部分交給 deterministic code：讀 input、組 prompt、限制工具、跑 gates、寫 report。模型只負責需要判斷與編輯的工作。

最小 runner 的五段

段落責任不要混進來
Load讀取 issue / brief 與 runner config。不要在這裡讓模型補需求。
Prompt用固定模板組出 agent prompt。不要每次手寫新 prompt。
Run呼叫 claude -p 或 SDK。不要先做 scheduler 或 queue。
Gate用 script 跑 test、lint、scope check。不要讓模型自稱通過。
Report把 evidence 寫進 report / handoff。不要只留在聊天紀錄。
list(): discover inputs → return stable JSON summary
show(id): load → validate → normalize contract
runDry(id): call show → render prompt/tools/gates/paths
            → return willCallAgent:false

這是 language-neutral starter：先讓三個純路徑可測，再決定用 Node、Python 或 repo 現有 CLI framework。若你還不能把這段轉成三個可測 handler，先不要進第 04 課。

判斷規則：一開始 runner 只接受一份 input、跑一個任務、產出一份 report。等單一路徑能穩定重跑，再談多任務、資料庫、佇列或平台。

第一個可執行切片

命令輸出副作用
runner list可執行 input 的 id、標題與狀態。無。
runner show <id>解析後的 contract，包含 scope、gates 與 stop conditions。無。
runner run --dry <id>即將使用的 prompt、tools、commands 與 artifact paths。不呼叫模型、不改檔。

把 /goal 與 effort 寫進 contract

Runner 不是把一句「請持續做到完成」塞進 prompt。若這條任務會由人手動啟動 Claude Code，可以把 /goal 的文字直接列為 Goal condition；若由 runner 呼叫，則把同一段轉成 stop conditions 與 gate precedence。Effort policy 要寫明預設值與升級條件。

欄位例子
Goal conditionAll declared gates pass, report includes evidence paths, and unverified items are empty or explicitly reviewed.
Effort policyDefault high; switch to a model that supports xhigh only when gate failures require cross-module reasoning; never use max in unattended runner.
Stop conditionsOut-of-scope files, missing credentials, repeated gate failure, or budget limit reached.

實作步驟（做完打勾）

只選已完成 Phase 4 第 02 課 contract 的任務：input 穩、gates 清楚、evidence 位置明確、report/handoff 模板已定。

打開 Minimal runner 速查表，先把 contract 填成文字，不要先寫程式。這一版要明確填入 goal condition 與 effort policy。

先確認 runner 能穩定找到 input、解析欄位並用 JSON 回傳結果。找不到 id 或 contract 不合法時要明確失敗。

Dry run 只印出 input、prompt、allowed tools、gates、output paths，不呼叫模型、不改檔。執行前後用 git diff --exit-code 或等價檢查證明工作區未變。

至少包含一個合法 contract、一個缺欄位 contract 與一個不存在的 id。只有 happy path，runner 很容易把錯誤任務送進 agent。

你已完成第一個 runner 切片。回對話視窗貼上三個命令的 JSON 輸出與無檔案變更證據，請 AI 老師檢查 dry-run 是否真的安全。

觀念檢查（憑記憶作答）

1. 最小 runner 一開始應該支援什麼？

最小 runner 先固定一份 input、一條路徑、一份 report。多任務與平台化要等單任務可重跑後再加。

2. Dry run 最重要的用途是什麼？

Dry run 不呼叫模型、不改檔，先驗證 input、prompt、allowed tools、gates、output paths 是否正確。

3. 哪種情況比較適合先用 SDK？

需要程式化控制工具、權限、session、telemetry 或多步事件處理時，SDK 才比單純 claude -p 更合適。

4. Runner 裡的 effort policy 應該寫什麼？

Runner 要能重跑，就要知道何時維持 high、何時連同模型升級、何時停止，而不是每次靠當下感覺。
