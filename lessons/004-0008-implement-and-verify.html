Phase 4 · 第 08 課 · 約 35 分鐘 · Repo 實作課

在 repo 實作並對照 intent 驗證

目標：讓 Claude Code 在既有 repo 完成一個最小垂直切片，跑過 repo checks，再用真實 browser 對照 design intent 驗證 responsive、interaction 與 accessibility，最後留下可接手的 closeout。

本課只做：實作 handoff 已同意的一條端到端路徑，驗證後收尾。
先不要做：順手重構相鄰模組、重建 design system，或以「測試有過」取代 browser 與 intent review。

知識：最小切片要可用，不只是可看

切片不是一個孤立元件，而是一條能完成的最短路徑：

進入點 → 看見必要資訊 → 執行主要動作 → 收到成功或失敗回饋

例如先做「搜尋一筆訂單並開啟詳情」，不要一次完成整個後台。切片仍要包含對應的 loading、empty 或 error 狀態；若本次不做，必須在 handoff 明列而不是悄悄消失。

知識：程式檢查與 browser evidence 缺一不可

Gate檢查內容Evidence
Repo checks專案既有 tests、lint、typecheck、build實際命令、結果、未執行項目
Intent review層級、內容、元件／token、狀態是否符合 bundle逐條 pass／deviation 與理由
Responsive窄、中、寬尺寸的重排、溢位與觸控目標viewport、截圖、觀察紀錄
Interaction滑鼠、鍵盤、成功、失敗與狀態轉移操作步驟、預期、實際
Accessibility語意、名稱、焦點、鍵盤操作、對比與訊息人工結果與自動工具輸出
不要只問「像不像設計稿」。要問：最重要的 intent 是否保留？差異是 repo 約束下的合理調整，還是漏實作？每個 deviation 都要有理由與決定。

實作 checklist（做完打勾）

在乾淨分支確認目標、non-goals、預計修改檔案與成功條件。先看 git status --short，不要覆蓋既有變更。

要求沿用既有元件、token、錯誤處理與測試慣例。完成後逐檔 review diff；若範圍長大，先縮回本切片。

執行專案既有 test、lint、typecheck 或 build。記錄確切命令與完整結果；不能跑的項目要寫原因，不能宣稱通過。

啟動本機專案，以窄／中／寬尺寸走主路徑；再用鍵盤、錯誤狀態與 accessibility checks 驗證。將每條 intent 標成 pass、deviation 或 blocker。

只修本次驗證找到、且屬於切片範圍的問題。重跑受影響 checks 與完整主路徑，避免修一處破壞另一個狀態。

再次確認 diff 只含必要變更。Handoff 寫清楚：改了什麼、驗證命令、browser evidence、已知 deviation、未做事項與下一步；再依 repo 規則 commit／PR。

你已完成從 design intent 到可驗證 repo 變更的閉環。把 closeout 貼回對話視窗，請 AI 老師檢查是否有未被證據支持的完成宣稱。

Closeout 最小格式

Changed: [切片與必要檔案]
Repo checks: [命令與結果]
Browser checks: [尺寸、互動、a11y 與結果]
Intent deviations: [差異、原因、決定]
Not verified: [未驗證項目與原因]
Next: [下一個最小步驟或 none]

觀念檢查（憑記憶作答）

1. 哪一個最符合「最小垂直切片」？

垂直切片從進入點走到結果，能被使用與驗證；它不是一次鋪完整平台或 design system。

2. 自動 tests 全過後，還缺哪一類關鍵證據？

Repo checks 不會自動證明 responsive、真實互動、焦點流程或 design intent。仍需 browser verification。

3. Closeout 遇到未跑的檢查時應怎麼寫？

Fail loudly：清楚列出未驗證項目與原因，讓下一位接手者知道證據邊界。
