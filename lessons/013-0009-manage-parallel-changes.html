管理平行 changes

本課成果：一張兩個 active changes 的狀態表，能明確指出各自的範圍、下一步、blocker 與同步時機。

每次下命令都寫出 change 名稱：Active changes 超過一個時，不要讓模型猜目前要處理哪一項。Apply、verify、sync 與 archive 前，都先對照狀態表與實際清單。

先把兩條工作線分開

openspec list

挑兩個真正在進行的 changes。若它們其實描述同一項行為，先合併或重切邊界，不要用兩份互相覆蓋的規格繼續。

Blocker／相依性無也要寫明無也要寫明

比較 delta specs、design、tasks 與預計修改路徑。若同時改到同一 requirement 或介面，先決定順序與重新驗證責任，不要等 archive 時才發現衝突。

/opsx:sync <change> 可在 change 仍 active 時把 delta 合併到 main specs；需要讓另一個 change 讀到新規格時才使用，並單獨審查 diff。一般完成線仍由 /opsx:archive <change> 處理同步提示與封存。

完成：兩個 changes 都有明確目前狀態與下一步，重疊處也已有順序或 blocker 決策。

觀念檢查

同時有多個 active changes，最能避免作用到錯誤對象的做法是什麼？

明確名稱讓命令、狀態表與實際 artifacts 能互相核對；猜測目前 change 容易把 tasks 或規格寫進錯的工作線。

停止線

不要因為 changes 多就直接 bulk archive。每一項都要分別確認 tasks、程式、測試、規格差異與封存結果；跨 repo 協調與 beta Stores 不在本課範圍。
