第 4 階段 · 設計 · 004-0002 · Brief

把模糊要求收斂成可驗收的 Design brief

進入條件：已選定 Design route，並有一個真實 mission。本課先固定問題、內容與 acceptance，不先接受第一個生成結果。

七欄把「好看」改成可觀察條件

欄位必須回答可觀察範例
目標（Goal）誰要完成什麼任務？新手能在兩分鐘內比較方案並選一個。
受眾（Audience）角色、情境、裝置與既有知識？第一次設定帳號、以手機操作的繁中使用者。
內容（Content）真實文案、資料與 states？價格、限制、loading、empty、error、disabled。
版面（Layout）區塊、層級與 responsive 行為？桌面雙欄；窄螢幕改單欄且 CTA 不溢位。
脈絡（Context）哪些 approved sources 不可被發明？design system、brand assets、repo、policy 等已核准來源。
非目標（Non-goals）本輪明確不做什麼？不改 pricing policy、不實作 repo。
驗收（Acceptance）要觀察什麼才進下一步？兩個方向都涵蓋 states，reviewer 能完成指定 task。

建立 brief artifact

Project / revision:
Goal:
Audience and use context:
Real content and required states:
Layout / responsive expectations:
Approved context and source of truth:
Accessibility expectations:
Non-goals / sensitive-data boundary:
Acceptance tasks and evidence:
Feedback giver:
Open assumptions:
  1. 刪除「現代、直覺、有質感」等無法驗收的形容詞，或替它補上 observable behavior。
  2. 至少加入一個 non-happy-path state 與一個窄 viewport expectation。
  3. 把尚未確認的事實標成 assumption，不要求 Claude 補成看似確定的內容。
  4. 請 feedback giver 只讀 brief，重述 user、task、限制與 success；重述不同就先修 brief。
具體成果：一份可交給另一人執行與驗收、且有 revision identity 的 Design brief。
可觀察回饋：Reviewer 不看作者補充說明，也能指出 user task、真實內容、states、non-goals 與 acceptance evidence；無法重述的欄位回到 brief 修正。

只在命中條件時走 design-system branch

若已有 approved design system、brand source 或可安全匯入的 product context，進 004-0003 校正；若沒有，明確記錄「無 approved context／不發明 tokens」，直接進 004-0004。這是 choose-one branch，不是缺課。

哪一項最能讓 brief 可驗收？

可觀察的 task、states 與 acceptance 能讓生成與 review 共用同一標準；風格形容詞不能獨立驗收。

合法停止／續行：Goal、真實 content、資料權限或 feedback giver 未定時，保存 brief draft 並回 readiness 補缺口。Brief 可重述後，依 approved context 選 conditional system branch 或直接到 direction exploration。
