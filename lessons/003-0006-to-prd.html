Phase 3 · 第 06 課 · 約 30 分鐘 · 固化任務

用 /to-prd 把對話凝結成 PRD

目標：把前面 grill 與 prototype 已經釐清的內容，整理成一份可引用、可審查、可切 issue 的 PRD。這一課只做「凝結」，不重新訪談，也不開始實作。

本課只做：把已對齊的內容整理成 PRD。
先不要做：需求還沒問清楚就硬產 PRD。

Pipeline 全景：你在這裡

/grill-with-docs → 可選 /prototype → /to-prd → /to-issues → /implement

凝結，不是再訪談

/to-prd 的關鍵設計是：不要再訪談使用者，直接綜合這個 session 已經知道的內容。若它開始問大量新問題，通常代表前面的 grill 沒做透，應該回去補對齊，而不是把 PRD 當補救訪談。

PRD 應該包含你要檢查什麼
問題陳述與範圍邊界是否清楚說明要解的問題，以及哪些事不做。
大量編號 user stories是否覆蓋 grill 中談過的場景與邊界案例。
實作決策與測試接縫是否尊重 CONTEXT.md、ADR 與既有 repo 介面。
發佈位置是否寫到第 01 課設定的 GitHub / Linear / local files。
你的主要工作：審 PRD 的「漏」與「多」。漏掉 user story 會讓後續 issue 不完整；多寫未同意 scope 會讓 agent 做出不該做的功能。

實作步驟（做完打勾）

最好在第 04 課 grill 的同一個 session 繼續。若已換 session，先提供 grill 結論、prototype 結論、CONTEXT.md 與相關 ADR。

/to-prd

若它說資訊不足，先回到 /grill-with-docs；不要在 PRD 階段臨時補一堆沒有驗證的假設。

逐條對照前面對齊過的需求：有沒有漏掉角色、例外、錯誤狀態、權限或資料邊界？

確認它提的 seams 是 repo 裡真實可測的位置。看不懂就追問：為什麼在這個介面驗證？有沒有更高層的接縫？

確認 PRD 被發佈到 issue tracker 或 local files，下一課才能用它切成 issues。

🎉 你已把對話凝結成 PRD。回對話視窗回報：PRD 裡最重要的 user story 是哪一條？

觀念檢查（憑記憶作答）

1. /to-prd 開始大量追問新需求，這代表？

/to-prd 是綜合已知內容，不是重新訪談。大量追問代表上游沒有足夠材料。

2. PRD 裡的 user stories 最重要的作用是？

下一課 /to-issues 會依 PRD 切成可認領的工作；user stories 是切片的主要材料。
