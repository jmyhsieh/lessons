Phase 3 · 第 07 課 · 約 35 分鐘 · 工作切片

用 /to-tickets 切成可認領工作

目標：把第 06 課的 spec 拆成一組可以獨立認領、獨立驗收的 tickets。這一課練的是「切片品質」與 blocking edges，不是把大計畫切成一堆技術層待辦。

本課只做：把 spec 切成可認領 tickets。
先不要做：用資料層、API 層、UI 層做水平切片。

Pipeline 全景：你在這裡

/to-spec → /to-tickets → /implement

垂直切片，不是水平分工

/to-tickets 的核心是 tracer bullet：每張 ticket 都是一條窄但完整的端到端路徑。它可以很小，但必須自己能 demo、能測、能判斷完成。

好的 ticket不好的 ticket
新增「查詢一筆訂單」：schema、API、畫面、測試最小通路。先建完所有資料表，之後再補 API 與畫面。
一張 ticket 有明確驗收條件與 Blocked by。一張 ticket 只寫「完成後端」或「整理前端」。
Blocked by 只列真正會卡住這張 ticket 的前置。把所有看起來相關的工作都塞進依賴清單。
你要把關的問題：這片能不能獨立驗收？Blocking edge 是否真的阻塞？如果不能，就要求它再切。這比 ticket 數量漂亮更重要。

Blocking edges 與 frontier

每張 ticket 都要列出 Blocked by：哪些 tickets 沒完成前，這張不能開始。沒有 blocker 的 ticket 就在 frontier 上，可以先被認領。local markdown tracker 會把 edges 寫成文字；GitHub、GitLab 或其他真 tracker 則盡量使用原生 blocking / sub-issue 關係。

欄位你要檢查什麼
Title一眼看得出它交付哪個行為。
What it delivers從使用者角度描述端到端結果，不是分層實作清單。
Blocked by只列真正 gate 住它的 tickets；沒有 blocker 就寫 None。
Acceptance criteria完成後能被檢查，不只是「看起來完成」。
Wide refactor 例外：若是欄位改名、共享型別重打這種 blast radius 很大的機械改動，不能硬切成普通垂直切片。改用 expand-contract：先加新形式，再分批搬 call sites，最後刪舊形式。

Local markdown：一張 ticket 一個檔案

使用 local tracker 時，upstream 的 canonical shape 是：

.scratch/<feature>/spec.md
.scratch/<feature>/issues/01-<slug>.md
.scratch/<feature>/issues/02-<slug>.md

每張 ticket 依 dependency order 編號，檔內包含 What to build、Blocked by、Status: ready-for-agent 與 acceptance criteria。不要把所有工作合併成單一 tickets.md。

實作步驟（做完打勾）

確認 spec 有 user stories、scope、驗收條件與測試接縫。沒有這些，先回第 06 課補 spec。

/to-tickets [spec 路徑或 issue 連結]

讓它先列出 ticket 草案，不要直接發布。

每片都問一次：能不能獨立 demo？能不能獨立測？是否只依賴少數明確前置？

每個 blocker 都追問：它沒完成時，這張 ticket 真的不能開始嗎？能平行就不要假裝依賴。

核准後發佈 tickets。local tracker 要確認是一張一檔，不是合併的 tickets.md。挑 frontier 上第一張可開始的 ticket，下一課開乾淨 context 用 /implement 完成。

🎉 Spec 已變成可認領工作。回對話視窗回報：你挑哪一張 ticket 當第一張 implement？

觀念檢查（憑記憶作答）

1. 哪個比較像垂直切片？

垂直切片要窄但完整，能自己 demo、自己驗收。只做一層是水平切片。

2. 一張 ticket 的 Blocked by 是 None，代表什麼？

沒有 blocker 代表它可開始，不代表重要性最高，也不代表可以跳過驗收。

3. 遇到 blast radius 很大的欄位改名，正確切法是？

wide refactor 是垂直切片的例外：先 expand 新形式，再分批 migrate，最後 contract 舊形式。

4. Local markdown tracker 的 tickets 應該怎麼存？

一張一檔才能讓每張 ticket 有自己的狀態、依賴與驗收條件，也能用路徑交給乾淨 context 的 /implement。
