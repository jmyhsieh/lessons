用 /to-tickets切成可認領工作

本課成果：一組可獨立認領、各自有完成條件的工作項目（tickets）。

本課只做：把規格切成可認領工作項目。
先不要做：用資料層、API 層、UI 層做水平切片。

工作流程全景：你在這裡

/to-spec → /to-tickets → /implement

垂直切片，不是水平分工

/to-tickets 的核心是 tracer bullet：每張工作項目都是一條窄但完整的端到端路徑。它可以很小，但必須自己能 demo、能測、能判斷完成。

好的工作項目不好的工作項目
新增「查詢一筆訂單」：schema、API、畫面、測試最小通路。先建完所有資料表，之後再補 API 與畫面。
一張工作項目有明確驗收條件與 Blocked by。一張工作項目只寫「完成後端」或「整理前端」。
Blocked by 只列真正會卡住這張工作項目的前置。把所有看起來相關的工作都塞進依賴清單。
你要把關的問題：這片能不能獨立驗收？Blocking edge 是否真的阻塞？如果不能，就要求它再切。這比工作項目數量漂亮更重要。

Blocking edges 與 frontier

每張工作項目都要列出 Blocked by：哪些工作項目沒完成前，這張不能開始。沒有 blocker 的工作項目就在 frontier 上，可以先被認領。local markdown 追蹤系統會把 edges 寫成文字；GitHub、GitLab 或其他真追蹤系統則盡量使用原生 blocking / sub-issue 關係。

欄位你要檢查什麼
Title一眼看得出它交付哪個行為。
What it delivers從使用者角度描述端到端結果，不是分層實作清單。
Blocked by只列真正關卡住它的工作項目；沒有 blocker 就寫 None。
Acceptance criteria完成後能被檢查，不只是「看起來完成」。
Wide refactor 例外：若是欄位改名、共享型別重打這種 blast radius 很大的機械改動，不能硬切成普通垂直切片。改用 expand-contract：先加新形式，再分批搬 call sites，最後刪舊形式。

Local markdown：一張工作項目一個檔案

使用 local 追蹤系統時，upstream 的 canonical shape 是：

.scratch/<feature>/spec.md
.scratch/<feature>/issues/01-<slug>.md
.scratch/<feature>/issues/02-<slug>.md

每張工作項目依 dependency order 編號，檔內包含 What to build、Blocked by、Status: ready-for-agent 與 acceptance criteria。不要把所有工作合併成單一 tickets.md。

實作步驟（做完打勾）

確認規格有使用情境、範圍、驗收條件與測試接縫。沒有這些，先回第 06 課補規格。

/to-tickets [spec 路徑或 issue 連結]

讓它先列出工作項目草案，不要直接發布。

每片都問一次：能不能獨立 demo？能不能獨立測？是否只依賴少數明確前置？

每個 blocker 都追問：它沒完成時，這張工作項目真的不能開始嗎？能平行就不要假裝依賴。

核准後發佈工作項目。local 追蹤系統要確認是一張一檔，不是合併的 tickets.md。挑 frontier 上第一張可開始的工作項目，下一課開乾淨對話脈絡用 /implement 完成。

完成條件：每張工作項目都有完成條件與相依關係，而且至少一張已可直接認領。

觀念檢查（憑記憶作答）

1. 哪個比較像垂直切片？

垂直切片要窄但完整，能自己 demo、自己驗收。只做一層是水平切片。

2. 一張工作項目的 Blocked by 是 None，代表什麼？

沒有 blocker 代表它可開始，不代表重要性最高，也不代表可以跳過驗收。

3. 遇到 blast radius 很大的欄位改名，正確切法是？

wide refactor 是垂直切片的例外：先 expand 新形式，再分批 migrate，最後 contract 舊形式。

4. Local markdown 追蹤系統的工作項目應該怎麼存？

一張一檔才能讓每張工作項目有自己的狀態、依賴與驗收條件，也能用路徑交給乾淨對話脈絡的 /implement。
