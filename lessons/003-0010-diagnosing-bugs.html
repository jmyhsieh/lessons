Phase 3 · 第 10 課 · 約 45 分鐘 · 缺陷修復

用 /diagnosing-bugs 做紀律除錯

本課成果：一份以可重現現象與驗證證據支持的錯誤診斷紀錄。

本課只做：用可重現訊號推進除錯。
先不要做：在沒有失敗案例（failing case）時只靠猜測改程式碼。

整個工作技能就一句話

/diagnosing-bugs 的核心是先建立快速、穩定，而且 Claude Code 能自己執行的通過／失敗訊號。有了回饋迴圈才能驗證假說；沒有它，就只能猜著修改。

六階段地圖

階段做什麼鐵律
1. 建回饋迴圈用十種武器之一造出通過／失敗訊號沒有迴圈不准進下一階段
2. 重現並最小化親眼看錯誤出現，再逐項刪除非必要輸入、呼叫端、設定、資料與步驟必須是使用者描述的那個錯誤；最後每個剩餘元素都不可再刪
3. 提出假說先列 3–5 個排序假說再測任何一個每個假說要可否證（能說出預測）
4. 加入觀測點每個探針對應一個預測，一次改一個變數除錯紀錄全部加唯一前綴（如 [DEBUG-a4f2]）
5. 修正並補回歸測試先寫回歸測試（看它失敗）再修只在「正確的接縫」寫；沒有正確接縫＝那本身就是發現
6. 清理並回顧搜尋前綴，清光除錯紀錄並記下學到的事沒清乾淨不算完成

重現後一定要最小化

看見紅燈只是前半段。接著一次只移除一個輸入、呼叫端、設定、資料或操作步驟，每移除一次就重跑回饋迴圈；能維持紅燈就繼續刪，變綠則把該元素放回。最後留下的最小重現案例（minimal reproduction）會縮小假說空間，也能成為乾淨的回歸測試。

程式庫地圖的邊界：陌生子系統可以用窄地圖協助找到真實呼叫路徑與測試接縫，但地圖必須服務於建立能重現紅燈的命令。

入門先用三種回饋迴圈

  1. 失敗測試：最適合已經有測試接縫的程式庫；先證明測試能重現錯誤。
  2. 重現命令：用 curl 或 CLI 固定輸入，每次修改後執行同一個命令。
  3. 瀏覽器證據：網頁錯誤先留下固定操作步驟、主控台訊息與追蹤記錄（trace），再比較修改前後。
前三種都做不到時，再看進階工具
  • 用固定資料比對輸出快照。
  • 重放已捕獲的請求資料或追蹤記錄。
  • 建立只執行錯誤路徑的拋棄式測試工具。
  • 用模糊測試（fuzzing）、git bisect 或新舊版本差分縮小問題。
  • 真的無法自動重現時，才保留人工操作腳本。
三個對高風險錯誤特別重要的細則： (1) 迴圈本身要迭代：「30 秒且會閃爍的迴圈只比沒有好一點；2 秒且確定性的迴圈是除錯超能力」。 (2) 非確定性錯誤：先把重現率拉高，不必等到每次都能乾淨重現。觸發 100 次、平行化、加壓、加入等待（sleep），50% 重現率就能除錯。 (3) 真的造不出迴圈時，它會停下來明說：向你要環境存取、捕獲資料（HAR 檔、執行紀錄傾印（log dump）或錄影）或臨時埋點的許可。它被禁止在沒有迴圈時瞎猜假說。

你的角色：在假說階段補上人類脈絡

它列出排序假說後會先給你看。這時補一句「#3 那個模組我們上週才改過」，就可能重新排定調查順序。工作技能也明定你不在場時它會照自己的排序繼續，不會卡住。

實作步驟（做完打勾）

從議題追蹤系統、QA 回報或產品待辦挑一個真實錯誤，最好有點難重現，才看得出這套紀律能幫上什麼忙。

/diagnosing-bugs [描述症狀：錯誤訊息、何時發生、影響誰]

觀察它選哪種武器造迴圈。迴圈造出來後問自己：夠快嗎？訊號夠尖嗎（斷言（assert）的是具體症狀，還是只有「沒有當掉（crash）」）？

逐一刪除輸入、呼叫端（caller）、設定、資料與步驟，每次都重跑同一個命令（command）。直到任何一項再刪都會讓訊號轉綠。

看到假說清單時認真讀，用你對系統、產品或近期變更的了解重排序或排除（「這個我們查過了」）。

確認：回歸測試先紅後綠了嗎？它寫測試的接縫真的能重現錯誤的觸發模式嗎？若它回報「沒有正確接縫」，把這個發現餵給 Phase 3 第 11 課的架構健檢。

搜尋除錯前綴，確認所有臨時紀錄已清除，再重跑原始情境。若修正釐清了領域術語，經人確認後才更新 CONTEXT.md；需要保存的重要取捨才寫 ADR，其餘留在議題或提交紀錄。

完成條件：診斷紀錄包含最小重現案例、排序過的假說、推翻假說的證據與修正後驗證。

觀念檢查（憑記憶作答）

1. 錯誤很難重現（約 1% 機率），/diagnosing-bugs 的正確策略是？

技能原文要求先提高重現率：50% 就能除錯，1% 不行。沒有迴圈就猜著修，正是這套紀律要根除的行為。

2. 為什麼要求「先列 3–5 個假說再測任何一個」？

單一假說生成會錨定（anchoring）：第一個合理解釋會吸走所有注意力。先發散再排序，而且每個假說都要能說出可否證的預測。

3.（複習 Phase 3 第 08 課）第 5 階段「先寫回歸測試、看它失敗、再修」對應 TDD 的什麼？

（間隔複習）同一條鐵律：測試必須先紅，證明它真的在測這個錯誤；修完轉綠才有意義。診斷迴圈就是 TDD 哲學的除錯變體。

4.（複習 Phase 3 第 03 課）陌生子系統出錯誤，程式庫地圖放在 /diagnosing-bugs 的哪個階段最有價值？

地圖可以協助找到呼叫路徑與測試接縫，但它服務的是能重現紅燈的命令；建立迴圈前，不能只靠閱讀程式碼猜原因。
