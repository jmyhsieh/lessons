Phase 3 · 第 10 課 · 約 45 分鐘 · 缺陷修復

用 /diagnosing-bugs 做紀律除錯

目標：學會六階段診斷紀律，下次真實 repo 出 bug 時用 /diagnosing-bugs 跑完整迴圈。這支 skill 的核心價值是把模糊症狀變成可重現、可驗證、可回歸的修復流程。

本課只做：用可重現訊號推進除錯。
先不要做：在沒有 failing case 時只靠猜測改 code。

整個 skill 就一句話

/diagnosing-bugs skill 原文：「This is the skill. Everything else is mechanical.」— 有了快速、確定性、agent 能自己跑的 pass/fail 訊號，bug 就等於修好了 90%；沒有它，盯 code 盯再久都沒用。這是 Phase 1 第 12 課「給它能自己跑的驗證」的除錯版，也是整套課程的母題。

六階段地圖

階段做什麼鐵律
1. 建回饋迴圈用十種武器之一造出 pass/fail 訊號沒有迴圈不准進下一階段
2. Reproduce + minimise親眼看 bug 出現，再逐項刪除非必要輸入、caller、設定、資料與步驟必須是使用者描述的那個 bug；最後每個剩餘元素都不可再刪
3. Hypothesise先列 3–5 個排序假說再測任何一個每個假說要可否證（能說出預測）
4. Instrument每個探針對應一個預測，一次改一個變數debug log 全部加唯一前綴（如 [DEBUG-a4f2]）
5. Fix + 回歸測試先寫回歸測試（看它失敗）再修只在「正確的接縫」寫；沒有正確接縫＝那本身就是發現
6. Cleanup + 復盤grep 前綴清光 debug log、記錄學到的沒清乾淨不算完成

重現後一定要最小化

看見紅燈只是 Phase 2 的前半。接著一次只移除一個輸入、caller、設定、資料或操作步驟，每移除一次就重跑回饋迴圈；能維持紅燈就繼續刪，變綠則把該元素放回。完成條件是：剩下的每個元素都對 bug 成立不可或缺。這份 minimal repro 會縮小假說空間，也會成為第 5 階段最乾淨的 regression test。

Repo 地圖的邊界：陌生子系統可以在第 1 階段用窄地圖協助找到真實 call path 與測試 seam，但地圖必須服務於建立 red-capable command。迴圈存在前，不要先靠讀 code 建立原因假說。

diagnosing-bugs 內部第 1 階段的武器庫（節選）

十種造迴圈的方法，大致依序嘗試：失敗測試 → curl/HTTP script → CLI＋fixture 比對快照 → headless browser → 重放捕獲的 trace（存下真實 payload 重放）→ 拋棄式 harness（mock 依賴只跑出 bug 的路徑）→ fuzz 迴圈 → bisection harness（自動化「回到狀態 X 檢查」讓 git bisect 跑）→ 差分迴圈（新舊版同輸入比輸出）→ 最後手段 HITL script。

三個對高風險 bug 特別重要的細則： (1) 迴圈本身要迭代 — 「30 秒且會閃爍的迴圈只比沒有好一點；2 秒且確定性的迴圈是除錯超能力」。 (2) 非確定性 bug：目標不是乾淨重現而是「拉高重現率」— 觸發 100 次、平行化、加壓、注入 sleep，50% 重現率就能除錯。 (3) 真的造不出迴圈時它會停下來明說，向你要環境存取、捕獲物（HAR/log dump/錄影）或臨時埋點的許可 — 它被禁止在沒有迴圈時瞎猜假說。

你的角色：diagnosing-bugs 內部第 3 階段的關鍵一秒

它列出排序假說後會先給你看 — 這是人類脈絡的關鍵介入點：「#3 那個模組我們上週才改過」一句話就能瞬間重排序。skill 也明定你不在場時它會照自己的排序繼續，不會卡住。

實作步驟（做完打勾）

從 issue tracker、QA 回報或產品待辦挑一個真實 bug — 最好是有點難重現的，才能看出這套紀律的價值。

/diagnosing-bugs [描述症狀：錯誤訊息、何時發生、影響誰]

觀察它選哪種武器造迴圈。迴圈造出來後問自己：夠快嗎？訊號夠尖嗎（assert 的是具體症狀還是「沒 crash」）？

逐一刪除輸入、caller、設定、資料與步驟，每次都重跑同一個 command。直到任何一項再刪都會讓訊號轉綠。

看到假說清單時認真讀，用你對系統、產品或近期變更的了解重排序或排除（「這個我們查過了」）。

確認：回歸測試先紅後綠了嗎？它寫測試的接縫真的能重現 bug 的觸發模式嗎？若它回報「沒有正確接縫」— 把這個發現餵給 Phase 3 第 11 課的架構健檢。

grep debug 前綴確認清光、原始（未最小化）情境重跑通過。修 bug 若釐清了領域術語，經人確認後才更新 CONTEXT.md；若形成決策，仍要同時通過難以回頭、缺少背景會令人意外、真實 tradeoff 三項 gate 才寫 ADR，否則留在 issue 或 commit。

🎉 缺陷線開張：你有了系統化除錯的紀律。回對話視窗回報：它用哪種武器造迴圈？你的人類脈絡在假說階段重排了什麼？

觀念檢查（憑記憶作答）

1. bug 很難重現（約 1% 機率），/diagnosing-bugs 的正確策略是？

skill 原文：目標不是乾淨重現而是「更高的重現率」— 50% 就能除錯，1% 不行。沒有迴圈就猜著修，正是這套紀律要根除的行為。

2. 為什麼要求「先列 3–5 個假說再測任何一個」？

單一假說生成會錨定（anchoring）— 第一個合理解釋會吸走所有注意力。先發散再排序，而且每個假說都要能說出可否證的預測。

3.（複習 Phase 3 第 08 課）第 5 階段「先寫回歸測試、看它失敗、再修」對應 TDD 的什麼？

（間隔複習）同一條鐵律：測試必須先紅 — 證明它真的在測這個 bug — 修完轉綠才有意義。診斷迴圈就是 TDD 哲學的除錯變體。

4.（複習 Phase 3 第 03 課）陌生子系統出 bug，repo 地圖放在 /diagnosing-bugs 的哪裡最有價值？

地圖可以協助找到 call path 與測試 seam，但它服務的是 red-capable command；迴圈存在前，不能先靠 code reading 建立原因假說。
