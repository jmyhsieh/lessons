Phase 3 · Lesson 0025 · 約 25 分鐘 · Harness mindset

判斷任務是否值得變成 harness

目標：判斷一個 Claude Code / skill 工作流，什麼時候值得從「單次對話」升級成可重跑、可驗證、可回報的 harness。這一課先學 mindset，不做 CLI runner 實作。

為什麼第 25 課從 harness 開始

第 24 課教的是 /handoff：把一次對話打包給下一個人或 agent。下一個問題是：如果同類任務會一直出現，是否還要每次靠人工重講？

單次 agent session → handoff → 可重跑流程 → harness

Harness 在這門課不是大型平台，也不是一開始就寫 task runner。它先是一張工作流契約：輸入從哪裡來、agent 怎麼跑、哪些 gate 必須過、證據要留在哪裡。

四個 harness 槽位

槽位要回答的問題例子
Input 這次任務的來源是 issue、brief、PRD、PR diff，還是手動指令？ issues/0017-fix-login-copy.md
Runner agent 要照什麼順序做：探索、計劃、實作、驗證、回報？ read → plan → edit → test → report
Gate 哪些測試、lint、review、權限規則或人工確認必須通過？ npm test、diff review、protected-file check
Evidence 結果要留下哪些報告、log、diff、截圖或 handoff？ .harness/reports/run-123.md
判斷規則：只有重複出現、輸入可描述、gate 可檢查、evidence 有價值的任務，才值得 harness 化。一次性探索、模糊產品判斷、需要大量人類取捨的任務，先留在一般 agent session。

實作步驟（做完打勾）

從第 18–24 課挑一條：PRD→issues、TDD、review、diagnose、QA/triage 或 handoff。先不要選太大的系統導入。

問四件事：會不會重複？輸入能不能標準化？驗收能不能自動或半自動？報告是否會被下一個人使用？

照 Harness readiness 速查表 填 Input、Runner、Gate、Evidence。每格都要有具體 artifact。

如果不值得，也要能說清楚原因。例：輸入太模糊、驗收依賴人類判斷、任務一年只出現一次。

格式：當 [input] 出現時，runner 依 [steps] 執行；必須通過 [gates]；最後留下 [evidence]。

你已完成 harness 判斷。回對話視窗貼上你的四槽摘要，請 AI 老師檢查它是否真的值得 harness 化。

觀念檢查（憑記憶作答）

1. 這一課的 harness 首先是什麼？

這一課先學 harness mindset。重點是 Input、Runner、Gate、Evidence 四個槽位，不是馬上做 CLI 或 task runner。

2. 哪種任務最適合 harness 化？

重複、可描述、可驗收、需要留下證據的任務最適合。模糊探索和高取捨決策先留在人類主導流程。

3. Evidence 槽位最主要留下什麼？

Evidence 要讓下一個人能重看結果、理解限制、接手判斷；不是留下宣傳語或工具名。

下一步

把你最常重複的 Claude Code 任務，用 Harness readiness 速查表 填一次。如果四格填不出來，先不要實作 harness；回到第 9–24 課，把 brief、驗收或 handoff 補清楚。若四格都穩，接著進入 第 26 課：把任務寫到 agent 可以直接接手。
