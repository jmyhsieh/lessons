Phase 3 mattpocock/skills 參考索引

同一組來源的 skills 放在這裡查；主線課程只保留從需求到交付最常用的路徑。

校準基準：upstream 66898f6（2026-07-13）。上游會持續變動，實際使用前仍要重新查閱 current repository 的 SKILL.md。

共同前置：在任何工程流程前先完成 /setup-matt-pocock-skills；未設定 issue tracker 與 domain docs 時先不要往下跑。

使用原則：先用主線入口推進工作；只有遇到特定情境，才拉出流程內能力或補充 skill。

項目選擇或規則課程

Editable project copy執行 npx skills@latest add mattpocock/skills。需要可編輯的 project copy，或從 Codex 等其他支援 skills 的 agent 使用時選這條；兩種模式擇一後再跑 setup。03-01
CONTEXT.md純粹、implementation-free 的領域詞彙表；第一個詞釐清後才逐步建立，不放 module 名稱或實作細節。03-01
ADR只有 decision 同時難以逆轉、缺少脈絡會令人意外，而且確實存在 tradeoff 時才寫；零篇 ADR 也可以。03-01

主要入口與 on-ramps

Skill用途課程
/ask-matt不知道該走哪條路時，先請它選入口。03-02
/grill-me沒有 codebase 時，用逐題訪談壓測計劃或設計；不讀寫 repo 文件。03-04
/grill-with-docs已有 codebase 時，用 grilling＋domain-modeling 問清楚需求；已確認詞彙才寫 CONTEXT.md，decision 也須同時符合三項門檻才寫 ADR。03-04
/prototype用拋棄式原型回答單一設計或邏輯問題；主線用 /handoff 進出。答案寫進 issue／commit／ADR，完整原型留在不 merge 的 throwaway branch 作為 primary source。03-05
/to-spec把已對齊的對話凝結成 spec；你可以把它理解成 PRD 的現行 canonical 名稱。03-06
/to-tickets把 spec 切成帶 blocking edges、可獨立認領與驗收的 tickets；local tracker 使用 .scratch/<feature>/issues/NN-slug.md，一張一檔。03-07
/implement完成一個已對齊的 bounded slice：單-session 小需求可沿用目前 context 的 plan；跨 session 工作則依 spec 與單張 ticket 冷啟動。兩者都包含 TDD、檢查與 /code-review 紀律。03-08
/triage把外部回報分流成 needs-info、ready-for-agent、ready-for-human 或 wontfix；agent-ready issue 通常交 /implement，難解、間歇或回歸 bug 才改走 diagnosing-bugs。03-09
/wayfinder巨大、模糊、超過一個 session 的 effort 先建立共享 map。普通 frontier ticket 一個 session 解一張；research ticket 是例外，charting 後可平行啟動 research subagents，讓結果留在不 merge 的 research/<name> branch，並在 ticket 留 context pointer。路徑清楚後回到 /to-spec。03-13 · 03-14 · 速查
/improve-codebase-architecture掃描架構深化機會；挑一個候選後回 /grill-with-docs。同-session 小改直接接 bounded implement；跨 session 才先產生 spec 與 tickets。03-11
/handoff把脈絡寫成 OS temp 文件供本機新 session 冷啟動。跨人或跨機器必須另用授權管道安全傳送；本機 temp 路徑不會自動同步。03-12

流程內能力

Skill / 能力定位何時出現
/tdd用 RED → GREEN 保護行為；refactoring 歸 review 階段。主要在 /implement 與除錯修復中出現。
/code-review以使用者提供的 fixed point（commit、branch、tag 或 merge-base）做 three-dot diff；先找 spec 與 repo standards，再由 Standards／Spec reviewers 平行檢查。Standards 以 repo 規則為準，Fowler code smell baseline 只當 heuristic；兩軸 findings side by side 呈現，不合併或跨軸重排。可作為 /implement 收尾關卡，也可獨立 review PR、branch 或 WIP。
diagnosing-bugs先建立 red-capable feedback loop，再重現、最小化、列假說、埋點、修復與回歸。難解、間歇或回歸 bug；repo 地圖只能服務回饋迴圈，不先代替它猜原因。
domain-modeling逐詞穩定專案的 implementation-free 領域語言；由人確認已釐清的詞彙後再寫進 CONTEXT.md。/grill-with-docs 與 CONTEXT.md 會反覆用到；ADR 仍須另外通過 foundation 的三項門檻。
codebase-design提供深模組、接縫與介面設計 vocabulary；Adapter 是在 seam 上滿足 interface 的具體角色，描述它填入哪個位置。/improve-codebase-architecture 與設計 review 時使用。

主線外補充

Skill使用時機為什麼不獨立成課
/research需要外部 primary sources、官方文件或 API 事實時，讓背景 agent 留一份 cited Markdown。它餵資料進 /grill-with-docs 或 spec，不直接替代需求對齊與交付主線。
resolving-merge-conflictsmerge 或 rebase 已經進入 conflict，需要理解雙方意圖、解每個 hunk、重跑檢查並完成 merge/rebase。它很重要，但只在衝突發生時使用；不屬於每個需求都會經過的主線。
