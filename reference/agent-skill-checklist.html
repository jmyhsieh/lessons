Claude Code 工作技能檢查表

把影片的四個問題——怎麼啟用、怎麼組織、怎麼引導、怎麼精簡——變成台灣工程師可以在真實 repo 逐項審查的路線。

根本目標：工作技能（Skill）要讓 Claude Code 每次走相近的過程，不是保證每次輸出逐字相同。先為真實 repo 做一個 Skill，再依 diff、檢查結果與交接品質修正；不要先蒐集一大包 Skills。

入門完成線

步驟你要核對完成證據
01 選流程同一組指示真的在 repo 工作中重複出現，而且有可觀察輸出與停止線。一張 Skill 需求卡
02 建 Skill專案範圍使用 .claude/skills/<skill-name>/SKILL.md；先審查 Claude Code 草稿再寫入。一個可用 /skill-name 執行的 Skill
03 選啟用方式要由工程師決定時機就設 disable-model-invocation: true；需要 Claude 自動發現時，description 才負責列出具體啟用情境。一張啟用方式決策卡
04 整理結構執行步驟（steps）是要做的順序；參考資料（reference）是執行時查用的規則。每個步驟都有可檢查的完成條件。第一次執行審查

四個進階檢查問題

軸核心問題常見失敗優先修法
啟用方式（Trigger）要由工程師手動啟用，還是讓 Claude 自動啟用？哪一種比較不會干擾目前對話？該用時沒用、不該用時亂用、Skills 太多而記不住先決定啟用方式；自動啟用的 description 只保留真實使用情境與工程師會說的詞。
內容結構（Structure）哪些是執行步驟，哪些是參考資料？每種使用情境都需要這段嗎？SKILL.md 過長、特定情境的資料一直佔用對話脈絡所有情境都需要的留在主檔；只有特定情境才要的放額外參考檔，按需讀取提示要寫清楚「何時讀」。
行為引導（Steering）有沒有一個 Claude 已熟悉的引導詞可以濃縮目標做法？完成條件是否要求它真的讀檔、查找與驗證？指示寫了卻沒改變行為、還沒驗證就過早收尾先改成正向而具體的引導詞，收緊完成條件；仍觀察到搶快才考慮拆成多個 Skill。
精簡整理（Pruning）每個規則是否只有一個維護來源？每句話真的會改變 Claude 的做法嗎？規則重複、過期內容堆積、無效指令、只寫禁止事項逐句測試刪除後是否有差；刪掉過期或無作用句，將禁止句改寫成正向目標。

啟用方式快速判斷

情境建議代價
要由工程師決定時機，或流程包含 commit、deploy、傳送訊息等外部影響使用者手動啟用；設定 disable-model-invocation: true人要記得 Skill 名稱與使用時機，增加記憶負擔。
Claude 必須在相關任務自動套用專案知識或檢查流程Claude 自動啟用；在 description 寫出具體啟用情境description 會進入對話脈絡，也要評估該用時沒用與不該用時亂用。
手動啟用的 Skills 多到記不住先刪除或合併不需要的；仍很多時再做一個手動使用的選路 Skill選路 Skill 只能幫人選擇，不能讓其他限定手動的 Skill 自動執行。

測試所需的最小證據

啟用方式與執行結果要分開測。準備應該啟用、不該啟用與輸出邊界案例；每個案例都開一個新的 Claude Code 對話，比較有 Skill 與停用 Skill 的結果。編寫 Skill 時留下的對話內容，會掩蓋 SKILL.md 真正缺少的指示。

停止線：一次成功只代表那次成功。至少保留測試提示詞、預期過程、實際檢查證據、有／沒有 Skill 的差異，以及下一個最小修改。
