Phase 8：Claude Code × Playwright

這個 Phase 不要求你手動背 Playwright API。你先把任務講清楚，讓 Claude Code 操作或產生變更；你負責觀看真實瀏覽器、審查規格、diff 與執行結果，並判斷證據是否足夠。

先選三層中的一層

層級用來回答工具與留下的證據
即時查核（live check）這條路徑現在正常嗎？Playwright MCP（或 Claude in Chrome）操作可見瀏覽器，留一份查核紀錄；不會自動變成 repo 測試。
耐久測試（durable test）以後壞掉時會被發現嗎？Claude Code 產生並執行 Playwright Test，留下已提交的測試與可解釋的失敗 → 通過紀錄。
代理工作流程（agent workflow）需求變多時，如何保留人工審查？Playwright Test Agents：規劃代理 → 核准規格 → 產生代理 → 已審查測試 → 修復代理；每一層都有可審查成果。

最小指令

node --version
claude mcp add --transport stdio --scope local playwright -- npx @playwright/mcp@latest
claude mcp get playwright

# 已有 Playwright Test 地基後，才建立 Claude Code 測試代理
npx playwright init-agents --loop=claude

Playwright MCP README 也示範較短的 claude mcp add playwright npx @playwright/mcp@latest。本課以 Claude Code 現行 MCP 文件的參數順序與 -- 分隔寫法為準。

三個可直接貼給 Claude Code 的提示

即時查核

只做瀏覽器查核，不要修改 repo 檔案。
使用 Playwright 打開＿＿URL，完成＿＿動作，確認＿＿結果。
每次導覽或操作後重新讀取頁面狀態。
回報實際步驟、觀察結果、console errors 與未知項目。

規劃代理

只讓 Playwright 規劃代理處理這條路徑：＿＿。
使用現有種子測試與這份需求：＿＿。
在 specs/ 下寫一份 Markdown 規格；不要產生測試或修改產品程式碼。

修復代理

只讓 Playwright 修復代理處理這個失敗測試：＿＿。
讀取已核准規格與 trace，先判斷原因在產品、測試或環境。
不要跳過、刪除或弱化 assertion，也不要為了通過而改變產品行為。
套用前先顯示建議 patch 與證據。

三條實作路線

路線順序留下什麼
即時查核01 選路 → 02 MCP → 03 可見瀏覽器當下操作與觀察紀錄；不會自動成為 repo 測試
耐久測試01 選路 → 04 Playwright Test測試 diff＋同一風險的失敗／通過輸出
代理流程04 地基 → 05 → 06 → 07 → 08 → 09核准規格、已審查測試、trace 與 CI 紀錄

進階 05–09

課只做這件事人工關卡
05以 --loop=claude 產生測試代理審查代理定義與種子測試
06讓規劃代理寫一份有限規格核准範圍、步驟與預期結果
07讓產生代理依核准規格產生一個測試比對規格、diff、locator 與測試輸出
08讓修復代理用 trace 診斷一個失敗禁止跳過或弱化 assertion；產品錯誤就停
09把已審查測試接到最小 CI 關卡核對專案、成果、執行紀錄與限制

安全與停止線

MCP 範圍：先用本機範圍。專案範圍的 .mcp.json 會成為團隊設定，必須先共同審查伺服器命令、來源與權限。
外部內容：瀏覽器讀到的網頁可能含提示注入（prompt injection）；不要讓未信任內容擴大操作範圍，也不要隨意啟用 repo 以外的檔案存取。
成果檔：報告、trace 與 screenshot 可能包含 token、資料或原始碼；限制存取與保留期限，分享前先脫敏。
人類責任：代理顯示成功不等於需求正確。每次都審查提示、規格、diff 與真實輸出；修復代理的綠燈也不能取代工程師判斷。

第 03 課與第 04 課各自是完成線，不必兩條都做。只有一條路徑時，不必初始化測試代理或建立完整瀏覽器矩陣；第 09 課也只能聲稱指定測試與專案有證據，不能說「所有 UI 都已自動驗證」。
