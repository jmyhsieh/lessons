Claude Code × Design Engineering Skills 路線卡

先分清楚要命名、審查、找機會、寫計畫還是執行，再叫對應的 Skill。

本路線採用的六個 Skills 不是一條自動流水線：上游 repo 可能另含其他 Skills；安裝後要記錄實際清單。每次只選一個工作，先訂範圍與完成證據。審查、命名、找候選與寫計畫不等於授權修改程式。

本路線採用的六個 Skills 怎麼選

你現在要完成使用 Skill這次成果不要拿它做什麼
用一致原則審查一個介面元件emil-design-eng修改前／修改後／原因表格不要把建議當成使用者證據
把「滑一下、彈一下」說清楚animation-vocabulary最佳 term、白話解釋與 close alternates 差異不要要求它設計規格或直接實作
套用 Apple 的流暢互動原則apple-design一個小範圍介面改動不要把整站改成 Apple 風格
審查一份既有動態差異review-animations問題清單（findings）與審查結論（verdict）不要用來盤點整個程式庫
找值得評估的動態位置find-animation-opportunities少量候選與排除理由不要要求每個地方都加效果
盤點、寫計畫或 dispatch 核准計畫improve-animations唯讀盤點、單一計畫，或交給獨立執行者後的受控差異不要把盤點或計畫直接當執行許可

兩條學習路線

路線順序完成線
入門安全安裝 → 審查單一元件 → 釐清一個術語 → 實作按壓回饋 → 審查該 diff一個小幅 diff、審查結論與真實瀏覽器證據
進階從第 05 課審查橋接 → 保留一項，也排除一項 → 建立單一計畫 → dispatch 給獨立執行者 → review diff計畫、diff、檢查結果與動態證據

先說明這個 Skill 會做什麼、不會做什麼。
只處理核准範圍；遇到現況不符就停止並回報。
除非我明確核准實作，否則不要修改產品程式。

交付前核對

核對項目要看到的證據
來源上游位置、版本或 commit、授權、實際安裝清單與安裝路徑
範圍精確檔案、元件、diff 或計畫；沒有順手改動
程式完整 diff、相關檢查結果與未通過項目
互動真實瀏覽器操作、快速重複、中途改變操作與減少動態
取捨採用理由、排除理由，以及仍未驗證的限制
停止線：不讓審查 Skill 或 improve-animations planner 自動改產品程式、不為了展示技巧到處加動態、不忽略 prefers-reduced-motion，也不在計畫與目前 commit 不符時硬著執行。
