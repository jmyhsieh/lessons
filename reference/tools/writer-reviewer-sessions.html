Writer／Reviewer 工作階段

讓一個工作階段負責產出，另一個不帶前一段實作對話，只依需求、diff 與證據重看固定成果，減少自己審自己時的盲點。

解決的問題

把作者與審查者角色分開

Reviewer 不承接所有實作對話，只依需求、diff 與證據重新檢查成果。

何時用

值得獨立再審一次

規格、安全性或維護風險較高，且可以提供固定 commit、diff 或 artifact 給 reviewer。

何時不用

沒有清楚交接邊界

若兩邊同時改同一批檔案，只會製造競爭；小型低風險修改也不必為了形式增加工作階段。

會讀寫什麼

Writer 寫，Reviewer 預設唯讀

交接內容包含需求、固定 diff、已跑檢查與未知風險；若需平行寫入，另用 worktree 隔離。

權限與副作用

明確指定唯一寫入者。Reviewer 不修程式，只回報 finding；作者收到回饋後另行修改，再以新 diff 驗證。

最低完成證據

  • 一份可獨立理解的 handoff，含需求與固定 diff／commit。
  • Reviewer findings 附位置、理由與嚴重度。
  • 每項 finding 有採納、拒絕或待確認的處理紀錄。

交給 Claude Code

你是唯讀 Reviewer。只審查固定成果「＿＿」，不要修改檔案。
先對照需求與 repo 規則，再檢查 diff、測試證據與未覆蓋風險。
只回報可定位、可重現的 findings；沒有 finding 就直接說明。
