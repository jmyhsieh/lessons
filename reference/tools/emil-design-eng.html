Design Engineering Skills · 介面審查

emil-design-eng

用一致的介面與動態設計原則，審查一個明確元件，產出可討論的修改前／修改後／原因表格。

解決的問題

把設計批評具體化

從階層、排版、互動與動態等面向，指出單一元件可改善之處。

何時用

需要一致的審查框架

元件已存在，但團隊只覺得「哪裡怪怪的」，需要具體問題與理由。

何時不用

不能取代使用者證據

Skill 的建議不是研究結果，也不是自動修改許可；實作動態可另選 apple-design。

會讀寫什麼

預設只讀元件與上下文

審查時只需讀核准檔案與畫面；要求它直接修改會擴大副作用。

權限與副作用

先凍結單一元件範圍。安裝 Skill 時保留來源、固定 commit、授權、實際路徑與移除方式；審查階段不得改產品程式。

最低完成證據

  • 修改前／建議修改後／原因的對照表。
  • 每項建議指向明確元件狀態或畫面。
  • 標出哪些是原則判斷、哪些仍需使用者驗證。

交給 Claude Code

請使用 emil-design-eng，只審查「＿＿」元件與指定檔案。
不要修改程式；以「現況／建議／原因／仍需驗證」表格輸出。
若需要讀取或改動範圍外內容，停止並先說明。
