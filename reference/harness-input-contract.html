Harness-ready issue / brief 速查表

把模糊任務改寫成 Claude Code / harness 可以穩定接手的 issue 或 brief。

先穩 input contract，再談 runner。如果 issue / brief 裡的任務來源、範圍、驗收與停止條件不穩，自動化只會把模糊需求跑得更快。

Issue / brief 六格模板

欄位必填問題不成熟訊號
ID這次任務如何被追蹤？只用「這個」、「剛剛那個問題」。
Source任務正本在哪裡？背景只在聊天紀錄，沒有文件或路徑。
Outcome完成後能觀察到什麼改變？寫「改善」、「優化」、「整理」但沒有可驗收結果。
Scope允許碰哪些檔案、系統、資料？沒有禁止區，也沒有保護路徑。
Gates哪些檢查不過就不能收工？只要求 agent 自稱完成。
Stop遇到哪些狀況必須停下來問人？secret、schema、刪除資料、需求衝突都沒列。

可直接貼進 issue

ID:
Source:
Outcome:

Stop:

Runner-ready prompt:
請讀取 [Source]，只在 [Scope] 內工作。
目標是 [Outcome]。
完成前必須通過 [Gates]。
若遇到 [Stop]，停止並回報問題，不要自行假設。

模糊任務改寫範例

模糊寫法contract 寫法
幫我看一下登入壞掉。 ID: issue-0042-login-timeout
Source: issues/0042.md
Outcome: session timeout 後重新登入成功導回原頁。
Scope: src/auth/**、tests/auth/**
Gates: npm test -- auth
Stop: 需要 production secret、要改 DB schema。

成熟度判斷

狀態判斷下一步
不成熟Source 或 Outcome 填不出來。回到需求釐清，不要 harness。
半成熟Source 與 Outcome 穩，但 Gates 或 Stop 還靠人工判斷。先用 checklist 與 handoff。
成熟六格都具體，陌生 agent 可依 contract 開始。進入最小 runner 設計。
