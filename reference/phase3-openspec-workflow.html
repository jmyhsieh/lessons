Phase 3／OpenSpec 工作路線卡

Phase 3 負責選路、釐清與安全交付；OpenSpec 負責把行為變更留在 repo 裡，讓 current specs 隨 archive 更新。

一項變更只留一份規格正本：選 OpenSpec 後，proposal、requirements、design 與 tasks 都放在 openspec/changes/<name>/。不要再替同一項工作建立另一份 .scratch spec／tickets。

先決定這次需不需要 OpenSpec

工作情況建議路線原因
範圍清楚、可在一個工作階段完成，也不需要長期行為規格Phase 3 有邊界的實作多一套規格生命週期只會增加維護成本。
需求仍模糊、正在 triage、查難解 bug 或找架構切入點先走 Phase 3要交給 OpenSpec 前，先把工作縮成一項說得清楚的 change；診斷與需求追問仍留在 Phase 3。
工作跨 session、會被多人審查，或完成後需要 current behavior specOpenSpecChange 目錄會保留變更意圖、行為差異、技術方案與 tasks；完成後還能從 archive 追查當時的決策。
兩個 changes 同時進行，而且各自會改動行為規格OpenSpec 進階每個 change 有獨立 artifacts，可明確指定 apply、verify、sync 與 archive 的對象。

OpenSpec 的兩種資料狀態

openspec/specs/                  系統目前已生效的行為

openspec/changes/add-timeout/   尚未封存的提議
├── proposal.md                 為什麼改、範圍到哪裡
├── specs/auth/spec.md          ADDED／MODIFIED／REMOVED
├── design.md                   技術方案與取捨
└── tasks.md                    實作清單

archive 後
├── delta specs 合併進 openspec/specs/
└── change 移到 openspec/changes/archive/YYYY-MM-DD-add-timeout/

Brownfield repo 不用先補完所有規格。第一個 change 只記錄它碰到的行為；後面的 archive 再逐步補齊其他領域。

命令要在哪裡輸入

位置用途常用命令
Terminal安裝、初始化、列出狀態、結構驗證與管理openspec init、openspec list、openspec show、openspec validate
Claude Code 對話探索、建立 artifacts、實作、查核、同步與封存/opsx:explore、/opsx:propose、/opsx:apply、/opsx:archive

新安裝的 core profile 已包含 explore、propose、apply、sync 與 archive。/opsx:new、/opsx:continue、/opsx:ff、/opsx:verify 與 bulk archive 屬於 expanded workflow，需先用 openspec config profile 選取，再執行 openspec update。

四個人工關卡

  1. Proposal：是不是你要解的問題？有沒有偷帶其他範圍？
  2. Delta specs：每項 requirement 是否可觀察？Scenario 有沒有涵蓋最怕壞掉的情況？
  3. Implementation：相關 tests、diff 與 code review 是否真的通過？
  4. Archive：Current spec 是否符合已交付行為？Archive 裡是否保留足夠脈絡？
停止線：不要把 openspec validate 當成產品測試，也不要因為 /opsx:verify 沒有 CRITICAL 就直接合併。Beta Stores、custom schemas 與大批量 archive 都留到真實需求出現後再學。
